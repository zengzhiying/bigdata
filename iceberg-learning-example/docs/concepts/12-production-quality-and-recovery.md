# 生产实践：质量门禁、表健康与逻辑恢复

Iceberg 的原子提交保证读者看到一次完整提交，但提交的数据仍可能违反业务规则。
实验 09 用三个层次进行验证：字段及主键规则、行数金额对账、恢复后的完整行比较；
实验 10 将质量门禁放在 CDC 当前态物化之后、分析指标构建之前。
主键唯一性需要写入流程或检查器负责，不能把 Iceberg 表当作自动约束主键的数据库。

## 质量检查的位置

实验先提交错误数据，再让 `assert_true` 抛出异常，便于观察检测和回滚。
这意味着异常数据在提交后已经可见，检查失败不会自动撤销 INSERT 或 UPDATE。
真实发布流程可以复用实验 03 的分支/WAP 机制，在候选数据上检查后再发布，并单独
验证目标引擎的引用与发布支持。业务规则应来自明确的数据契约；合法范围检查无法发现
所有错误，实验中每条订单金额增加 10 元就需要对账或完整数据比较才能识别。

流式场景还要区分摄取成功和业务数据合格：Flink 成功 Checkpoint 只说明原始事件已经可见，
不说明重复、乱序、删除和业务字段已经得到正确解释。实验 10 先将事件 append 到原始表，
由 Spark 按 `event_id` 去重、按版本 `MERGE` 为当前态，再对当前态执行质量门禁；通过后才
重建日指标表。质量检查失败不会撤销原始事件，也不能替代 Checkpoint、Source 延迟或恢复
状态的监控。

## 健康指标的解释

Data File 数量、大小和小文件比例帮助判断读取开销；Delete File 数量可提示合并读取
成本；Manifest 数量与保留快照数量用于观察规划及历史维护压力。这些指标受写入模式、
并发度和保留要求影响，不能对三行练习表机械套用生产阈值，也不能仅凭 WARN 自动清理。

当前引用应从 `refs.main` 获取。Snapshot ID 不按数值大小排序，最近生成的 Snapshot
在回滚后也未必是当前 Snapshot。提交时间不等于数据新鲜度，空提交、Metadata-only
提交及回滚都会影响解释。生产数据新鲜度应结合事件时间、摄取延迟与流任务状态。

## 回滚的范围

回滚只切换表的当前 Snapshot 引用，依赖目标快照及所有引用文件仍存在。
演练前应暂停同表写入及快照过期，记录基线 ID、预期数据和当前引用；演练后同时核对
数据及引用。行数和金额相同仍可能存在不同订单，因此恢复检查使用双向 `EXCEPT ALL`。

回滚不能恢复丢失的对象文件，也不覆盖 Catalog 故障或整个存储丢失。
实验 09 已在当前外部环境完成最小权限和隔离备份恢复演练：使用专属 Location
复制完整表树、恢复到原始 Location，并通过 `register_table` 重新注册完整 Metadata JSON
后验收读取结果。保留一个 Snapshot 或复制 Metadata JSON 本身仍不等于完整备份；恢复
需要同时覆盖 Catalog 状态、Iceberg Metadata 与所有被引用对象文件。

当前已落地可重复的质量检查、逻辑恢复、权限和隔离备份恢复路径，阶段 9 已完成；阶段 10
已验证将 CDC 原始事件、当前态质量门禁和指标构建串联为一条跨引擎路径。常见故障的排查见
[Spark、REST Catalog 与 MinIO 帮助手册](../faq-spark-rest-minio.md)；生产环境的升级回归
属于专有运维流程，不作为本项目学习案例。CDC Checkpoint 恢复仍需按 Source 和 Connector
的实际语义单独验证。
