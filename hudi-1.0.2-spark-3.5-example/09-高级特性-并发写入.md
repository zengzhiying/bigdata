# Hudi 高级特性：并发写入 (Concurrent Writes)

## 概述

并发写入（Concurrent Writes）是 Apache Hudi 支持**多个写入者同时向同一张表写入数据**的能力。它适合多个 Spark 作业、多个流式任务、批流任务或表服务同时操作同一张 Hudi 表的场景。

> 本笔记以当前示例项目使用的 Hudi `1.0.2` 为准。不同 Hudi 版本的配置项和可用锁实现可能不同，生产使用前应按实际依赖版本核对。

### 核心价值

- **提升总体吞吐量**：多个写入者可以并行准备数据和执行写入
- **解耦数据管道**：不同数据源或团队可以独立维护写入作业
- **支持批流协同**：批处理、流处理、Compaction、Clustering 等可以被统一协调
- **降低相互影响**：通过锁、heartbeat 和失败写清理策略减少异常写入对其他作业的影响

---

## 1. 并发写入挑战

### 1.1 无并发控制的问题

```
场景: 两个写入者同时更新同一个 file group

时间线:
T1: Writer-1 读取当前表状态，准备更新 fileId=A
T2: Writer-2 读取当前表状态，也准备更新 fileId=A
T3: Writer-1 写入新文件并提交
T4: Writer-2 基于旧状态写入并提交

问题:
- 可能丢失 Writer-1 的更新
- 同一 file group 的最终状态不确定
- Timeline 上可能留下互相冲突的提交、inflight 或 rollback 信息
```

### 1.2 需要解决的核心问题

1. **Timeline 串行化**：同一张表的提交、回滚、清理、压缩、聚类等 timeline 操作需要被协调
2. **文件组冲突**：多个写入者修改同一 partition + fileId/file group 时，不能让冲突提交同时成功
3. **失败写清理**：失败写入留下的文件不能被其他活跃写入者误删
4. **表服务并发**：Compaction、Clustering、Clean、Metadata Table 等服务也会修改表状态，需要纳入同一并发控制策略
5. **锁配置一致性**：所有并发写入者必须使用同一把表级锁，否则看似启用了 OCC，实际仍然没有互斥

## 2. Hudi 并发控制机制

### 2.1 并发模式

Hudi 1.0.2 的写并发模式由 `hoodie.write.concurrency.mode` 控制：

| 模式 | 含义 | 是否支持多写入者 | 典型场景 |
|------|------|------------------|----------|
| `single_writer` | 默认模式，假设同一时刻只有一个活跃写入者 | 否 | 单个写入作业 |
| `optimistic_concurrency_control` | 乐观并发控制（OCC），使用锁协调提交，并在提交阶段做冲突检测 | 是 | 常见多写入者场景 |
| `non_blocking_concurrency_control` | 非阻塞并发控制，允许多个 writer 写入同一 file group，由 reader/compactor 处理冲突 | 是 | 特定高并发场景，需充分验证 |

### 2.2 OCC 的基本流程

```
1. Writer-1 和 Writer-2 分别读取表状态并准备写入
2. 两个 writer 写出数据文件/marker，但尚未最终提交
3. 提交前获取同一把表级锁
4. 获得锁的 writer 检查从自己开始写入以来是否有重叠 file group 的提交
5. 无冲突则提交；有冲突则失败，是否重试由写入端和重试配置决定
6. 释放锁，下一位 writer 继续提交检查
```

注意：OCC 不表示冲突后一定会自动重新读取、重新计算并提交成功。默认冲突解析策略通常会让重叠写入失败；是否重试取决于 `hoodie.write.num.retries.on.conflict.failures` 以及作业自身的重试逻辑。

### 2.3 最小可用配置

```scala
df.write.format("hudi")
  .option("hoodie.table.name", tableName)
  .option("hoodie.write.concurrency.mode", "optimistic_concurrency_control")
  .option("hoodie.write.lock.provider",
    "org.apache.hudi.client.transaction.lock.ZookeeperBasedLockProvider")
  .option("hoodie.write.lock.zookeeper.url", "zk1:2181,zk2:2181,zk3:2181")
  .option("hoodie.write.lock.zookeeper.base_path", "/hudi/locks")
  .option("hoodie.write.lock.zookeeper.lock_key", s"${tableName}_lock")
  .option("hoodie.clean.failed.writes.policy", "LAZY")
  .save(basePath)
```

关键要求：所有写入同一张表的 writer 和表服务作业都必须使用相同的 `base_path` 和 `lock_key`。

## 3. 锁机制详解

### 3.1 ZooKeeper 锁

**生产环境常见选择**

```scala
.option("hoodie.write.concurrency.mode", "optimistic_concurrency_control")
.option("hoodie.write.lock.provider",
  "org.apache.hudi.client.transaction.lock.ZookeeperBasedLockProvider")

// ZooKeeper connect string，建议包含端口
.option("hoodie.write.lock.zookeeper.url", "zk1:2181,zk2:2181,zk3:2181")
.option("hoodie.write.lock.zookeeper.base_path", "/hudi/locks")
.option("hoodie.write.lock.zookeeper.lock_key", s"${tableName}_lock")

// 可选：超时配置
.option("hoodie.write.lock.zookeeper.session_timeout_ms", "60000")
.option("hoodie.write.lock.zookeeper.connection_timeout_ms", "15000")
```

说明：
- `hoodie.write.lock.zookeeper.url` 是 Curator 使用的连接串，通常直接写成 `host1:2181,host2:2181`。
- `hoodie.write.lock.zookeeper.port` 在该写法下通常不需要单独配置，避免与 url 端口产生误解。
- 同一张表的所有 writer 必须使用相同的 `base_path` 和 `lock_key`。

**优点：**
- 成熟稳定，适合多作业协调
- 支持 session timeout，writer 异常退出后锁可释放
- 可以与 Hudi HBase index 复用 ZooKeeper 集群

**缺点：**
- 需要部署和维护 ZooKeeper 集群
- 锁服务不可用时，写入作业通常会失败或长时间等待

### 3.2 Hive Metastore 锁

**适合已有 Hive Metastore 的环境**

```scala
.option("hoodie.write.concurrency.mode", "optimistic_concurrency_control")
.option("hoodie.write.lock.provider",
  "org.apache.hudi.hive.transaction.lock.HiveMetastoreBasedLockProvider")

.option("hoodie.write.lock.hivemetastore.database", "default")
.option("hoodie.write.lock.hivemetastore.table", "hudi_lock_table")
.option("hoodie.write.lock.hivemetastore.uris", "thrift://hive:9083")
```

**优点：**
- 可以复用现有 Hive Metastore
- 不需要额外引入 ZooKeeper 作为锁服务

**缺点：**
- 依赖 Hive Metastore 的可用性和事务锁行为
- 性能和稳定性需要结合实际 HMS 负载验证

### 3.3 Storage Based 锁

**Hudi 1.0.2 中可用的存储锁实现**

```scala
.option("hoodie.write.concurrency.mode", "optimistic_concurrency_control")
.option("hoodie.write.lock.provider",
  "org.apache.hudi.client.transaction.lock.StorageBasedLockProvider")

// 可选：锁租约和心跳轮询
.option("hoodie.write.lock.storage.validity.timeout.secs", "300")
.option("hoodie.write.lock.storage.heartbeat.poll.secs", "10")
```

**适用：** 希望减少外部协调组件、并且底层存储的原子创建/条件更新语义满足要求的环境。

**注意：** 不同对象存储或文件系统的一致性语义不同，生产使用前需要压测并验证异常退出、网络抖动、锁续租失败等场景。

### 3.4 DynamoDB 锁（AWS）

DynamoDB 锁通常用于 AWS 环境，但当前示例项目仅引入 `hudi-spark3.5-bundle_2.12:1.0.2`，本地 bundle 中没有 `org.apache.hudi.aws.transaction.lock.DynamoDBBasedLockProvider` 类。

如需使用 DynamoDB 锁，应额外引入 Hudi AWS 相关依赖，并按实际版本核对配置项和 AWS 权限。不要直接复制下面这类配置到当前示例项目中运行：

```scala
.option("hoodie.write.lock.provider",
  "org.apache.hudi.aws.transaction.lock.DynamoDBBasedLockProvider")
```

### 3.5 文件系统锁（仅测试或受控环境）

```scala
.option("hoodie.write.concurrency.mode", "optimistic_concurrency_control")
.option("hoodie.write.lock.provider",
  "org.apache.hudi.client.transaction.lock.FileSystemBasedLockProvider")
.option("hoodie.write.lock.filesystem.path", s"${basePath}/.hoodie/locks")
```

**不建议作为通用生产方案：**
- 对底层文件系统原子语义要求高
- 对 S3 等对象存储不一定可靠
- 异常退出和锁过期策略需要额外验证

## 4. 并发写入配置

### 4.1 核心配置参数

| 参数 | 说明 | Hudi 1.0.2 默认值 | 建议 |
|------|------|-------------------|------|
| `hoodie.write.concurrency.mode` | 写并发模式 | `single_writer` | 多写入者使用 `optimistic_concurrency_control` |
| `hoodie.write.lock.provider` | 锁提供者完整类名 | 无 | ZooKeeper/Hive/Storage，根据环境选择 |
| `hoodie.clean.failed.writes.policy` | 失败写清理策略 | `EAGER` | 多写入者必须使用 `LAZY` |
| `hoodie.write.lock.wait_time_ms` | 单次获取锁等待时间 | `60000` | 按作业耗时设置 |
| `hoodie.write.lock.num_retries` | 锁 provider 内部获取锁重试次数 | `15` | 按锁服务稳定性调整 |
| `hoodie.write.lock.wait_time_ms_between_retry` | 获取锁重试初始等待时间 | `1000` | 可按锁竞争程度调整 |
| `hoodie.write.lock.max_wait_time_ms_between_retry` | ZK 锁重试最大等待时间 | `16000` | 可按锁竞争程度调整 |
| `hoodie.write.lock.client.num_retries` | LockManager 层额外重试次数 | `50` | 通常保持默认或谨慎调大 |
| `hoodie.write.num.retries.on.conflict.failures` | 冲突失败后的批次重试次数 | `0` | 需要自动重试时显式配置 |
| `hoodie.write.lock.conflict.resolution.strategy` | 冲突解析策略类 | `org.apache.hudi.client.transaction.SimpleConcurrentFileWritesConflictResolutionStrategy` | 特殊索引或语义再定制 |

### 4.2 ZooKeeper 锁配置

| 参数 | 说明 | 示例 |
|------|------|------|
| `hoodie.write.lock.zookeeper.url` | ZK 连接串 | `zk1:2181,zk2:2181,zk3:2181` |
| `hoodie.write.lock.zookeeper.base_path` | ZK 基础路径 | `/hudi/locks` |
| `hoodie.write.lock.zookeeper.lock_key` | 表级锁键名 | `${tableName}_lock` |
| `hoodie.write.lock.zookeeper.session_timeout_ms` | 会话超时 | `60000` |
| `hoodie.write.lock.zookeeper.connection_timeout_ms` | 连接超时 | `15000` |

### 4.3 完整配置示例

```scala
// 生产环境并发写入配置示例（ZooKeeper + OCC）
df.write.format("hudi")
  .option("hoodie.table.name", tableName)

  // 启用 OCC
  .option("hoodie.write.concurrency.mode", "optimistic_concurrency_control")

  // 配置同一张表共享的锁
  .option("hoodie.write.lock.provider",
    "org.apache.hudi.client.transaction.lock.ZookeeperBasedLockProvider")
  .option("hoodie.write.lock.zookeeper.url", "zk1:2181,zk2:2181,zk3:2181")
  .option("hoodie.write.lock.zookeeper.base_path", "/hudi/locks")
  .option("hoodie.write.lock.zookeeper.lock_key", s"${tableName}_lock")

  // 锁获取配置
  .option("hoodie.write.lock.wait_time_ms", "120000")
  .option("hoodie.write.lock.num_retries", "15")
  .option("hoodie.write.lock.wait_time_ms_between_retry", "1000")

  // 多写入者场景必须使用 LAZY，避免清理其他活跃 writer 的临时文件
  .option("hoodie.clean.failed.writes.policy", "LAZY")

  // 可选：冲突失败后的批次重试。默认 0，打开前应评估作业幂等性
  .option("hoodie.write.num.retries.on.conflict.failures", "3")

  .save(basePath)
```

## 5. 并发写入模式与场景

### 5.1 分区隔离并发写入

**场景：** 多个写入者写入不同分区。

```
Writer-1: 写入 dt=2023-12-01
Writer-2: 写入 dt=2023-12-02
Writer-3: 写入 dt=2023-12-03

冲突概率: 低
推荐程度: 高
```

**建议：**
- 通过调度或业务规则保证不同 writer 处理不同分区
- 即使分区隔离，也要让所有 writer 使用同一锁配置
- 不需要配置不存在的 `partition` 冲突检测策略

**重要说明：分区隔离不能替代锁**

写入不同数据分区通常可以避免数据文件的 `partition + fileId/file group` 冲突，但不代表可以不启用并发控制。多个 writer 仍然会同时修改同一张 Hudi 表的 timeline；如果启用了 metadata table，还会同时更新 `<table_base_path>/.hoodie/metadata/` 下的内部 Hudi 表。

例如：

```text
Writer-1: 写入 dt=2023-12-01
Writer-2: 写入 dt=2023-12-02

数据文件层面:
  - 两个 writer 写入不同分区，file group 冲突概率低

表级元数据层面:
  - 两个 writer 都会提交到同一张数据表 timeline
  - 两个 writer 都可能更新 metadata table 的 files/column_stats/bloom_filter/record_index 等分区
  - clean、compaction、clustering 等表服务也可能同时修改表状态
```

因此，分区隔离的作用是**降低冲突概率、提升并发成功率**，不是取消锁需求。只要是多个 writer 同时写同一张 Hudi 表，尤其是 Hudi 1.0.2 默认启用 metadata table 的场景，仍然应使用 `optimistic_concurrency_control`、同一把表级锁和 `hoodie.clean.failed.writes.policy=LAZY`。

### 5.2 同分区并发写入

**场景：** 多个写入者可能写入相同分区。

```
Writer-1: 写入 dt=2023-12-01, 影响 fileId=A
Writer-2: 写入 dt=2023-12-01, 可能也影响 fileId=A

冲突概率: 中到高
推荐程度: 需要谨慎验证
```

**说明：**
- Hudi 默认 OCC 冲突检测关注重叠的 partition + fileId/file group，而不是单纯的分区名
- 同一分区内写入不同 file group 可能不冲突
- 同一 file group 的重叠写入通常只能一个成功，另一个失败或由上层重试

### 5.3 批流并发写入

**场景：** 批处理和流处理同时写入同一张表。

```
Batch Writer:
  - 处理历史或补数数据
  - 大批量写入
  - 可能触发 Compaction/Clustering/Clean

Stream Writer:
  - 处理实时数据
  - 小批量、高频写入

协调方式:
  - 使用相同锁配置
  - 使用 LAZY failed writes cleaner
  - 合理安排表服务的执行窗口
```

**配置建议：**

```scala
// Batch Writer
.option("hoodie.write.concurrency.mode", "optimistic_concurrency_control")
.option("hoodie.write.lock.wait_time_ms", "300000")
.option("hoodie.clean.failed.writes.policy", "LAZY")

// Stream Writer
.option("hoodie.write.concurrency.mode", "optimistic_concurrency_control")
.option("hoodie.write.lock.wait_time_ms", "60000")
.option("hoodie.clean.failed.writes.policy", "LAZY")
```

如果批处理还会执行 inline compaction 或 clustering，要确认这些表服务也使用同一套并发控制和锁配置。

## 6. 冲突检测与解决

### 6.1 Hudi 1.0.2 的默认冲突粒度

Hudi 1.0.2 没有 `hoodie.write.conflict.detection.strategy=partition/file_group/record` 这样的字符串枚举配置。默认冲突解析策略是：

```scala
.option("hoodie.write.lock.conflict.resolution.strategy",
  "org.apache.hudi.client.transaction.SimpleConcurrentFileWritesConflictResolutionStrategy")
```

该策略会比较两个并发操作变更过的 `partition + fileId` 集合：

```
Writer-1 mutated: (dt=2023-12-01, fileId=A)
Writer-2 mutated: (dt=2023-12-01, fileId=A)
=> 冲突

Writer-1 mutated: (dt=2023-12-01, fileId=A)
Writer-2 mutated: (dt=2023-12-01, fileId=B)
=> 通常不冲突
```

### 6.2 冲突后的处理

```
1. Writer-1 获取锁并提交成功
2. Writer-2 随后获取锁
3. Writer-2 发现 Writer-1 已提交，并且影响同一 file group
4. 默认策略无法合并两个重叠写入，Writer-2 提交失败
5. 如果配置了冲突失败重试，Writer-2 所在批次可以重新执行；否则作业失败，由调度系统处理
```

**相关配置：**

```scala
// 冲突失败后的批次重试次数，默认 0
.option("hoodie.write.num.retries.on.conflict.failures", "3")

// 锁获取重试，不等于冲突后的数据重算重试
.option("hoodie.write.lock.num_retries", "15")
.option("hoodie.write.lock.wait_time_ms_between_retry", "1000")
```

### 6.3 早期冲突检测

Hudi 还提供基于 marker 的早期冲突检测配置，可在创建 marker 前尽早发现冲突、释放计算资源：

```scala
.option("hoodie.write.concurrency.early.conflict.detection.enable", "true")
.option("hoodie.write.concurrency.early.conflict.detection.strategy", "<EarlyConflictDetectionStrategy 实现类>")
```

是否开启需要结合 marker 类型、timeline server、流式写入方式和作业稳定性验证，不建议在未验证前作为默认配置。

## 7. 性能优化

### 7.1 减少锁竞争和文件组冲突

**策略 1：分区隔离**

```sql
-- Writer-1
WHERE dt BETWEEN '2023-12-01' AND '2023-12-15'

-- Writer-2
WHERE dt BETWEEN '2023-12-16' AND '2023-12-31'
```

**策略 2：业务维度隔离**

```text
Writer-1: region=US
Writer-2: region=EU
Writer-3: region=APAC
```

**策略 3：时间错峰**

```bash
# 批处理在低峰期运行
0 2 * * * /path/to/batch_job.sh

# 流处理持续运行，但批处理窗口内降低写入频率或暂停部分补数任务
```

**策略 4：拆表再合并**

```text
stream_table/  -> 实时写入
batch_table/   -> 批量补数
main_table/    -> 周期性合并后的主表
```

### 7.2 锁超时优化

```scala
// 快速作业（流式微批）
.option("hoodie.write.lock.wait_time_ms", "30000")

// 慢速作业（大批量补数或带表服务）
.option("hoodie.write.lock.wait_time_ms", "300000")
```

设置原则：
- 太短：容易在锁竞争时失败
- 太长：异常作业可能让其他写入者等待过久
- 需要结合调度系统的超时、重试和告警统一设计

### 7.3 控制并发写入者数量

并发写入者越多，准备阶段吞吐越高，但提交锁竞争和 file group 冲突概率也越高。生产环境应通过压测确定合理数量，不建议直接照搬固定值。

建议压测维度：
- 写入者数量
- 每批数据量
- Upsert/Insert/Bulk Insert 操作类型
- 分区和 file group 重叠率
- 是否开启 metadata table、compaction、clustering、clean
- 锁服务延迟和可用性

## 8. 监控与故障排查

### 8.1 监控指标

**关键指标：**
- 锁获取等待时间
- 锁获取失败次数
- 冲突失败次数
- 冲突失败后的重试次数
- 提交成功率
- inflight/requested instant 是否长期滞留
- rollback、clean、compaction、clustering 的失败次数

**查看锁状态：**

```bash
# ZooKeeper 锁状态，路径以实际 base_path 和 lock_key 为准
zkCli.sh -server zk1:2181
> ls /hudi/locks
> ls /hudi/locks/table_name_lock

# 查看 Hudi Timeline
./hudi-cli.sh
> connect --path s3://bucket/table_path
> commits show
```

### 8.2 常见问题

#### 问题 1：锁获取超时

**症状：**

```
Failed to acquire lock after 60000ms
```

**原因：**
- 其他写入者或表服务持有锁时间过长
- ZooKeeper/Hive/Storage 锁服务不稳定
- 网络抖动或锁配置不一致

**解决：**

```scala
// 增加单次等待时间
.option("hoodie.write.lock.wait_time_ms", "180000")

// 调整锁重试
.option("hoodie.write.lock.num_retries", "15")
.option("hoodie.write.lock.wait_time_ms_between_retry", "1000")
```

```bash
# 检查 ZooKeeper 健康状态
echo stat | nc zk1 2181
```

#### 问题 2：频繁冲突失败

**症状：**

```
HoodieWriteConflictException
ConcurrentModificationException
```

**原因：**
- 多个写入者频繁更新同一 partition + fileId/file group
- 批流任务或补数任务处理范围重叠
- Compaction/Clustering 与写入任务重叠较多

**解决：**
- 优先做分区或业务维度隔离
- 对大批量补数任务做时间错峰
- 评估是否需要打开 `hoodie.write.num.retries.on.conflict.failures`
- 检查是否所有 writer 和表服务都使用同一锁配置

#### 问题 3：锁长期不释放

**症状：**
- 所有写入者都在等待锁
- ZK/HMS/Storage 中能看到疑似旧锁信息

**原因：**
- 写入者进程异常但锁 session 尚未超时
- 锁服务连接异常
- 手动 kill 作业后，调度系统又立即重启导致持续竞争

**解决：**
- 先确认是否还有活跃 writer 或表服务
- 等待 session timeout 或锁租约过期
- 检查 writer 日志和锁服务日志
- 必要时由运维在确认无活跃写入者后清理孤儿锁节点

> 不建议把 `delete /hudi/locks/...` 作为常规处理手段。误删活跃锁节点可能破坏正在进行的写入。

## 9. 最佳实践

### 9.1 推荐做法

1. **所有 writer 使用同一表级锁**

   ```scala
   .option("hoodie.write.lock.zookeeper.base_path", "/hudi/locks")
   .option("hoodie.write.lock.zookeeper.lock_key", s"${tableName}_lock")
   ```

2. **多写入者必须使用 LAZY 失败写清理**

   ```scala
   .option("hoodie.clean.failed.writes.policy", "LAZY")
   ```

3. **优先通过数据范围降低冲突**

   ```text
   不同 writer 尽量写不同分区、租户、地区或业务线。
   这只能降低数据 file group 冲突概率，不能替代表级锁；
   启用 metadata table 时，不同分区写入仍会更新同一张 metadata table。
   ```

4. **让表服务也纳入并发控制**

   ```text
   Compaction、Clustering、Clean、Metadata Table 相关作业应使用同一锁配置，或由调度系统保证不会与写入冲突
   ```

5. **使用完整类名配置锁和冲突策略**

   ```scala
   .option("hoodie.write.lock.provider",
     "org.apache.hudi.client.transaction.lock.ZookeeperBasedLockProvider")
   ```

### 9.2 避免的陷阱

1. **只配置了 concurrency mode，没配置锁 provider**

   ```scala
   // 不完整：OCC 需要锁 provider 和对应锁配置
   .option("hoodie.write.concurrency.mode", "optimistic_concurrency_control")
   ```

2. **不同 writer 使用了不同 lock_key**

   ```text
   Writer-1: lock_key=orders_lock
   Writer-2: lock_key=orders_job2_lock
   => 两个 writer 实际没有互斥
   ```

3. **继续使用 EAGER failed writes cleaner**

   ```scala
   // 多写入者场景错误
   .option("hoodie.clean.failed.writes.policy", "EAGER")
   ```

4. **使用不存在的冲突检测配置**

   ```scala
   // Hudi 1.0.2 中不是有效配置
   .option("hoodie.write.conflict.detection.strategy", "partition")
   ```

5. **把锁重试当作冲突重试**

   ```text
   hoodie.write.lock.num_retries 只影响获取锁重试；
   冲突失败后的批次重试应看 hoodie.write.num.retries.on.conflict.failures 和作业重试逻辑。
   ```

## 10. 实际应用场景

### 场景 1：Lambda 架构

```
Batch Layer:
  - Spark Batch Job
  - 处理历史数据或补数
  - 大批量写入

Speed Layer:
  - Spark Structured Streaming
  - 处理实时数据
  - 小批量高频写入

统一查询层:
  - Spark SQL / Trino / Presto
  - 查询同一张 Hudi 表或合并后的结果表
```

**配置重点：**

```scala
.option("hoodie.write.concurrency.mode", "optimistic_concurrency_control")
.option("hoodie.write.lock.provider",
  "org.apache.hudi.client.transaction.lock.ZookeeperBasedLockProvider")
.option("hoodie.write.lock.zookeeper.url", "zk1:2181,zk2:2181,zk3:2181")
.option("hoodie.write.lock.zookeeper.base_path", "/hudi/locks")
.option("hoodie.write.lock.zookeeper.lock_key", s"${tableName}_lock")
.option("hoodie.clean.failed.writes.policy", "LAZY")
```

### 场景 2：多租户数据湖

```
Tenant-1 Writer: 写入 region=US
Tenant-2 Writer: 写入 region=EU
Tenant-3 Writer: 写入 region=APAC

通过分区或业务维度隔离降低 file group 冲突概率
```

**配置重点：**

```scala
.option("hoodie.datasource.write.partitionpath.field", "region")
.option("hoodie.write.concurrency.mode", "optimistic_concurrency_control")
.option("hoodie.clean.failed.writes.policy", "LAZY")
```

### 场景 3：CDC 多源同步

```
MySQL CDC      -> Hudi Table
PostgreSQL CDC -> Hudi Table
Oracle CDC     -> Hudi Table
```

**设计建议：**
- 如果多个 CDC 源更新相同主键，应先明确主键归属和更新优先级
- 尽量按源表、业务域、分区范围拆分 writer
- 对同一主键的跨源更新，Hudi OCC 不能替代业务层的冲突合并规则
- 如果需要记录级合并语义，应通过 precombine 字段、payload/record merger、上游去重或统一 CDC 汇聚层设计

**配置重点：**

```scala
.option("hoodie.write.concurrency.mode", "optimistic_concurrency_control")
.option("hoodie.clean.failed.writes.policy", "LAZY")
.option("hoodie.write.num.retries.on.conflict.failures", "3")
```

## 11. 与 HBase 索引的配合

### 11.1 HBase 索引的作用

HBase 索引可以把 record key 到 file group 的映射存储在外部系统中，适合超大表或跨分区 upsert 的快速定位场景。

```
HBase Index:
  - 记录定位: record key -> partition + fileId
  - 外部存储: 多个作业可以访问同一索引表
  - 运维要求: HBase 可用性、QPS、回滚同步都需要监控

OCC / Lock:
  - 协调 timeline 和提交
  - 检测并发写入的 file group 冲突
```

### 11.2 注意事项

- HBase 索引不能替代并发控制，仍然需要 `hoodie.write.concurrency.mode` 和锁 provider
- HBase 索引会引入额外运维成本和外部系统依赖
- 需要关注 `hoodie.index.hbase.rollback.sync`、HBase QPS 限制、region server 稳定性
- 当前项目只是 Spark Hudi 示例，不应把 HBase Index 作为并发写入的默认推荐方案

### 11.3 配置示例

```scala
.option("hoodie.index.type", "HBASE")
.option("hoodie.index.hbase.zkquorum", "zk1,zk2,zk3")
.option("hoodie.index.hbase.zkport", "2181")
.option("hoodie.index.hbase.table", "hudi_index_table")

.option("hoodie.write.concurrency.mode", "optimistic_concurrency_control")
.option("hoodie.write.lock.provider",
  "org.apache.hudi.client.transaction.lock.ZookeeperBasedLockProvider")
.option("hoodie.clean.failed.writes.policy", "LAZY")
```

## 12. 常见问题 (FAQ)

### Q1：并发写入会影响性能吗？

会。主要开销来自锁获取、冲突检测、失败写清理和可能的重试。是否提升总体吞吐量取决于数据范围是否隔离、file group 冲突率、锁服务性能和 Spark 资源是否充足。

### Q2：最多支持多少个并发写入者？

没有一个适合所有场景的固定值。建议通过压测确定：从 2 个 writer 开始，逐步增加，观察锁等待时间、冲突失败率、提交成功率和端到端延迟。

### Q3：可以不使用锁吗？

单写入者场景可以使用默认 `single_writer`。多写入者使用 OCC 时必须配置锁 provider。否则多个 writer 无法可靠协调 timeline 和提交冲突。

### Q4：ZooKeeper 故障怎么办？

短暂故障通常会导致写入等待或重试；长时间故障会让写入失败。生产环境建议部署高可用 ZooKeeper 集群，并对连接失败、锁等待时间和 session timeout 做监控告警。

### Q5：如何测试并发写入？

```bash
# 同时启动多个 Spark 作业，确保它们写入同一张表并使用同一锁配置
spark-submit --class Writer1 ...
spark-submit --class Writer2 ...
```

验证建议：
- 检查 Hudi timeline 中是否有长期滞留的 requested/inflight instant
- 对比源端和 Hudi 快照表的主键数量、更新后最终值和关键字段 checksum
- 对同一主键多次更新场景验证 precombine 结果是否符合预期
- 人为制造一个 writer 失败，验证 `hoodie.clean.failed.writes.policy=LAZY` 下后续写入和清理是否正常

## 15. 总结

并发写入让 Hudi 可以支持多写入者和批流协同，但需要正确配置：

```scala
.option("hoodie.write.concurrency.mode", "optimistic_concurrency_control")
.option("hoodie.write.lock.provider",
  "org.apache.hudi.client.transaction.lock.ZookeeperBasedLockProvider")
.option("hoodie.write.lock.zookeeper.url", "zk1:2181,zk2:2181,zk3:2181")
.option("hoodie.write.lock.zookeeper.base_path", "/hudi/locks")
.option("hoodie.write.lock.zookeeper.lock_key", s"${tableName}_lock")
.option("hoodie.clean.failed.writes.policy", "LAZY")
```

核心原则：
- 多写入者不要使用默认 `single_writer`
- 所有 writer 和表服务使用同一把表级锁
- 多写入者必须使用 `hoodie.clean.failed.writes.policy=LAZY`
- 默认冲突粒度是重叠的 partition + fileId/file group，不是记录级自动合并
- 冲突重试、锁重试、作业重试是三类不同机制，需要分别设计
