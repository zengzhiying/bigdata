# Hudi 核心特性：清理 (Cleaning)

> 版本说明：本文以本项目使用的 Apache Hudi 1.0.2 + Spark 3.5 为准。Hudi 官网 latest 文档可能包含新版本能力，配置名和触发策略请优先以当前版本为准。

## 概述

清理（Cleaning）是 Apache Hudi 的表服务之一，用于删除表中不再需要的旧 file slices / 数据文件，从而控制存储成本、限制元数据和文件列表规模，并为时间旅行、增量查询保留一个明确的历史窗口。

Hudi 使用 MVCC 管理文件版本，核心原则是**不在原数据文件上做原地更新**：

- COW 表更新时，通常读取受影响的旧 base file，合并更新记录后写出新的 base file；旧 base file 继续保留在历史窗口内，过期后由 cleaner 删除。
- MOR 表更新时，通常先追加新的 delta log file，不会立即重写 base file；后续 compaction 再把 base file + log files 合并成新的 base file，旧 base/log file slices 再由 cleaner 按策略清理。
- 因此，“更新产生新版本，旧文件按清理策略后续回收”对 COW 和 MOR 都成立；只是 COW 更像“重写相关 base file”，MOR 更像“先追加 log，后压缩成新 base file”。
- Cleaner 删除的是数据文件或 file slices；commit / deltacommit 等 timeline 元数据主要由 archival 管理。

### 核心价值

- **释放存储空间**：删除已过保留窗口且不再服务当前快照的旧 file slices。
- **降低存储成本**：尤其适用于对象存储（S3、GCS、OSS）上的高频更新表。
- **限制元数据开销**：间接减少文件 listing、规划和表服务扫描成本。
- **维护表健康**：避免旧版本文件无限累积。
- **定义历史窗口**：决定时间旅行和增量查询最多能回溯多远。

## 1. 为什么需要 Cleaning？

### 1.1 Hudi 的版本管理

```text
以一个 COW file group 为例：

T1: 插入数据 -> file_1.parquet        当前快照使用
T2: 更新数据 -> file_2.parquet        当前快照使用，file_1 成为旧版本
T3: 更新数据 -> file_3.parquet        当前快照使用，file_1/file_2 成为旧版本

Cleaner 的目标：
- 当前快照仍需要的最新 file slice 必须保留。
- 保留窗口内的旧 file slices 保留，用于时间旅行和增量查询。
- 保留窗口外、且没有 savepoint 等保护的旧 file slices 可以物理删除。
```

MOR 表的更新链路不同：

```text
旧 base file + 新 delta log file -> 当前逻辑视图
compaction 后 -> 新 base file
旧 base/log file slices -> cleaner 后续清理
```

所以，COW 和 MOR 都不是“刷新原文件”。它们都保留旧文件来支撑 MVCC、时间旅行和增量查询，只是 COW 通常直接产出新 base file，MOR 通常先产出 log file，再由 compaction 产出新 base file。

### 1.2 不清理的后果

如果关闭 cleaner，或 cleaner 长期失败，旧文件会持续累积：

```text
假设每天更新一次，每次约产生 100GB 旧版本文件：

Day 1:  当前数据 1TB + 旧版本 100GB
Day 30: 当前数据 1TB + 旧版本 3TB
Day 90: 当前数据 1TB + 旧版本 9TB

影响：
- 存储成本持续增长
- 文件 listing 和元数据操作变慢
- 查询规划可能变慢
- compaction / clustering / cleaner 自身的规划成本上升
```

> 默认情况下，Hudi 1.0.2 已启用自动清理（`hoodie.clean.automatic=true`），因此真正危险的是关闭自动清理后没有外部调度，或清理任务持续失败但未监控。

## 2. 清理机制

### 2.1 清理流程

```text
Cleaning 基本流程：

1. 读取清理配置
   - 清理策略：按提交数、按 file slice 版本数、按小时保留
   - 触发策略：Hudi 1.0.2 只有 NUM_COMMITS

2. 扫描 timeline 和分区文件
   - 增量清理开启时，从上次 clean 之后的 timeline 事件推导待清理文件
   - 否则可能需要更重的全表/分区 listing

3. 生成 cleaner plan
   - 当前快照需要的最新 file slice 保留
   - 保留窗口内的旧 file slices 保留
   - savepoint 等保护的文件保留
   - 其他过期 file slices 标记为可删除

4. 执行物理删除
   - 删除 parquet / log 等实际数据文件

5. 写入 clean instant
   - 在 `.hoodie` 下记录 `.clean` 元数据，例如删除文件数、耗时、earliest commit to retain
```

### 2.2 清理类型

#### 2.2.1 Inline Cleaning（内联清理）

**定义：** 写入完成后，在同一个写入流程里同步执行清理。

**配置（Hudi 1.0.2 主配置名）：**

```scala
.option("hoodie.clean.automatic", "true")
.option("hoodie.clean.async.enabled", "false")
```

`hoodie.clean.async` 是旧/兼容配置名，Hudi 1.0.2 仍可识别，但新笔记建议优先写 `hoodie.clean.async.enabled`。

**特点：**

- 自动触发，配置简单。
- 清理和写入串行执行，可能增加写入延迟。
- 适合低频批处理或希望写入完成时立即回收空间的场景。

#### 2.2.2 Async Cleaning（异步清理）

**定义：** 写入触发清理后，由当前 writer 作业内部的后台 cleaner service 异步执行清理。

**配置：**

```scala
.option("hoodie.clean.automatic", "true")
.option("hoodie.clean.async.enabled", "true")
```

**特点：**

- 降低写入端等待清理完成的时间。
- 需要额外执行资源，清理结果会有延迟。
- 不需要额外部署一个常驻 Hudi 服务；但 cleaner 依赖触发它的 Spark application / writer 进程仍然存活。
- Hudi 表目录本身只是文件组织，不会在 Spark 任务退出后继续运行 cleaner。
- 更适合长期运行的 streaming job 或持续写入作业；短生命周期 batch job 如果很快退出，异步 clean 可能来不及完成。

```text
短生命周期 batch job：
write -> commit -> 触发 async cleaner -> Spark application 退出
                                      -> cleaner 可能未完成

长期 streaming job：
write -> commit -> 触发 async cleaner
Spark application 持续运行 -> cleaner 有机会在后台完成
```

因此，对短 batch 任务更稳妥的选择通常是：

- 使用 inline cleaning：`hoodie.clean.async.enabled=false`，让当前写入任务同步完成清理。
- 或关闭自动清理：`hoodie.clean.automatic=false`，再由 Airflow、DolphinScheduler、crontab、独立 Spark SQL `CALL run_clean(...)` 等外部维护任务定期清理。

#### 2.2.3 Manual Cleaning（手动清理）

**定义：** 关闭自动清理或保留自动清理的同时，在需要时手动触发 cleaner。

当前项目依赖的 `hudi-spark3.5-bundle_2.12-1.0.2.jar` 中没有 `org.apache.hudi.utilities.HoodieCleaner` 这个类，不能直接使用该类名 `spark-submit`。Spark 侧可以使用 Hudi procedure（取决于 catalog/procedure 注册方式）：

```sql
-- 常见形式：按表名触发 clean
CALL run_clean(table => 'db.table_name');

-- 可显式覆盖策略参数
CALL run_clean(
  table => 'db.table_name',
  clean_policy => 'KEEP_LATEST_COMMITS',
  retain_commits => 20,
  trigger_strategy => 'NUM_COMMITS',
  trigger_max_commits => 1
);
```

如果使用 Hudi CLI 或单独的 utilities 包，应以对应包版本的官方命令为准，不要假设当前 Spark bundle 自带 `HoodieCleaner` 主类。

**适用：** 需要在维护窗口清理、需要外部调度统一管控、或需要事故后手动重跑 cleaner 的场景。

## 3. 清理策略

Hudi 1.0.2 的主配置名是 `hoodie.clean.policy`。`hoodie.cleaner.policy` 是兼容旧名，仍可用，但新配置建议使用主 key。

### 3.1 KEEP_LATEST_COMMITS（推荐）

**策略：** 保留最近 N 个提交对应的历史窗口，窗口外的旧 file slices 可被清理。

**配置：**

```scala
.option("hoodie.clean.policy", "KEEP_LATEST_COMMITS")
.option("hoodie.clean.commits.retained", "10")
```

兼容旧名：

```scala
.option("hoodie.cleaner.policy", "KEEP_LATEST_COMMITS")
.option("hoodie.cleaner.commits.retained", "10")
```

**工作原理：**

```text
Timeline: [C1] -> [C2] -> [C3] -> ... -> [C10] -> [C11] -> [C12] 最新

配置：hoodie.clean.commits.retained = 10

清理含义：
- earliest commit to retain 大约落在 C3。
- C3-C12 窗口内用于时间旅行/增量查询的旧 file slices 尽量保留。
- C1-C2 对应的过期旧 file slices 可以删除。
- C1/C2 的 commit 元数据不是 cleaner 删除对象，timeline 归档由 archival 控制。
```

**优点：**

- 与提交频率直接相关，便于按增量消费延迟估算。
- 对时间旅行和增量查询窗口最直观。
- 默认策略，生产环境最常见。

**估算方式：**

```text
retained_commits >= 最大回溯时间内的提交数 + 安全余量

示例：
- 每小时 1 次提交，希望回溯 7 天：7 * 24 = 168，建议至少 180+
- 每 10 分钟 1 次提交，希望回溯 1 天：24 * 6 = 144，建议至少 160+
- 流式高频提交不能盲目使用 20-30，因为可能只覆盖几十分钟
```

### 3.2 KEEP_LATEST_FILE_VERSIONS

**策略：** 每个 file group 至少保留最近 N 个 file slices。

**配置：**

```scala
.option("hoodie.clean.policy", "KEEP_LATEST_FILE_VERSIONS")
.option("hoodie.clean.fileversions.retained", "3")
```

**工作原理：**

```text
File Group: fg_001

Slice 1: base/log files at T1   删除候选
Slice 2: base/log files at T2   保留，最近 3 个 file slices 内
Slice 3: base/log files at T3   保留
Slice 4: base/log files at T4   保留，当前最新 slice
```

**优点：**

- file group 级别控制更直接。
- 适合某些更新热点集中、希望每组固定保留版本数的场景。

**缺点：**

- 不同 file group 的提交时间可能差异很大，难以换算成统一时间窗口。
- 对时间旅行和增量查询窗口不如 `KEEP_LATEST_COMMITS` 直观。

### 3.3 KEEP_LATEST_BY_HOURS

**策略：** 保留最近 N 小时内的历史 file slices；早于该时间窗口的旧 file slices 可被清理。

**配置：**

```scala
.option("hoodie.clean.policy", "KEEP_LATEST_BY_HOURS")
.option("hoodie.clean.hours.retained", "24")
```

**工作原理：**

```text
当前时间: 2026-07-01 12:00
配置: hoodie.clean.hours.retained = 24

清理含义：
- 2026-06-30 12:00 之后的历史窗口尽量保留。
- 更早的旧 file slices 可被清理。
- 每个 file group 的最新 file slice 仍要保留，不能为了小时窗口破坏当前快照。
```

**优点：**

- 以时间表达业务需求，比提交数更贴近“保留 N 小时历史”。
- 适合提交频率不均但历史回溯按时间定义的表。

**缺点：**

- 提交频率极低时，历史可用性仍可能和预期不同。
- 与增量消费 checkpoint 的关系需要单独验证。

### 3.4 策略对比

| 策略 | 保留依据 | 适合场景 | 时间旅行/增量窗口 |
|------|---------|---------|------------------|
| `KEEP_LATEST_COMMITS` | 提交次数 | 大多数生产表 | 最容易按提交频率估算 |
| `KEEP_LATEST_FILE_VERSIONS` | 每个 file group 的 file slice 数 | 希望固定保留版本数 | 不同 file group 时间窗口可能不同 |
| `KEEP_LATEST_BY_HOURS` | 小时时间窗口 | 按自然时间定义保留期 | 更贴近时间，但仍需验证低频提交 |

### 4.1 Hudi 1.0.2 主配置

| 参数 | 说明 | 默认值 | 备注 |
|------|------|--------|------|
| `hoodie.clean.automatic` | 是否自动触发 cleaner | `true` | 关闭后必须有外部清理调度 |

### 4.2 高级配置

| 参数 | 说明 | 默认值 | 备注 |
|------|------|--------|------|
| `hoodie.clean.incremental.enabled` | 增量生成 cleaner plan | `true` | 兼容旧名 `hoodie.cleaner.incremental.mode` |
| `hoodie.clean.failed.writes.policy` | 失败写入清理策略 | `EAGER` | 多写入者/OCC 场景应使用 `LAZY` |

| `hoodie.clean.delete.bootstrap.base.file` | 是否删除 bootstrap 原始 base file | `false` | bootstrap 表特殊场景使用 |

### 4.3 生产环境参考配置

```scala
df.write.format("hudi")
  .option("hoodie.table.name", tableName)

  // cleaner 服务
  .option("hoodie.clean.automatic", "true")
  .option("hoodie.clean.async.enabled", "true")

  // 保留策略：按业务回溯窗口和提交频率计算，不要机械套用 20
  .option("hoodie.clean.policy", "KEEP_LATEST_COMMITS")
  .option("hoodie.clean.commits.retained", "180")

  // Hudi 1.0.2 仅支持 NUM_COMMITS 触发
  .option("hoodie.clean.trigger.strategy", "NUM_COMMITS")
  .option("hoodie.clean.trigger.max.commits", "5")

  // 性能调优
  .option("hoodie.clean.parallelism", "200")
  .option("hoodie.clean.incremental.enabled", "true")

  // 单写入者可使用默认 EAGER；多写入者/OCC 必须使用 LAZY
  .option("hoodie.clean.failed.writes.policy", "EAGER")

  .save(basePath)
```

多写入者配置应参考 `09-高级特性-并发写入.md`，使用同一套锁/OCC 配置，并设置：

```scala
.option("hoodie.clean.failed.writes.policy", "LAZY")
```

## 5. 清理触发机制

### 5.1 Hudi 1.0.2：按提交数触发

Hudi 1.0.2 的 `CleaningTriggerStrategy` 只有 `NUM_COMMITS`。因此 cleaner 是否尝试触发，由距离上次 clean 的提交数决定：

```scala
.option("hoodie.clean.trigger.strategy", "NUM_COMMITS")
.option("hoodie.clean.trigger.max.commits", "5")
```

```text
提交序列：C1 -> C2 -> C3 -> C4 -> C5 -> 尝试触发清理 -> C6 -> ...
```

`hoodie.clean.trigger.max.commits=1` 是默认值，不是错误配置。它意味着每次提交后都可能尝试清理；在 inline cleaning + 高频写入下可能增加写入延迟，因此可调大到 5、10 或更高，并配合监控验证。

### 5.2 容易混淆：按小时保留不是按小时触发

`KEEP_LATEST_BY_HOURS` / `hoodie.clean.hours.retained` 控制的是“保留多长历史窗口”，不是“每隔多少小时触发 cleaner”。

Hudi 1.0.2 中不要配置以下不存在的能力：

```scala
// Hudi 1.0.2 不支持
.option("hoodie.clean.trigger.strategy", "TIME_ELAPSED")
.option("hoodie.clean.max.time.hours", "24")
```

### 5.3 手动触发

Spark SQL procedure 示例：

```sql
CALL run_clean(table => 'db.table_name');

CALL run_clean(
  table => 'db.table_name',
  clean_policy => 'KEEP_LATEST_COMMITS',
  retain_commits => 20,
  trigger_strategy => 'NUM_COMMITS',
  trigger_max_commits => 1
);
```

某些 catalog 注册方式可能需要使用带 namespace 的调用形式；如果 `CALL run_clean` 不可用，应检查当前 Spark/Hudi catalog 配置和 Hudi SQL extension 是否启用。

## 6. 清理与其他特性的关系

### 6.1 清理 vs 时间旅行 / 增量查询

```text
Trade-off：存储成本 vs 历史查询窗口

保留更多提交：
+ 支持更长时间的时间旅行和增量消费延迟
- 存储成本更高

保留更少提交：
+ 存储成本更低
- 旧快照和旧 checkpoint 更早失效
```

关键原则：

- `hoodie.clean.commits.retained` 必须覆盖最长时间旅行需求。
- 对增量查询，retention 必须覆盖最大消费延迟；否则旧 checkpoint 对应的数据文件可能已经被清理。
- 长查询运行时间也应纳入考虑，避免查询还在读旧快照时相关文件已被删除。

### 6.2 清理 vs Compaction

| 维度 | Cleaning | Compaction |
|------|----------|-----------|
| 作用 | 删除过期 file slices / 数据文件 | 合并 MOR delta logs，生成新的 base file |
| 目标 | 控制存储和历史窗口 | 优化 MOR 读性能和文件布局 |
| 适用表 | COW 和 MOR | 主要是 MOR |
| 结果 | 物理删除旧文件 | 产生新 file slice，旧 file slices 后续由 cleaner 清理 |
| 并发关系 | 表服务，需关注调度和锁 | 表服务，需关注调度和锁 |

### 6.3 清理 vs Archival

```text
Cleaning：删除旧数据文件，如 parquet / log files
Archival：归档旧 timeline 元数据，如 commit / deltacommit / clean instants
```

示意：

```text
.hoodie/
  20260701100000.commit
  20260701110000.commit
  ...

archival 后：
.hoodie/
  archived/
    commits.archive.1
  20260701100000.commit
  20260701110000.commit
```

常用配置：

```scala
.option("hoodie.clean.commits.retained", "30")
.option("hoodie.keep.min.commits", "35")
.option("hoodie.keep.max.commits", "40")
```

建议关系：

```text
hoodie.clean.commits.retained < hoodie.keep.min.commits < hoodie.keep.max.commits
```

这样 cleaner 的数据文件历史窗口不会比 active timeline 元数据窗口更长，能降低 timeline 先被归档导致排查或消费窗口不一致的风险。

更具体地说，Hudi 历史查询和增量查询不仅需要底层 parquet/log 文件存在，还需要 timeline 元数据解释这些文件属于哪个 commit、哪个 file slice、哪个快照。推荐让 active timeline 覆盖 cleaner 承诺保留的数据窗口：

```text
最新 commit: C100

hoodie.clean.commits.retained = 30
  -> cleaner 尽量保留 C71 ~ C100 回溯所需的数据文件

hoodie.keep.min.commits = 40
  -> archival 后 active timeline 至少保留 C61 ~ C100 的元数据
```

此时大致可以理解为：

```text
C71 ~ C100:
  元数据在 active timeline，数据文件也在 cleaner 保留窗口内
  -> 时间旅行 / 增量查询更可靠

C61 ~ C70:
  元数据可能仍在 active timeline，但旧数据文件不一定还在
  -> 不保证还能 time travel，但通常不影响当前快照查询

C60 以前:
  元数据可能已归档，旧数据文件也可能已清理
  -> 通常不作为活跃回溯窗口
```

因此，`keep.min.commits` 大于 `clean.commits.retained` 的目的不是保证 active timeline 中每个 commit 都能时间旅行，而是保证 **cleaner 仍保留的数据版本，有足够的 active timeline 元数据可以直接解释**。active timeline 中额外多出的较老元数据，即使对应旧数据文件已经被 cleaner 清理，通常也不会让当前快照查询报错；只有当用户尝试回溯到已经超出 cleaner 数据保留窗口的旧 instant 时，才可能因为所需数据文件不存在而失败。

## 7. 监控与故障排查

### 7.1 监控指标

关键指标：

- clean instant 是否持续成功生成。
- 每次清理删除的文件数量和耗时。
- `earliest_commit_to_retain` 是否符合预期。
- 表数据目录和 `.hoodie` 目录大小趋势。
- 时间旅行和增量消费的最大回溯/延迟是否仍在保留窗口内。

查看存储使用：

```bash
# 查看表总大小
hadoop fs -du -h s3://bucket/table_path

# 查看 timeline 大小
hadoop fs -du -h s3://bucket/table_path/.hoodie
```

如果已安装 Hudi CLI，可根据 CLI 版本使用 clean 相关命令查看历史；当前项目更建议通过 Spark SQL procedure 或直接检查 `.hoodie/*.clean` 元数据验证。

### 7.2 常见问题

#### 问题 1：存储空间未释放

可能原因：

- 保留策略过宽，例如 `hoodie.clean.commits.retained` 远大于实际需要。
- 还没有达到 `hoodie.clean.trigger.max.commits` 触发条件。
- cleaner 执行失败或未启用。
- savepoint / 当前快照仍保护相关文件。
- 对象存储账单或控制台统计存在延迟。

检查方式：

```bash
# 查看 clean instant 是否生成
hadoop fs -ls s3://bucket/table_path/.hoodie | grep clean

# 查看目录大小趋势
hadoop fs -du -s -h s3://bucket/table_path
```

调整配置示例：

```scala
.option("hoodie.clean.commits.retained", "30")
.option("hoodie.clean.trigger.max.commits", "5")
```

#### 问题 2：时间旅行或增量查询失败

症状：

- 历史快照查询失败。
- 增量查询从旧 checkpoint 恢复时报文件不存在或 instant 不可用。

常见原因：

- cleaner 保留窗口过短，历史文件已被物理删除。
- archival active timeline 保留过短，旧 instant 已归档，查询方式未正确读取 archived timeline。
- 使用非 Hudi reader 直接读取底层文件，绕过 MVCC 语义。

解决建议：

```scala
.option("hoodie.clean.commits.retained", "180")
.option("hoodie.keep.min.commits", "200")
.option("hoodie.keep.max.commits", "240")
```

如果文件已被物理删除，Hudi cleaner 本身不能自动恢复；只能依赖备份、对象存储版本化、快照、savepoint 保护文件或重新导入数据。

#### 问题 3：清理操作很慢

可能原因：

- 分区或小文件数量过多。
- 清理并行度不足。
- 未开启增量 cleaner plan。
- 元数据表或文件 listing 性能异常。

调优示例：

```scala
.option("hoodie.clean.parallelism", "500")
.option("hoodie.clean.incremental.enabled", "true")
```

同时应排查是否存在小文件问题；cleaner 不是小文件治理工具，小文件应通过写入参数、clustering 或 compaction 等方式治理。

## 8. 最佳实践

### 8.1 保留策略选择

推荐按业务窗口反推配置，而不是机械使用固定数值：

```text
hoodie.clean.commits.retained >= 最大回溯时间内的提交数 + 安全余量
```

示例：

```scala
// 每小时提交一次，需要 7 天时间旅行/增量恢复窗口
.option("hoodie.clean.policy", "KEEP_LATEST_COMMITS")
.option("hoodie.clean.commits.retained", "180")

// 每 10 分钟提交一次，需要 1 天窗口
.option("hoodie.clean.commits.retained", "160")
```

低频或不均匀提交可以考虑 `KEEP_LATEST_BY_HOURS`，但仍要验证时间旅行和增量查询是否满足预期。

### 8.2 执行策略

推荐做法：

1. 长期运行的 streaming job 或持续写入作业适合自动异步清理。
2. 短生命周期 batch job 如果需要保证本次作业完成清理，优先使用 inline cleaning。
3. 手动/外部调度适合维护窗口严格的生产环境，但必须有明确调度和告警。
4. `hoodie.clean.trigger.max.commits` 可从默认 `1` 开始，若 inline 写入延迟明显，再调大并观察存储增长。
5. 多写入者/OCC 场景必须使用 `hoodie.clean.failed.writes.policy=LAZY`，并配置一致的锁。

示例：

```scala
.option("hoodie.clean.automatic", "true")
.option("hoodie.clean.async.enabled", "true")
.option("hoodie.clean.trigger.max.commits", "5")
```

### 8.3 避免的陷阱

常见错误：

1. **只保留 1-2 次提交却要求长时间回溯**

   ```scala
   .option("hoodie.clean.commits.retained", "2")
   ```

   这会让时间旅行和增量消费窗口非常短。

2. **禁用自动清理但没有外部调度**

   ```scala
   .option("hoodie.clean.automatic", "false")
   ```

   关闭 automatic 本身不是错误；没有替代的定期 clean 才是问题。

3. **把保留小时数当成触发频率**

   ```scala
   .option("hoodie.clean.policy", "KEEP_LATEST_BY_HOURS")
   .option("hoodie.clean.hours.retained", "168")
   ```

   这表示保留 168 小时历史，不表示每 168 小时清理一次。

4. **忽略 cleaner 与 archival 的关系**

   ```scala
   // 不推荐：cleaner 窗口大于 active timeline 最小保留
   .option("hoodie.clean.commits.retained", "100")
   .option("hoodie.keep.min.commits", "20")
   ```

   建议保持 `clean.commits.retained < keep.min.commits < keep.max.commits`。

## 9. 实际应用场景

### 场景 1：日志数据表

需求：

- 每小时写入一次。
- 需要保留 7 天历史查询窗口。
- 成本敏感。

配置：

```scala
.option("hoodie.clean.policy", "KEEP_LATEST_COMMITS")
.option("hoodie.clean.commits.retained", "180")
.option("hoodie.keep.min.commits", "200")
.option("hoodie.keep.max.commits", "240")
.option("hoodie.clean.async.enabled", "true")
.option("hoodie.clean.trigger.max.commits", "12")
```

如果提交频率非常不稳定，也可以评估：

```scala
.option("hoodie.clean.policy", "KEEP_LATEST_BY_HOURS")
.option("hoodie.clean.hours.retained", "168")
```

### 场景 2：交易数据表

需求：

- 高频更新。
- 增量消费可能延迟 30 天。
- 合规和审计要求高。

配置思路：

```scala
// 假设每小时约 1 次提交；如果更高频，应按实际提交数放大
.option("hoodie.clean.policy", "KEEP_LATEST_COMMITS")
.option("hoodie.clean.commits.retained", "760")
.option("hoodie.keep.min.commits", "800")
.option("hoodie.keep.max.commits", "900")
.option("hoodie.clean.async.enabled", "true")
.option("hoodie.clean.trigger.max.commits", "10")
```

注意：cleaner 只提供 Hudi 表内历史窗口，不等同于长期审计归档。严格审计通常还需要外部快照、备份、归档表或对象存储版本化。

### 场景 3：维度表

需求：

- 低频更新（每天一次）。
- 希望保留近一年历史。
- 存储成本可接受。

配置：

```scala
.option("hoodie.clean.policy", "KEEP_LATEST_COMMITS")
.option("hoodie.clean.commits.retained", "365")
.option("hoodie.keep.min.commits", "400")
.option("hoodie.keep.max.commits", "450")
.option("hoodie.clean.async.enabled", "true")
.option("hoodie.clean.trigger.max.commits", "30")
```

如果需求是“永久保留所有历史版本”，不要依赖 cleaner retention 表达；应考虑禁用清理并接受成本、使用 savepoint 保护关键版本，或采用外部备份/审计归档方案。

### 10.1 存储成本分析

示例场景：

```text
当前表大小：1TB
更新频率：每天一次
每天产生旧版本数据：100GB

不清理或 cleaner 失败：

保留 10 天历史：
Day 30: 1TB + 10 * 100GB = 2TB
```

- 对象存储版本化、生命周期策略和删除计费延迟。

## 11. 常见问题 (FAQ)

### Q1：清理会影响正在运行的查询吗？

**A：** 通常 Hudi reader 通过 MVCC 能安全读取其快照，但这依赖 cleaner retention 覆盖查询运行时间和消费延迟。不要把 `hoodie.clean.commits.retained` 配得过小；超长查询、旧 checkpoint 增量消费、非 Hudi reader 直接读底层文件，都可能受到已清理文件影响。

### Q2：清理失败了怎么办？

**A：** 先确认失败原因，再重跑或等待下次触发：

```bash
# 查看 clean instant
hadoop fs -ls s3://bucket/table_path/.hoodie | grep clean

# 查看存储和 timeline 是否持续增长
hadoop fs -du -s -h s3://bucket/table_path
hadoop fs -du -s -h s3://bucket/table_path/.hoodie
```

常见原因是权限、对象存储临时错误、锁冲突、并行度不足或 metadata/listing 异常。

### Q3：如何估算应该保留多少提交？

**A：** 用最大回溯窗口和提交频率计算：

```text
retained_commits = 回溯天数 * 每天提交次数 + 安全余量

示例：
- 回溯 7 天，每小时提交 1 次：7 * 24 = 168，建议 180+
- 回溯 3 天，每 10 分钟提交 1 次：3 * 24 * 6 = 432，建议 450+
```

同时设置：

```text
hoodie.clean.commits.retained < hoodie.keep.min.commits < hoodie.keep.max.commits
```

### Q4：清理能恢复吗？

**A：** Cleaner 是物理删除数据文件，Hudi 不会自动恢复已删除文件。可恢复性取决于外部保护：对象存储版本化、备份、快照、savepoint 或重新导入原始数据。生产环境应在启用激进清理前验证恢复方案。

### Q5：Archival 和 Cleaning 的区别？

**A：**

```text
Cleaning：删除旧数据文件，如 .parquet / .log
Archival：归档旧 timeline 元数据，如 .commit / .deltacommit / .clean
```

两者互补：cleaner 控制数据文件增长，archival 控制 active timeline 元数据增长。

## 13. 总结

清理是 Hudi 表维护的关键操作：

```scala
.option("hoodie.clean.automatic", "true")
.option("hoodie.clean.async.enabled", "true")
.option("hoodie.clean.policy", "KEEP_LATEST_COMMITS")
.option("hoodie.clean.commits.retained", "按提交频率计算")
.option("hoodie.clean.trigger.strategy", "NUM_COMMITS")
```

核心原则：

- Cleaner 删除数据文件，不删除 commit timeline；timeline 由 archival 管理。
- Hudi 1.0.2 只有 `NUM_COMMITS` 触发策略，没有按时间触发 cleaner。
- `KEEP_LATEST_BY_HOURS` 是保留策略，不是触发策略。
- 保留窗口要覆盖时间旅行、增量消费延迟和长查询运行时间。
- 多写入者场景必须配合 OCC/锁，并使用 `hoodie.clean.failed.writes.policy=LAZY`。
- 如果要永久审计或长期历史，使用备份、归档、savepoint 或外部数据保留方案，不要只依赖 cleaner retention。
