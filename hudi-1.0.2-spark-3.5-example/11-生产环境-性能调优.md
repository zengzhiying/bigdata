# Hudi 生产环境：性能调优指南（Spark 3.5 + Hudi 1.0.2）

## 概述

Hudi 性能调优不是简单复制一组“万能参数”，而是围绕数据规模、写入模式、查询模式、存储系统和 SLA 做持续验证。本文档面向 Spark 3.5 + Hudi 1.0.2 示例项目，重点说明生产环境中常见的写入、查询、存储和表服务调优方法，并补充每类配置背后的原因、适用场景和风险。

> 重要原则：先建立基准，再改配置；每次只改少量参数，并通过 Spark UI、Hudi Timeline、对象存储指标和查询执行计划验证效果。

---

## 1. 调优方法论

### 1.1 调优前先确认上下文

生产调优前建议先记录以下信息，否则很容易把参数调成“看起来合理但实际无效”：

| 类别 | 需要确认的问题 | 影响的配置 |
|------|----------------|------------|
| 数据规模 | 每批/每天写入多少 GB/TB？平均记录大小是多少？ | 文件大小、写入并行度、bulk insert 并行度 |
| 写入模式 | insert、bulk_insert、upsert、delete 哪种为主？更新比例多高？ | 索引类型、precombine、compaction |
| 分区模式 | 查询是否经常带分区过滤？每个分区数据量多大？ | 分区字段、分区粒度、clustering |
| 查询模式 | 点查、范围查、聚合、join、全表扫描分别占比多少？ | metadata index、column stats、clustering key |
| 表类型 | COW 还是 MOR？是否要求读取最新数据？ | compaction、read optimized、snapshot |
| 存储系统 | HDFS、S3、OSS、COS、ABFS？list/rename/写入延迟如何？ | metadata table、S3A 参数、marker/lock |
| SLA | 写入延迟、查询延迟、保留周期、成本目标是多少？ | clean、archive、资源、表服务频率 |

### 1.2 推荐调优流程

```text
1. 建立基准
   - 固定一组代表性数据和查询
   - 记录写入吞吐、commit 耗时、文件数量、查询耗时
   - 保留 Spark UI / Event Log / Hudi commit metadata

2. 定位瓶颈
   - 写入慢：index tagging、shuffle、写文件、commit、table service 哪一步慢？
   - 查询慢：分区裁剪、文件裁剪、列裁剪、small files、MOR log merge 哪一步慢？
   - 存储膨胀：clean 未执行、MOR log 堆积、compaction backlog、archive 保留过多？

3. 针对性优化
   - 先调结构：分区、主键、索引、表类型、文件布局
   - 再调参数：并行度、文件大小、metadata index、table services
   - 最后调资源：executor、内存、网络、对象存储连接池

4. 验证和回滚
   - 对比基准，不只看单次最快值，要看 p50/p95/p99
   - 观察副作用：小文件、写放大、读放大、元数据维护成本
   - 参数变更要可回滚，生产建议灰度表或灰度分区验证
```

### 1.3 KPI 应作为 SLA 示例而不是通用目标

以下数值只能作为示例。真实目标要根据集群规模、存储系统、表大小、并发度和业务 SLA 压测确定。

| 指标类别 | 观察指标 | 示例目标/判断方式 |
|---------|----------|------------------|
| 写入性能 | 吞吐量、commit 耗时、index lookup 耗时 | 与基准相比稳定提升，不牺牲文件布局 |
| 查询性能 | 查询 p50/p95/p99、扫描文件数、扫描字节数 | 查询计划命中分区裁剪、谓词下推、data skipping |
| 存储效率 | 文件大小分布、小文件数量、log 文件数量 | 大多数 base file 接近目标文件大小 |
| 表服务 | compaction/clustering/clean backlog | backlog 可控，不影响写入和查询 SLA |
| 稳定性 | 失败率、重试次数、锁等待、对象存储 4xx/5xx | 长期趋势稳定，无持续堆积 |

## 2. 写入路径与瓶颈拆解

### 2.1 Hudi 写入大致经过哪些阶段

理解写入路径有助于从 Spark UI 定位慢在哪里：

```text
输入 DataFrame
  -> record key / partition path / precombine 处理
  -> 去重或预合并（取决于操作类型和输入数据）
  -> 索引标记 index tagging（判断是 insert 还是 update）
  -> shuffle / bin-packing / small file handling
  -> 写 base file 或 log file
  -> commit timeline 元数据
  -> 触发或调度 clean / compaction / clustering 等表服务
```

常见瓶颈与线索：

| 瓶颈 | Spark UI / Timeline 表现 | 常见原因 |
|------|--------------------------|----------|
| index tagging 慢 | 某个 lookup stage 时间长 | 索引类型不合适、跨分区更新、文件过多、metadata index 未启用 |
| shuffle 慢 | shuffle read/write 大、task 倾斜 | 并行度不合适、分区字段倾斜、upsert 更新集中 |
| 写文件慢 | task 写出耗时高、对象存储请求慢 | 目标文件太大/太小、对象存储连接池不足、executor I/O 弱 |
| commit 慢 | commit metadata 或 listing 时间长 | 文件数量过多、元数据表未启用、对象存储 list 慢 |
| 表服务拖慢 | 每次写入后额外 stage 很长 | inline compaction/clustering/clean 频率过高 |

## 3. 写入性能优化

### 3.1 并行度不是固定公式

不要简单理解为“并行度 = executor 数 * core 数”。更实用的做法是结合以下因素估算：

```text
初始并行度参考 = max(
  可用总 core 数的 2~4 倍,
  预计写出数据大小 / 目标文件大小,
  活跃分区数
)
```

其中应使用预计的 Hudi 写出大小，不要直接使用 gzip 等高压缩比源文件的物理大小，否则可能明显低估任务数。可先根据样本数据的记录数、平均序列化大小和目标压缩编码估算，再用首批 commit 的实际写出量修正。

然后通过 Spark UI 修正：

- task 数明显少于总 core：资源未打满，可增加并行度。
- task 很多但每个 task 只处理少量数据：调度开销和小文件风险增加，应降低并行度。
- 少数 task 远慢于其他 task：优先处理数据倾斜，而不是盲目加并行度。
- 输出文件远小于目标文件大小：并行度可能过高，或分区过细，或写入批次太小。

#### 3.1.1 Insert / Upsert 并行度

```scala
.option("hoodie.insert.shuffle.parallelism", "200")
.option("hoodie.upsert.shuffle.parallelism", "200")
```

建议：

- 小数据量或本地学习环境可以从 `2~20` 开始。
- 中等生产作业可以从总 core 的 `2~4` 倍开始压测。
- 大批量写入不要只增加并行度，还要观察文件大小和对象存储请求量。
- upsert 更新比例高时，索引查找和 shuffle 成本通常比 insert 更敏感。

#### 3.1.2 Bulk Insert 并行度

```scala
.option("hoodie.bulkinsert.shuffle.parallelism", "400")
.option("hoodie.datasource.write.operation", "bulk_insert")
```

Bulk insert 常用于历史初始化，目标是高吞吐和较好的初始文件布局。并行度可以略高于常规 upsert，但要避免产生过多小文件。初始化后如果主要是 upsert，应继续验证后续增量写入的文件大小和索引性能。

#### 3.1.3 不同写入操作的选择

Hudi 写入操作由用户通过 `hoodie.datasource.write.operation` 显式指定。`bulk_insert` 不是“数据量大的普通写入”的别名，而是一种明确的写入路径；Hudi 会根据 operation 选择不同的处理逻辑和调优参数。

| Operation | 主要语义 | 是否适合已有 key 更新 | 典型场景 | 重点调优参数 |
|-----------|----------|----------------------|----------|--------------|
| `bulk_insert` | 高吞吐批量导入新数据 | 不适合 | 历史初始化、写入新表、确认不与目标表已有 key 冲突 | `hoodie.bulkinsert.shuffle.parallelism`、`hoodie.bulkinsert.sort.mode` |
| `insert` | 插入新数据 | 不适合 | 持续新增、业务保证不会更新旧 key | `hoodie.insert.shuffle.parallelism`、small file handling |
| `upsert` | 有则更新、无则插入 | 适合 | CDC、订单状态更新、维表变化 | 索引类型、`hoodie.upsert.shuffle.parallelism`、small file handling |
| `delete` | 删除已有 key | 适合 | 数据删除、隐私合规删除 | 索引类型、删除并行度、clean 保留策略 |
| `insert_overwrite` | 覆盖目标分区 | 不是按 key 更新 | 重刷某天/某小时分区 | 分区范围、输出文件大小 |
| `insert_overwrite_table` | 覆盖整张表 | 不是按 key 更新 | 全表重建 | 全量导入资源、文件布局 |

选择建议：

```text
目标表为空，正在做历史初始化？
  -> bulk_insert

目标表已有数据，但这批数据保证全是新 key？
  -> insert；如果是很大的离线批次，也可以评估 bulk_insert

这批数据可能和目标表已有 key 重复，业务语义是保留最新版本？
  -> upsert

只想重刷某些分区，不关心分区内旧 key 如何逐条合并？
  -> insert_overwrite
```

关于重复数据要特别注意：

- `bulk_insert` 优先保证导入吞吐，不负责像 `upsert` 那样通过索引查找并更新目标表已有 record key。
- `hoodie.datasource.write.precombine.field` 只定义同 key 记录的新旧比较字段，不代表 `insert` / `bulk_insert` 默认会对输入去重。Hudi 1.0.2 中 `hoodie.combine.before.insert` 默认为 `false`。
- 如果本批输入内部可能有重复 key，最稳妥的做法是写入前按 record key 去重；也可显式设置 `hoodie.combine.before.insert=true`，但必须验证 precombine/record merger 对相同 key 的选择结果，并评估额外 shuffle 或合并成本。
- 如果目标表中可能已有相同 key，应使用 `upsert`，不要指望 `bulk_insert` 自动维护全表唯一性。

### 3.2 文件大小优化

#### 3.2.1 目标文件大小

```scala
.option("hoodie.parquet.max.file.size", "134217728")  // 128 MB
```

建议范围通常是 `128MB~512MB`，不是越大越好：

- 文件太小：查询 task 多、metadata/listing 成本高、commit 元数据膨胀。
- 文件太大：COW 更新重写代价高，MOR compaction 单个 file group 压力大。
- HDFS 可以考虑和 block size 对齐；对象存储更关注请求数、扫描并发和查询引擎 split 行为。

#### 3.2.2 Small File Handling

```scala
.option("hoodie.parquet.small.file.limit", "104857600")  // 100 MB
```

含义：upsert/insert 时，Hudi 会尽量把新记录填充进小于该阈值的现有小文件，减少新文件创建。注意：

- 这个配置不负责执行 compaction，也不是 clustering 的替代品。
- 设置为 `0` 或负数会关闭小文件填充，通常只适合特殊高吞吐 append 场景。
- 如果每个分区每批只有很少数据，单靠 small file handling 很难避免小文件，需要调整批大小、分区粒度或定期 clustering。

#### 3.2.3 Bulk Insert 排序模式

```scala
.option("hoodie.bulkinsert.sort.mode", "PARTITION_SORT")
```

这个参数只对 `bulk_insert` 写入路径有意义。它控制的是本次输入记录在写出前如何排序或重分布，不会改变业务数据本身，也不是对已经存在的 Hudi 文件重新排序。

在 Hudi 1.0.2 的 Spark Row 写入路径中，常见模式含义如下：

| 模式 | 是否引入 shuffle | 做什么 | 适用场景 |
|------|------------------|--------|----------|
| `NONE` | 否 | 不主动排序，基本按输入分布写 | 追求最快导入、后续会马上 clustering |
| `PARTITION_SORT` | 通常否 | `coalesce(parallelism)` 后，在每个 Spark partition 内按 `_hoodie_partition_path`、`_hoodie_record_key` 排序 | 想降低 task 内目标分区切换成本，又不想引入按分区 shuffle |
| `PARTITION_PATH_REPARTITION` | 是 | 按 `_hoodie_partition_path` 重新分区，但不保证分区内排序 | 希望同一 Hudi 分区的数据更集中写入 |
| `PARTITION_PATH_REPARTITION_AND_SORT` | 是 | 先按 `_hoodie_partition_path` 重分区，再在分区内按 partition path 排序 | 文件布局优于单纯 repartition，但成本更高 |
| `GLOBAL_SORT` | 是 | 全局按 `_hoodie_partition_path`、`_hoodie_record_key` 排序 | 初始化窗口充足、追求较好的全局文件布局 |

`PARTITION_SORT` 的关键点：

- 它是在 Spark 分区内部排序，不负责把全表范围内相同 Hudi 分区路径的数据 shuffle 到同一个 Spark partition。
- Spark Row 路径使用 `coalesce(parallelism)`，通常只能减少上游 partition，不能把较少的 partition 增加到 `hoodie.bulkinsert.shuffle.parallelism` 指定的数量。例如上游只有 50 个 partition 时，把该参数设为 400 通常不会得到 400 个写任务。
- 它能让单个 task 内相同目标 Hudi 分区的数据尽量连续，减少写入过程中频繁切换目标分区和写句柄的开销。
- 如果输入数据本身分布很散，同一个 Hudi 分区仍可能被多个 Spark task 同时写入。
- 如果目标是让相同 Hudi 分区的数据尽量集中到更少 task，应评估 `PARTITION_PATH_REPARTITION` 或 `PARTITION_PATH_REPARTITION_AND_SORT`，但这会引入 shuffle。
- 如果目标是增加实际写入并发度，可在进入 Hudi 前对 DataFrame 显式 `repartition`，或选择会产生 shuffle 的 repartition sort mode，并同时监控 shuffle 成本和小文件数量。

示例：表按 `dt` 分区、按 `order_id` 作为 record key。

```scala
df.write.format("hudi")
  .option("hoodie.datasource.write.operation", "bulk_insert")
  .option("hoodie.datasource.write.recordkey.field", "order_id")
  .option("hoodie.datasource.write.partitionpath.field", "dt")
  .option("hoodie.bulkinsert.sort.mode", "PARTITION_SORT")
  .save(basePath)
```

这可以理解为：在每个 Spark task 内，按 `dt` 生成的 Hudi partition path 排序；相同 partition path 内再按 `order_id` 排序。但它不保证 `dt=2026-07-01` 的所有记录都由同一个 task 写入。

实践建议：

- 小到中等规模初始化：优先从 `PARTITION_SORT` 开始，成本较低。
- 分区非常多且输入随机分散：评估 `PARTITION_PATH_REPARTITION_AND_SORT`，观察 shuffle 成本和小文件改善是否值得。
- 导入窗口充足且希望初始文件布局更好：评估 `GLOBAL_SORT`。
- 如果导入后马上执行 clustering：可以使用 `NONE` 或 `PARTITION_SORT`，把布局优化交给 clustering。

### 3.3 索引选择不要一概推荐 BLOOM

索引影响 upsert/delete 的 index tagging 成本。生产环境应按表特征选择，而不是固定使用 `BLOOM`。

| 索引类型 | 适用场景 | 主要代价/风险 |
|---------|----------|---------------|
| `BLOOM` | 分区内主键更新，文件数可控，需要减少无关文件扫描 | Bloom filter 维护和读取有成本，随机 key range pruning 效果弱 |
| `SIMPLE` | 分区内更新，文件数量适中，想避免 Bloom filter 误判和维护成本 | 需要扫描受影响分区的 base files，分区大时成本高 |
| `GLOBAL_BLOOM` / `GLOBAL_SIMPLE` | record key 可能跨分区移动，需要全表唯一性 | 跨分区查找成本高，大表要谨慎 |
| `RECORD_INDEX` | 超大表、全局 key 查找、希望用 metadata table 加速定位 | 需要额外 metadata index 存储和维护成本 |
| `BUCKET` | 高吞吐写入、固定 key 到 bucket 的布局优化 | bucket 数设计困难，扩缩容和倾斜需要提前规划 |

Bloom 常用配置示例：

```scala
.option("hoodie.index.type", "BLOOM")
.option("hoodie.bloom.index.parallelism", "200")
.option("hoodie.bloom.index.prune.by.ranges", "true")
.option("hoodie.bloom.index.use.caching", "true")

// 如果希望 Bloom 写路径使用 metadata table 中的 Bloom Filter 信息，
// 需要同时构建对应 metadata index
.option("hoodie.metadata.enable", "true")
.option("hoodie.metadata.index.bloom.filter.enable", "true")
.option("hoodie.metadata.index.bloom.filter.column.list", "order_id")
.option("hoodie.bloom.index.use.metadata", "true")
```

Bloom FPP 不建议盲目固定：

```scala
.option("hoodie.index.bloom.fpp", "0.000001")
// 如需调优，也要同时关注 hoodie.index.bloom.num_entries、单文件记录数和误判率
```

说明：

- `hoodie.bloom.index.prune.by.ranges=true` 对单调递增或有范围局部性的 record key 更有效；完全随机 key 可能收益有限甚至增加开销。
- `hoodie.bloom.index.use.metadata=true` 只会使用已经可用的 metadata indexes，不会自动创建 `bloom_filters` 分区。`hoodie.metadata.enable=true` 也不等于所有 metadata index 都已启用。
- Hudi 1.0.2 中 `hoodie.metadata.enable` 默认为 `true`；将它显式写出有助于表达生产意图，但若当前本就是默认值，单独增加该配置不会带来额外性能收益。
- FPP 越低，Bloom filter 通常越大，存储和读取成本也会上升。
- 如果文件数量很多，先解决小文件和文件布局问题，单独调 Bloom 参数收益有限。

### 3.4 写入必填配置要明确

生产模板中必须显式配置主键、预合并字段和分区字段，否则 upsert、去重和查询裁剪都可能不符合预期。

```scala
df.write.format("hudi")
  .option("hoodie.table.name", tableName)
  .option("hoodie.datasource.write.table.type", "COPY_ON_WRITE")
  .option("hoodie.datasource.write.operation", "upsert")
  .option("hoodie.datasource.write.recordkey.field", "order_id")
  .option("hoodie.datasource.write.precombine.field", "updated_at")
  .option("hoodie.datasource.write.partitionpath.field", "dt")
  .option("hoodie.datasource.write.hive_style_partitioning", "true")
  .mode("append")
  .save(basePath)
```

注意：

- `recordkey.field` 决定同一条业务记录如何识别，不能随意修改。
- `precombine.field` 应选择同一 key 多条记录中能判断新旧顺序的字段，例如更新时间或版本号。
- 分区字段应服务查询和写入，不建议使用高基数字段如用户 ID 直接分区。

### 3.5 Spark 写入资源配置

```bash
spark-submit \
  --conf spark.serializer=org.apache.spark.serializer.KryoSerializer \
  --conf spark.sql.shuffle.partitions=200 \
  --conf spark.default.parallelism=200 \
  --executor-memory 8G \
  --executor-cores 4 \
  --executor-instances 10 \
  --conf spark.executor.memoryOverhead=2G
```

调优建议：

- `spark.sql.shuffle.partitions` 应与数据量和 core 数一起压测，不要固定 200。
- `spark.memory.fraction`、`spark.memory.storageFraction` 通常先使用 Spark 默认值，只有在明确 GC、spill 或缓存问题时再调整。
- `executor-cores` 常用 `3~5`，太大容易造成单 executor 内存和 GC 压力，太小会增加 executor 管理开销。
- 对象存储写入慢时，增加 executor 不一定有效，还要看连接池、请求限流和文件数量。

## 4. 查询性能优化

### 4.1 元数据表与 Metadata Index

Hudi metadata table 尤其适合对象存储和大分区表。Hudi 1.0.2 中 `hoodie.metadata.enable` 默认为 `true`，生产上仍应根据表的实际状态确认它没有被关闭。但不要把所有 metadata index 都无脑打开，因为它们会增加写入维护成本。

```scala
.option("hoodie.metadata.enable", "true")
```

常见 metadata index：

| 能力 | 配置 | 主要收益 | 成本/注意事项 |
|------|------|----------|---------------|
| 文件列表 | `hoodie.metadata.enable=true` | 减少文件 listing，尤其对象存储明显 | 需要维护 metadata table |
| 列统计 | `hoodie.metadata.index.column.stats.enable=true` | 范围过滤、data skipping | 维护列统计有写入成本；优先选高频过滤列 |
| Bloom filter | `hoodie.metadata.index.bloom.filter.enable=true` | 加速受支持的 Bloom 候选文件判断/写路径 lookup | 增加 metadata 分区维护成本；不代表普通 SQL 一定使用 |
| Record index | `hoodie.metadata.record.index.enable=true` | 全局 record key 定位 | 存储和初始化成本较高 |

列统计示例：

```scala
.option("hoodie.metadata.index.column.stats.enable", "true")
.option("hoodie.metadata.index.column.stats.column.list", "order_date,amount,user_id")
```

Bloom metadata index 示例：

```scala
.option("hoodie.metadata.index.bloom.filter.enable", "true")
.option("hoodie.metadata.index.bloom.filter.column.list", "order_id,user_id")
```

建议：

- 老表开启 metadata index 前，先在测试环境验证初始化、回填和查询收益。
- 宽表不要默认索引所有列，优先选择经常出现在 `where` 条件中的列。
- 如果 metadata table 出现不一致，应优先使用 Hudi 提供的校验/修复流程，不要手动删除数据文件。

### 4.2 分区裁剪优化

分区设计没有固定的“100~1000 个分区”标准，应看每个活跃分区的数据量、查询过滤条件和写入频率。

```scala
.option("hoodie.datasource.write.partitionpath.field", "dt")
.option("hoodie.datasource.write.hive_style_partitioning", "true")
```

分区粒度建议：

| 粒度 | 适合场景 | 风险 |
|------|----------|------|
| 日分区 | 多数离线/准实时表，查询经常按日期过滤 | 单日数据过大时单分区文件多 |
| 小时分区 | 单日数据很大，查询经常限定小时 | 小时数据少时会产生小文件 |
| 多级分区 `dt/hour` | 时间过滤明显且数据规模大 | 分区目录更多，写入分散 |
| 不分区 | 小表、维表、查询经常全表扫描 | 大表无法利用分区裁剪 |

反例：

- 按 `user_id`、`order_id` 这类高基数字段分区，容易产生海量小分区。
- 分钟级分区但每分钟数据很少，会制造小文件和过多目录。
- 查询从不带分区条件时，复杂分区结构收益有限。

### 4.3 Clustering 文件布局优化

Clustering 用于重写文件布局、合并小文件、按查询字段排序，通常能改善范围过滤、压缩率和基于列统计的 data skipping。单纯按 join key 排序通常不会让 Spark/Trino 将表识别为共分区布局，也不会直接消除 join shuffle。

调度配置示例：

```scala
.option("hoodie.clustering.inline", "false")
.option("hoodie.clustering.schedule.inline", "true")
.option("hoodie.clustering.inline.max.commits", "5")
.option("hoodie.clustering.plan.strategy.sort.columns", "event_time,user_id")
.option("hoodie.clustering.plan.strategy.target.file.max.bytes", "134217728")
```

关键说明：

- `hoodie.clustering.schedule.inline=true` 只是让写入任务尝试生成 clustering plan。
- `hoodie.clustering.inline=false` 时，普通短生命周期 batch 作业结束后不会继续执行 clustering。
- 需要长期运行的 async clustering 服务，或定时提交独立 clustering 作业执行 pending plan。
- 频繁 clustering 会与 upsert/delete 冲突并消耗大量资源，应结合写入频率和查询收益设置周期。

Clustering key 选择建议：

- 优先选择高频过滤或排序字段，例如 `event_time`、`user_id`。
- 只有当 join 字段同时常用于过滤/data skipping，或与 bucket、共定位布局等设计结合时，才应把它作为 clustering key 的优先候选。
- 不要选择几乎不参与查询的字段。
- 如果查询主要按时间范围过滤，优先把时间字段放前面。
- Clustering 不是索引，不能替代分区裁剪和 metadata column stats。

### 4.4 Spark SQL 查询优化

```scala
spark.conf.set("spark.sql.files.maxPartitionBytes", "134217728")
spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.coalescePartitions.enabled", "true")
spark.conf.set("spark.sql.parquet.filterPushdown", "true")
spark.conf.set("spark.sql.parquet.mergeSchema", "false")
```

说明：

- `spark.sql.files.maxPartitionBytes` 影响读文件 split 大小，过大并发不足，过小 task 过多。
- AQE 通常建议启用，但要结合 Spark 版本和复杂 SQL 验证。
- `mergeSchema=false` 可以避免读 Parquet 时做昂贵 schema 合并；生产建议通过 Hudi schema evolution 管控 schema。
- 查询性能问题优先看执行计划是否命中分区过滤、列裁剪、谓词下推和 metadata data skipping。

### 4.5 Trino / Presto 查询注意事项

Trino Hudi connector 的配置项与版本强相关，不建议把不确定的 Hive/Spark 配置写入 Hudi 文档中当作通用参数。常见 Hudi connector 配置示例：

```properties
hudi.split-generator-parallelism=4
hudi.size-based-split-weights-enabled=true
```

建议补充说明：

- 按实际 Trino 版本核对 Hudi connector 支持的配置项。
- 确认查询的是 COW、MOR snapshot 还是 read optimized 语义。
- 分区同步到 Hive Metastore/Glue 后，要验证 Trino 是否能正确裁剪分区。
- Trino 查询慢时看 split 数、扫描字节数、文件数量和 worker 数据倾斜。

### 4.6 查询类型选择

```scala
// Snapshot Query：查询最新快照，COW/MOR 都支持
val snapshotDf = spark.read.format("hudi").load(basePath)

// Read Optimized Query：MOR 表只读 base file，通常更快，但可能看不到最新 log 中的数据
val roDf = spark.read.format("hudi")
  .option("hoodie.datasource.query.type", "read_optimized")
  .load(basePath)

// Incremental Query：默认返回增量范围内每个 key 的最新状态
val incDf = spark.read.format("hudi")
  .option("hoodie.datasource.query.type", "incremental")
  .option("hoodie.datasource.read.begin.instanttime", beginInstant)
  .load(basePath)
```

选择建议：

- 实时看最新数据：使用 snapshot，但 MOR 表需要合并 log，查询成本更高。
- 报表允许轻微延迟：MOR 表可使用 read optimized，并通过 compaction 控制延迟。
- 下游增量 ETL：可使用 incremental query，同时确保 cleaner 保留周期覆盖增量消费延迟。默认 `latest_state` 语义返回增量范围内每个 key 的最新状态，不等于完整的 insert/update/delete 事件流。
- 下游需要完整 CDC 明细：写入侧要启用并验证 Hudi CDC 能力，读取侧使用 `hoodie.datasource.query.incremental.format=cdc`；还要验证删除事件、起止 instant 边界和下游幂等。

## 5. 存储与表服务优化

### 5.1 压缩编码

```scala
.option("hoodie.parquet.compression.codec", "snappy")
.option("hoodie.parquet.block.size", "134217728")
.option("hoodie.parquet.page.size", "1048576")
```

编码选择建议：

| Codec | 特点 | 适用场景 |
|-------|------|----------|
| `snappy` | CPU 成本低，读写快，压缩比中等 | 默认生产选择，低延迟写入和交互查询 |
| `zstd` | 压缩比更好，CPU 成本高于 snappy | 存储成本敏感、查询引擎支持良好时评估 |
| `gzip` | 压缩比高但 CPU 成本较高 | 冷数据、低频读写场景 |
| `lz4` | 速度快，压缩比一般 | CPU 极敏感场景，需要压测验证 |

压缩比与字段类型、数据重复度、排序方式强相关，不能固定承诺 `3~5x`。

### 5.2 Compaction 优化（仅 MOR 表）

MOR 表写入更新时会产生 log file，snapshot query 需要合并 base file 和 log file；compaction 会把 log 合并回新的 base file。

#### 5.2.1 Inline Compaction

```scala
.option("hoodie.compact.inline", "true")
.option("hoodie.compact.inline.max.delta.commits", "5")
```

特点：

- 写入任务负责调度并执行 compaction。
- 运维简单，但会增加写入延迟。
- 适合低频写入、数据量较小或 demo 环境。

#### 5.2.2 Inline Schedule + Async Execute

```scala
.option("hoodie.compact.inline", "false")
.option("hoodie.compact.schedule.inline", "true")
.option("hoodie.compact.inline.max.delta.commits", "5")
```

关键理解：

- 写入任务只会在满足条件时生成 compaction plan。
- 如果是普通 batch 作业，Spark application 结束后不会继续执行 compaction。
- 生产需要额外提交独立 compaction 作业，或在长期运行的 streaming 作业中启用异步执行。

独立 compaction 作业示意：

```bash
spark-submit \
  --class org.apache.hudi.utilities.HoodieCompactor \
  --conf spark.serializer=org.apache.spark.serializer.KryoSerializer \
  /path/to/hudi-utilities-bundle.jar \
  --base-path s3://bucket/table_path \
  --table-name table_name \
  --parallelism 200
```

#### 5.2.3 Compaction 策略

基于 log 总大小选择 file group：

```scala
.option("hoodie.compaction.strategy",
  "org.apache.hudi.table.action.compact.strategy.LogFileSizeBasedCompactionStrategy")
.option("hoodie.compaction.logfile.size.threshold", "1073741824")  // 1 GB
```

基于 log 文件数量选择 file group：

```scala
.option("hoodie.compaction.strategy",
  "org.apache.hudi.table.action.compact.strategy.LogFileNumBasedCompactionStrategy")
.option("hoodie.compaction.logfile.num.threshold", "10")
```

说明：

- `hoodie.compact.inline.max.delta.commits` 控制何时尝试调度。
- 具体哪些 file group 进入 compaction plan，还取决于 compaction strategy。
- `LogFileSizeBasedCompactionStrategy` 只读取 `hoodie.compaction.logfile.size.threshold`；`LogFileNumBasedCompactionStrategy` 只读取 `hoodie.compaction.logfile.num.threshold`。
- 同时写上述两个 threshold 不会自动形成“log 总大小达标或 log 数量达标”的 OR 关系；未被当前 strategy 读取的参数不参与候选 file group 判断。
- 如果业务确实需要“size 或 num”组合条件，需要自定义 `CompactionStrategy`，并对候选选择、排序和单次 IO 上限进行压测。
- 如果 log 文件持续堆积，read optimized 可能正常，但 snapshot query 会越来越慢。

### 5.3 Cleaning 优化

Cleaning 用于清理旧 file slice，控制存储增长，也影响时间旅行和增量查询可回溯范围。

```scala
.option("hoodie.clean.automatic", "true")
.option("hoodie.clean.async.enabled", "false")
.option("hoodie.clean.policy", "KEEP_LATEST_COMMITS")
.option("hoodie.clean.commits.retained", "20")
.option("hoodie.clean.trigger.max.commits", "5")
```

注意：

- `hoodie.clean.commits.retained` 必须是单个整数，不能写成 `20-30`。`hoodie.cleaner.commits.retained` 是 Hudi 1.0.2 仍可识别的兼容旧名，新配置建议使用当前主名。
- `hoodie.clean.async.enabled` 是 Hudi 1.0.2 推荐写法；`hoodie.clean.async` 是兼容旧名。
- `hoodie.clean.trigger.max.commits` 是当前主名；`hoodie.clean.max.commits` 是兼容旧名。它控制距离上次 clean 多少个 commit 后尝试再次调度，不是 cleaner 的数据保留数量。
- 短生命周期 batch 作业如果设置 async clean，作业很快退出时 cleaner 可能来不及执行；batch 更建议同步 clean 或独立调度 cleaner。
- cleaner 保留周期必须覆盖增量查询消费延迟，否则下游可能找不到需要的历史文件。

保留时间估算：

```text
可回溯时间约等于 clean.commits.retained * 平均 commit 间隔

例如：
commit 间隔 10 分钟，retained=20
可回溯时间约 200 分钟
如果下游可能延迟 6 小时消费，retained 至少要大于 36，并留安全余量。
```

### 5.4 Archival 补充

清理数据文件之外，还需要关注 timeline 归档。过多 active timeline instant 会拖慢元数据操作，过少又不利于排障。

建议补充配置说明：

```scala
.option("hoodie.keep.min.commits", "30")
.option("hoodie.keep.max.commits", "50")
```

注意：

- `keep.min.commits` 应大于 cleaner 保留提交数，避免清理和归档策略冲突。
- 需要根据时间旅行、增量查询和排障窗口确定具体值。

### 5.5 Clustering 与小文件治理

Clustering 是治理小文件和优化数据布局的主要手段之一，但应作为周期性表服务运行，而不是每次写入都同步执行。

```scala
.option("hoodie.clustering.plan.strategy.small.file.limit", "104857600")
.option("hoodie.clustering.plan.strategy.max.bytes.per.group", "2147483648")
.option("hoodie.clustering.plan.strategy.max.num.groups", "30")
.option("hoodie.clustering.plan.strategy.target.file.max.bytes", "134217728")
```

建议：

- 小文件比例高且查询慢时，优先通过 clustering 重写布局。
- 如果写入批次太小，应从源头增加 micro-batch 大小或降低分区粒度。
- Clustering 与 upsert 冲突要关注 pending replace commit，频率不要过高。

## 6. 资源、网络与对象存储优化

### 6.1 Executor 配置

```bash
spark-submit \
  --executor-memory 8G \
  --executor-cores 4 \
  --executor-instances 10 \
  --conf spark.executor.memoryOverhead=2G
```

资源配置原则：

```text
CPU:
- 常用 3~5 cores / executor。
- 总 core 数决定并发上限，但不是写入并行度的唯一依据。

内存:
- index tagging、shuffle、MOR log merge、clustering 都可能消耗大量内存。
- 频繁 spill 时，优先看 task 数据量、shuffle 分区和倾斜，而不是只加内存。

memoryOverhead:
- 至少 max(384MB, executor-memory * 10%)。
- 使用对象存储、压缩、native buffer、较大 shuffle 时可适当提高。
```

### 6.2 Driver 配置

```bash
--driver-memory 4G \
--conf spark.driver.memoryOverhead=1G \
--conf spark.driver.maxResultSize=2G
```

Driver 主要风险：

- collect 大结果到 Driver。
- 过多 partition/file metadata 导致 Driver 端规划压力大。
- Hudi timeline、metadata 初始化或异常堆栈过大。

### 6.3 动态资源分配

```scala
spark.conf.set("spark.dynamicAllocation.enabled", "true")
spark.conf.set("spark.dynamicAllocation.minExecutors", "5")
spark.conf.set("spark.dynamicAllocation.maxExecutors", "50")
spark.conf.set("spark.dynamicAllocation.initialExecutors", "10")
```

注意：

- 动态资源分配需要集群侧 shuffle service 或等价能力配合。
- 对长期 streaming + async table services，要确保 executor 不会在表服务执行前被过早回收。
- 对批处理任务，动态分配可能导致资源爬升慢，影响短作业延迟。

### 6.4 网络与 Shuffle

```scala
spark.conf.set("spark.shuffle.compress", "true")
spark.conf.set("spark.shuffle.spill.compress", "true")
spark.conf.set("spark.network.timeout", "800s")
spark.conf.set("spark.executor.heartbeatInterval", "60s")
```

说明：

- 网络超时参数只能缓解长 GC 或慢 task 引发的误判，不能解决根因。
- shuffle 大时优先减少无效数据、处理倾斜、调整并行度和开启 AQE。
- 如果频繁出现 fetch failed，要检查 executor 丢失、磁盘、网络和 shuffle service。

### 6.5 S3 / 对象存储优化

```scala
spark.conf.set("spark.hadoop.fs.s3a.connection.maximum", "200")
spark.conf.set("spark.hadoop.fs.s3a.threads.max", "100")
spark.conf.set("spark.hadoop.fs.s3a.connection.timeout", "300000")
spark.conf.set("spark.hadoop.fs.s3a.fast.upload", "true")
spark.conf.set("spark.hadoop.fs.s3a.fast.upload.buffer", "disk")
spark.conf.set("spark.hadoop.fs.s3a.multipart.size", "104857600")
```

建议：

- 对象存储 list 操作慢时，优先评估 metadata table。
- 小文件会放大对象存储请求数，先治理文件数量。
- S3 committer / Spark Parquet committer 不应作为 Hudi 通用推荐；Hudi 有自己的 commit timeline 和写入机制，不同发行版类名也可能不存在。
- 并发写入对象存储时，要配置合适的锁和失败恢复策略，避免只调性能不管一致性。

### 6.6 本地磁盘

```bash
--conf spark.local.dir=/mnt/disk1/spark,/mnt/disk2/spark,/mnt/disk3/spark
```

适用场景：shuffle、sort、spill、clustering 都会使用本地磁盘。生产建议使用多块本地盘并监控磁盘空间、IOPS 和吞吐。

## 7. 监控与诊断

### 7.1 写入监控

建议监控：

- 写入吞吐：records/s、MB/s。
- commit 总耗时和各阶段耗时：index、write、commit、table service。
- 每次 commit 写入/更新/删除记录数。
- 生成文件数量、平均文件大小、小文件数量。
- MOR 表 log file 数量、log file 大小、compaction backlog。
- 并发写入锁等待、冲突和回滚次数。

### 7.2 查询监控

建议监控：

- 查询 p50/p95/p99。
- 扫描文件数、扫描字节数、返回行数。
- 分区裁剪是否生效。
- column stats / data skipping 是否减少扫描。
- MOR snapshot query 的 log merge 成本。
- Trino/Presto split 数和 worker 倾斜。

### 7.3 存储监控

建议监控：

- 总存储大小、日增长量。
- base file 和 log file 数量。
- 文件大小分布，特别是 `<32MB`、`32~128MB`、`>512MB` 的比例。
- cleaner 执行记录和清理文件数量。
- archived timeline 大小。
- metadata table 大小和 compact 状态。

### 7.4 Hudi Timeline 分析

```bash
# 使用 Hudi CLI 查看 Timeline
./hudi-cli.sh
> connect --path s3://bucket/table_path

# 查看提交历史
> commits show --limit 20

# 查看提交详情
> commit showfiles --commit 20231201120000

# 查看 compaction 状态
> compactions show

# 查看 clean 历史
> cleans show
```

重点看：

- 是否有 pending compaction / clustering 长期未执行。
- 是否频繁 rollback。
- 单次 commit 是否写出大量小文件。
- cleaner 是否按预期运行。

### 7.5 Spark UI 分析

关键页面：

1. `SQL`：看执行计划、扫描文件数、过滤下推、AQE 是否生效。
2. `Stages`：找慢 stage、shuffle 大小、task 倾斜。
3. `Executors`：看 GC、spill、失败 task、数据读写量。
4. `Storage`：看缓存是否真的命中，避免误以为 cache 生效。

常见瓶颈：

```text
长时间 Shuffle:
- 检查 shuffle read/write、partition 数和 task 倾斜。
- 优化方向：调整并行度、处理倾斜、减少无效列/行、优化索引。

数据倾斜:
- 症状：少数 task 时间远超其他 task。
- 优化方向：调整分区字段、对热点 key salting、分离热点数据。

OOM:
- 检查 executor memory、memoryOverhead、spill、单 task 输入大小。
- 优化方向：降低单 task 数据量、增加并行度、优化 join/shuffle、必要时加内存。

文件过多:
- 症状：查询规划慢、commit metadata 大、对象存储请求多。
- 优化方向：调整写入批次、目标文件大小、小文件填充、定期 clustering。
```

## 8. 常见问题与解决方案

### 8.1 写入速度慢

症状：

- 写入吞吐低于基准。
- commit 耗时增加。
- Spark UI 中 index lookup 或 shuffle stage 很慢。

诊断：

```text
1. 看慢 stage 属于 index、shuffle、write 还是 table service。
2. 检查索引类型是否匹配：是否需要全局索引？是否有大量小文件？
3. 检查 shuffle 并行度和数据倾斜。
4. 检查是否每次写入都 inline compaction/clustering。
5. 检查对象存储请求数和失败重试。
```

优化方向：

```scala
.option("hoodie.upsert.shuffle.parallelism", "200")
.option("hoodie.metadata.enable", "true")
.option("hoodie.metadata.index.bloom.filter.enable", "true")
.option("hoodie.metadata.index.bloom.filter.column.list", "record_key_field")
.option("hoodie.bloom.index.use.metadata", "true")
.option("hoodie.compact.inline", "false")
.option("hoodie.clustering.inline", "false")
```

说明：以上只是展示参数依赖的调优方向，不应直接复制。只有在 Bloom index lookup 是已确认瓶颈时，才应评估构建 metadata bloom filter index，并对比索引维护成本。若瓶颈是数据倾斜或对象存储限流，单纯增加并行度可能恶化问题。

### 8.2 查询速度慢

症状：

- 点查询或范围查询扫描大量文件。
- MOR snapshot query 越来越慢。
- 查询计划没有分区裁剪或谓词下推。

诊断：

```text
1. 查询是否带分区条件？分区字段是否和查询匹配？
2. metadata table、column stats 是否启用并被查询引擎利用？
3. 文件大小是否过小，文件数量是否过多？
4. MOR 表 log file 是否堆积，compaction 是否滞后？
5. clustering key 是否匹配高频查询条件？
```

优化方向：

```scala
.option("hoodie.metadata.enable", "true")
.option("hoodie.metadata.index.column.stats.enable", "true")
.option("hoodie.metadata.index.column.stats.column.list", "query_field,event_time")
.option("hoodie.clustering.plan.strategy.sort.columns", "event_time,user_id")
```

### 8.3 存储空间持续增长

症状：

- 存储增长明显超过新增数据量。
- `.hoodie` timeline 或 log files 持续膨胀。
- read optimized 查询正常，但 snapshot 查询变慢。

诊断：

```text
1. cleaner 是否启用并成功执行？
2. cleaner 保留 commits 是否过大？
3. MOR compaction 是否长期 pending？
4. 是否有失败写入或 rollback 残留？
5. archive 配置是否合理？
```

优化方向：

```scala
.option("hoodie.clean.automatic", "true")
.option("hoodie.clean.async.enabled", "false")
.option("hoodie.clean.commits.retained", "20")
.option("hoodie.compact.schedule.inline", "true")
.option("hoodie.keep.min.commits", "30")
.option("hoodie.keep.max.commits", "50")
```

注意：如果 `hoodie.compact.inline=false`，还需要独立执行 compaction，不能只配置 schedule。

### 8.4 小文件过多

症状：

- 查询 task 很多但每个 task 读取数据很少。
- 对象存储请求数高。
- Hudi commit metadata 大。

诊断与优化：

```text
1. 检查每批写入数据量是否太小。
2. 检查分区粒度是否过细。
3. 检查写入并行度是否过高。
4. 启用 small file handling。
5. 定期执行 clustering 合并小文件。
```

示例：

```scala
.option("hoodie.parquet.max.file.size", "134217728")
.option("hoodie.parquet.small.file.limit", "104857600")
.option("hoodie.clustering.plan.strategy.small.file.limit", "104857600")
.option("hoodie.clustering.schedule.inline", "true")
```

## 9. 生产环境检查清单

### 9.1 写入检查

- [ ] 已明确 `recordkey.field`、`precombine.field`、`partitionpath.field`。
- [ ] operation 与业务匹配：`insert`、`bulk_insert`、`upsert`、`delete`。
- [ ] 使用 `bulk_insert` 前确认目标表为空，或业务保证不会与目标表已有 key 冲突。
- [ ] 使用 `bulk_insert` 前确认本批输入内部重复 key 已在上游处理，或已显式启用 `hoodie.combine.before.insert=true` 并验证 precombine/record merger 结果。
- [ ] `hoodie.bulkinsert.sort.mode` 的选择已结合 shuffle 成本、文件布局和导入窗口验证。
- [ ] 使用 `PARTITION_SORT` 时已核对上游 partition 数，没有把 `bulkinsert.shuffle.parallelism` 误当成必然增加并发度的 repartition。
- [ ] 索引类型与主键唯一性、跨分区更新、表规模匹配。
- [ ] `hoodie.bloom.index.use.metadata=true` 时已确认所需 metadata index 实际可用，并已评估维护成本。
- [ ] 写入并行度经过压测，不只是固定 200。
- [ ] 输出文件大小接近目标文件大小。
- [ ] inline 表服务不会拖慢写入 SLA。
- [ ] Spark UI 无明显数据倾斜、频繁 OOM 或大量 spill。

### 9.2 查询检查

- [ ] 查询能命中分区裁剪。
- [ ] 高频过滤列已评估 column stats 或 clustering。
- [ ] 增量消费已明确是 `latest_state` 还是完整 CDC，并验证删除事件和 instant 边界。
- [ ] MOR 表 snapshot 查询有 compaction SLA。
- [ ] 小文件数量可控。
- [ ] Spark/Trino 查询计划符合预期。
- [ ] metadata table 和相关 index 有监控和修复预案。

### 9.3 存储与表服务检查

- [ ] cleaner 保留周期覆盖时间旅行和增量消费需求。
- [ ] compaction/clustering pending instant 不长期堆积。
- [ ] Compaction strategy 与 size/num threshold 匹配，没有把两个策略专属参数误解为自动 OR 条件。
- [ ] archive 配置与 cleaner 配置匹配。
- [ ] 对象存储请求、限流、失败重试可观测。
- [ ] 并发写入场景已配置锁和冲突处理。

### 10.3 历史初始化 Bulk Insert 模板

```scala
df.write.format("hudi")
  .option("hoodie.table.name", tableName)
  .option("hoodie.datasource.write.table.type", "COPY_ON_WRITE")
  .option("hoodie.datasource.write.operation", "bulk_insert")
  .option("hoodie.datasource.write.recordkey.field", "order_id")
  .option("hoodie.datasource.write.precombine.field", "updated_at")
  .option("hoodie.datasource.write.partitionpath.field", "dt")
  .option("hoodie.datasource.write.hive_style_partitioning", "true")
  // 如果上游已严格去重，可评估设为 false 换取更高吞吐
  .option("hoodie.combine.before.insert", "true")
  .option("hoodie.bulkinsert.shuffle.parallelism", "400")

  // PARTITION_SORT 是 Spark 分区内排序，通常不引入按 Hudi 分区的 shuffle
  // 如果要让相同 Hudi 分区的数据更集中，可评估 PARTITION_PATH_REPARTITION_AND_SORT
  .option("hoodie.bulkinsert.sort.mode", "PARTITION_SORT")

  .option("hoodie.parquet.max.file.size", "268435456")
  .option("hoodie.metadata.enable", "true")
  .mode("overwrite")
  .save(basePath)
```

建议：

- 只有在目标表为空、写入新表，或业务明确保证不会与目标表已有 key 冲突时，才优先使用 `bulk_insert`。
- `hoodie.combine.before.insert=true` 只处理本批输入内部的同 key 记录，不会查找或合并目标表中已有的同 key。
- 如果同一业务 key 可能已经存在于目标表，应改用 `upsert`。
- 初始化完成后，使用代表性 upsert 和查询进行二次压测，因为 bulk insert 的最优参数不一定适合后续增量写入。

## 11. 总结

Hudi 生产性能调优需要在写入性能、查询性能、存储成本、数据新鲜度和运维复杂度之间平衡。

关键原则：

- 不要把示例参数当作生产标准；所有核心参数都要压测。
- 优先设计正确的主键、分区、表类型和索引，再调 Spark 资源。
- `schedule.inline=true` 不等于表服务已经执行，批处理场景尤其要注意。
- 小文件是写入、查询和对象存储成本的共同敌人，要从批大小、分区、并行度和 clustering 一起治理。
- cleaner、archive、compaction 会影响时间旅行、增量查询和 MOR 查询延迟，不能只看存储成本。
- 所有“性能提升倍数”和“秒级查询”都必须以本项目数据、集群和 SLA 的压测结果为准。
