# 时间旅行与增量查询对比笔记

本文整理本次关于 Apache Hudi 时间旅行（Time Travel）、增量查询（Incremental Query）、压缩（Compaction）和清理（Cleaner）的讨论，重点说明它们的语义区别、底层关系，以及对历史版本可用性的影响。

## 1. 一句话区别

时间旅行和增量查询都依赖 Hudi 的 Timeline、MVCC 和 File Slice 机制，但查询目标不同：

| 功能 | 核心问题 | 返回结果 |
|---|---|---|
| 时间旅行 | 某个历史时刻，整张表长什么样？ | 指定 instant 对应的完整快照 |
| 增量查询 | 某个时间范围内，哪些记录发生过变化？ | 指定 begin/end 范围内的变更记录 |

简单理解：

```text
Time Travel      = 查询历史快照
Incremental Query = 查询一段时间内的变化
```

## 2. 时间旅行是什么

时间旅行通过 `as.of.instant` 指定一个历史 instant，查询表在该 instant 的逻辑状态。

示例：

```scala
val df = spark.read.format("hudi")
  .option("as.of.instant", targetInstant)
  .load(basePath)
```

典型用途：

- 数据审计
- 问题排查
- 历史版本对比
- 错误数据恢复
- 合规留存查询

时间旅行返回的是目标 instant 下的完整表快照，而不是变化记录。

## 3. 增量查询是什么

增量查询通过 begin/end instant 指定一个时间范围，只读取该范围内发生变化的数据。

示例：

```scala
val df = spark.read.format("hudi")
  .option("hoodie.datasource.query.type", "incremental")
  .option("hoodie.datasource.read.begin.instanttime", beginCompletionTime)
  .option("hoodie.datasource.read.end.instanttime", endCompletionTime)
  .load(basePath)
```

典型用途：

- 增量 ETL
- CDC 同步
- 下游数据仓库同步
- 流式或批式增量处理
- 只处理新增、更新、删除的数据

增量查询默认通常返回增量范围内每个 key 的最新状态，不一定等同于完整 CDC 明细；如果需要完整 insert/update/delete 事件，需要结合 Hudi CDC 能力和对应配置。

## 4. Hudi 1.0.x 中的 requested time 与 completion time

在 Hudi 1.0.x 的 timeline layout v2 中，需要区分两个时间：

| 时间 | 含义 | 常见位置 |
|---|---|---|
| requested time | instant 被请求创建的时间 | 记录字段 `_hoodie_commit_time` 通常是这个值 |
| completion time | commit 真正完成的时间 | timeline 中 `HoodieInstant.getCompletionTime` |

关键点：

- `_hoodie_commit_time` 适合展示和排查。
- 增量查询的 `begin.instanttime` / `end.instanttime` 应优先使用 completion time。
- 不建议直接把 `_hoodie_commit_time` 当成增量查询边界。

推荐通过 `HoodieTableMetaClient` 获取 completed timeline：

```scala
case class CommitTime(requestedTime: String, completionTime: String)

val commits = metaClient.getCommitsTimeline
  .filterCompletedInstants()
  .getInstants
  .asScala
  .map(instant => CommitTime(instant.requestedTime(), instant.getCompletionTime))
  .toSeq
```

## 5. Compaction 与查询功能的关系

Compaction 不是时间旅行，也不是增量查询。它是 MOR 表的 table service，用于把 log files 合并进新的 base parquet 文件。

关系可以理解为：

```text
Timeline / MVCC / File Slices
├── Time Travel       按某个 instant 读取历史快照
├── Incremental Query 按 instant 范围读取变化
└── Compaction        合并 MOR 表的 base + log，生成新的 base file
```

Compaction 的主要作用：

- 提升 MOR 表查询性能
- 让 Read Optimized Query 能看到被压缩进 base file 的数据
- 减少 snapshot 查询时需要合并的 log files
- 改变物理文件布局，而不是改变数据的逻辑历史

## 6. COW 与 MOR 的底层差异

### 6.1 COW 表

COW 是 Copy-on-Write。更新时直接生成新的 parquet base file。

示例：

```text
t1: base parquet v1: A=10
t2: update A=20
    生成 base parquet v2: A=20
    旧 base parquet v1 暂时保留
```

特点：

- 没有 compaction。
- 每次更新会生成新的 base file。
- 旧 base file 是否保留，由 cleaner 决定。
- 时间旅行依赖旧 file version 是否仍然存在。

### 6.2 MOR 表

MOR 是 Merge-on-Read。更新通常先写入 log file，后续可通过 compaction 合并成新的 base file。

示例：

```text
t1: base parquet: A=10
t2: log file: A=20
t3: compaction
    生成新的 base parquet: A=20
    旧 base/log 暂时保留
```

特点：

- 有 compaction。
- 写入性能通常更好。
- Snapshot Query 会合并 base + log。
- Read Optimized Query 只读 base file，可能落后于最新写入。
- 旧 base/log 是否清理，由 cleaner 决定。

## 7. Compaction 会不会让时间旅行失效

通常不会。

Compaction 一般不是原地覆盖旧文件，而是生成新的 file slice。旧的 base/log 文件通常会暂时保留，用于支持 MVCC、长查询和历史版本读取。

例如：

```text
t1: A=10
t2: A=20
t3: B=30
t4: compaction
```

Compaction 后可能形成：

```text
旧 file slice:
  base/log 可以重建 t1/t2/t3 的历史状态

新 file slice:
  compacted base file，包含 t4 时刻的 A=20, B=30
```

此时：

```text
as.of.instant = t1 -> 理论上仍可看到 A=10
as.of.instant = t4 -> 看到 A=20, B=30
```

真正可能让 `as.of.instant = t1` 不可用的是 cleaner 或 timeline/file retention，而不是 compaction 本身。

## 8. Cleaner 才是历史版本保留的关键

Cleaner 负责删除超过保留策略的旧文件版本。

可以这样区分：

```text
Compaction = 生成新的合并后版本
Cleaner    = 删除过期旧版本
```

如果 cleaner 还没有清理支持 t1 的旧文件：

```text
as.of.instant = t1 -> 可以查询历史版本
```

如果 cleaner 已经清理了支持 t1 的旧文件：

```text
as.of.instant = t1 -> 可能失败，或无法重建该历史快照
```

COW 和 MOR 都受 cleaner 管理：

| 表类型 | 是否有 compaction | 是否有 cleaner | 历史文件由谁清理 |
|---|---:|---:|---|
| COW | 否 | 是 | cleaner |
| MOR | 是 | 是 | cleaner |

## 9. 增量查询、时间旅行和 compaction 是否相互影响

### 9.1 增量查询是否会执行 compaction

不会。增量查询是读操作，本身不会触发 compaction。

但写入作业、流式作业或独立 table service 可能配置了 inline/async compaction，这属于写入或 table service 行为，不是增量查询本身。

### 9.2 Compaction 是否会影响增量查询

通常不会改变增量查询的逻辑结果。

Compaction 不应该把已经发生过的业务更新重新变成新的业务变更。增量查询仍然按照 timeline 的 instant 范围判断哪些记录发生变化。

但 compaction 可能影响：

- 物理读取路径
- 查询性能
- Read Optimized Query 的可见数据范围

真正会让增量查询出问题的常见原因是：

```text
增量消费者 checkpoint 太旧
+ cleaner/archival 已经清理了相关历史文件或 timeline
= 无法从旧 checkpoint 正常继续
```

### 9.3 时间旅行是否会影响增量查询

不会。时间旅行也是读操作，不会改变表数据，不会触发 compaction，也不会影响增量查询结果。

## 10. 典型时间线示例

假设 MOR 表：

```text
t1 delta/base: A=10
t2 delta:      A=20
t3 delta:      B=30
t4 compaction: 生成新 base: A=20, B=30
t5 delta:      B=40
```

时间旅行结果：

```text
as.of t1 -> A=10
as.of t2 -> A=20
as.of t3 -> A=20, B=30
as.of t5 -> A=20, B=40
```

增量查询结果：

```text
begin=t1, end=t3 -> 返回 t2~t3 范围内变化的数据
begin=t3, end=t5 -> 返回 t5 范围内变化的数据，例如 B=40
```

Compaction t4 的作用：

```text
压缩前: Snapshot 可能需要读取 base + 多个 log
压缩后: t4 之后的读取可以更多依赖新的 compacted base file
```

但 t4 不应该让 t1 的历史语义立即消失。t1 是否还能查，取决于 supporting files 是否仍在 cleaner 保留范围内。

## 11. 常见误区

### 误区 1：Compaction 后旧值一定立刻消失

不准确。

Compaction 会生成新的合并后 base file，但旧 base/log 通常由 cleaner 后续按策略清理。

### 误区 2：MOR 有历史版本，COW 没有历史版本

不准确。

COW 更新时也会生成新的 base file version，旧版本也可能暂时保留，因此也可以支持时间旅行。区别是 COW 没有 compaction。

### 误区 3：增量查询的边界可以直接用 `_hoodie_commit_time`

在 Hudi 1.0.x 中不推荐。

`_hoodie_commit_time` 通常是 requested time，而增量查询 begin/end 边界应优先使用 timeline 中的 completion time。

### 误区 4：时间旅行能永久查询任意历史版本

不一定。

时间旅行能力受 cleaner、archival 和文件保留策略影响。旧文件被清理后，对应历史快照可能无法重建。

## 12. 生产实践建议

### 12.1 如果依赖时间旅行

需要配置足够的历史保留：

```text
hoodie.cleaner.commits.retained
hoodie.keep.min.commits
hoodie.keep.max.commits
```

建议：

- 根据审计和回溯需求设置保留周期。
- 对关键版本使用 savepoint 或导出归档。
- 不要只依赖默认 cleaner 策略。
- 定期验证重要历史 instant 是否仍可查询。

### 12.2 如果依赖增量查询

需要管理好 checkpoint：

```text
last_processed_completion_time
```

建议：

- checkpoint 使用 completion time。
- 增量消费者不要长时间停滞。
- cleaner retention 必须大于最大消费延迟。
- 下游处理逻辑保持幂等。
- 如果需要完整 CDC 语义，开启并验证 Hudi CDC 配置。

### 12.3 如果使用 MOR 表

需要同时关注 compaction 和 cleaner：

```text
compaction -> 查询性能和 read optimized 可见性
cleaner    -> 历史版本和增量 checkpoint 可追溯性
```

建议：

- 通过 compaction 控制 log 文件数量。
- 通过 cleaner retention 控制历史可查时间。
- 不要把 compaction 误认为历史清理机制。

## 13. 最终结论

可以用下面几句话总结：

```text
时间旅行查询历史快照。
增量查询读取时间范围内的变化。
Compaction 优化 MOR 表的物理文件布局。
Cleaner 决定旧版本文件保留多久。
COW 没有 compaction，但同样有 cleaner 和历史 file versions。
MOR 有 compaction，也有 cleaner。
历史版本是否还能查，核心取决于 timeline 和所需文件是否仍在保留范围内。
```
