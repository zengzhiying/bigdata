# Hudi 核心概念：查询类型 (Query Types)

## 概述

Apache Hudi 支持三种查询类型，每种查询类型针对不同的数据访问模式进行了优化：

- **Snapshot Query（快照查询）** - 查询表的最新完整状态
- **Incremental Query（增量查询）** - 查询指定时间范围内的变更数据
- **Read Optimized Query（读优化查询）** - 仅读取基础文件，性能最优但数据可能滞后（仅 MOR 表）

---

## 1. Snapshot Query（快照查询）

### 1.1 概念

Snapshot Query 是 Hudi 的**默认查询类型**，返回表的最新已提交快照，显示每条记录的最新版本。

### 1.2 工作原理

**对于 COW 表：**
- 直接读取 Parquet 基础文件
- 性能高效，无需额外合并操作

**对于 MOR 表：**
- 读取 Parquet 基础文件
- **实时合并** Avro 增量日志文件
- 返回最新的完整数据视图

```
COW: [Base Parquet Files] → Snapshot Result
MOR: [Base Parquet Files] + [Delta Logs] → Merge → Snapshot Result
```

### 1.3 核心特点

| 特性 | 说明 |
|-----|------|
| **默认查询** | 是，无需配置 |
| **数据新鲜度** | 最新（包含所有已提交的更新） |
| **支持表类型** | COW 和 MOR 都支持 |
| **查询性能** | COW: 快，MOR: 中等（需合并） |
| **返回数据** | 完整的当前状态 |
| **使用场景** | 通用查询、实时仪表盘、即席分析 |

### 1.4 配置示例

```scala
// 方式1: 默认即为 Snapshot Query
val df = spark.read.format("hudi").load(basePath)

// 方式2: 显式指定
val df = spark.read.format("hudi")
  .option("hoodie.datasource.query.type", "snapshot")
  .load(basePath)
```

### 1.5 适用场景

✅ **推荐使用场景：**
- 大多数通用查询需求
- 实时业务仪表盘
- 需要最新数据的分析查询
- 即席查询和数据探索
- BI 工具集成

❌ **不推荐使用场景：**
- 仅需要增量变更数据（使用 Incremental Query）
- MOR 表且对查询性能要求极高（使用 Read Optimized Query）

### 1.6 代码示例

参考文件：`src/main/scala/org/example/query_types/HudiSnapshotQueryExample.scala`

**示例代码片段：**

```scala
// 创建表并插入初始数据
df.write.format("hudi")
  .option("hoodie.table.name", tableName)
  .mode(SaveMode.Overwrite)
  .save(basePath)

// 快照查询（默认）
val snapshotDf = spark.read.format("hudi").load(basePath)
snapshotDf.show()

// 更新数据
updateDf.write.format("hudi")
  .option("hoodie.datasource.write.operation", "upsert")
  .mode(SaveMode.Append)
  .save(basePath)

// 再次快照查询，自动获取最新数据
val latestSnapshot = spark.read.format("hudi").load(basePath)
latestSnapshot.show()  // 显示更新后的数据
```

## 2. Incremental Query（增量查询）

### 2.1 概念

Incremental Query 用于**查询指定时间范围内的变更数据**（Change Data Capture），仅返回新增或修改的记录，而非完整快照。

### 2.2 工作原理

通过指定开始和结束的 instant time，Hudi 仅返回该时间范围内发生变化的记录。Hudi 1.0.x（timeline layout v2）里需要特别区分两个时间：

- **requested time**：写入 instant 的请求时间，记录中的 `_hoodie_commit_time` 通常是这个值。
- **completion time**：commit 真正完成的时间，`hoodie.datasource.read.begin.instanttime` 和 `hoodie.datasource.read.end.instanttime` 按这个时间判断范围。

```
Timeline:
  Commit1(requested=t1, completion=c1)
  Commit2(requested=t2, completion=c2)
  Commit3(requested=t3, completion=c3)
  Commit4(requested=t4, completion=c4)

Incremental Query(begin=c2, end=c4)
  ↓
Returns: Records changed in Commit2, Commit3 and Commit4
```

如果把 `_hoodie_commit_time` 直接当作 begin/end 传入，可能因为 requested time 与 completion time 不完全一致，出现边界看起来像“左闭右开”的现象。

### 2.3 核心特点

| 特性 | 说明 |
|-----|------|
| **默认查询** | 否，需显式配置 |
| **数据新鲜度** | 最新（指定时间范围内的变更） |
| **支持表类型** | COW 和 MOR 都支持 |
| **查询性能** | 快（仅扫描相关提交的数据） |
| **返回数据** | 默认返回变更记录的最新状态（latest_state），可配置 CDC 格式 |
| **使用场景** | 增量 ETL、数据同步、事件处理 |

### 2.4 配置示例

```scala
// 基本增量查询：从指定 completion time 开始到最新
val incrementalDf = spark.read.format("hudi")
  .option("hoodie.datasource.query.type", "incremental")
  .option("hoodie.datasource.read.begin.instanttime", "20231201120000000")
  .load(basePath)

// 指定 completion time 范围的增量查询
val incrementalDf = spark.read.format("hudi")
  .option("hoodie.datasource.query.type", "incremental")
  .option("hoodie.datasource.read.begin.instanttime", "20231201120000000")
  .option("hoodie.datasource.read.end.instanttime", "20231202120000000")
  .load(basePath)
```

### 2.5 关键配置参数

| 参数 | 说明 | 必需 |
|------|------|------|
| `hoodie.datasource.query.type` | 设置为 `incremental` | 是 |
| `hoodie.datasource.read.begin.instanttime` | 开始 completion time | 是 |
| `hoodie.datasource.read.end.instanttime` | 结束 completion time | 否 |
| `hoodie.datasource.query.incremental.format` | 增量返回格式：`latest_state` 或 `cdc` | 否 |

**注意：**
- Hudi 1.0.x 中 begin/end 使用 completion time，不建议直接使用 `_hoodie_commit_time` 作为边界。
- 默认范围语义按 completion time 闭区间理解：`completion_time >= begin` 且 `completion_time <= end`。
- 如果不指定 `end.instanttime`，则读取到最新已完成提交。
- 时间戳格式：`yyyyMMddHHmmssSSS`。
- 默认 `hoodie.datasource.query.incremental.format = latest_state`，返回增量范围内记录的最新状态；如需完整 CDC 明细，需要使用 `cdc` 格式并开启表的 CDC 能力。

### 2.6 获取提交时间

`_hoodie_commit_time` 可以帮助观察每条记录来自哪个 requested instant，但增量查询边界应优先使用 timeline 中的 completion time：

```scala
import org.apache.hudi.common.table.HoodieTableMetaClient
import org.apache.hudi.hadoop.fs.HadoopFSUtils
import scala.collection.JavaConverters._

case class CommitTime(requestedTime: String, completionTime: String)

def getCommitTimes(spark: SparkSession, basePath: String): Seq[CommitTime] = {
  val metaClient = HoodieTableMetaClient.builder()
    .setConf(HadoopFSUtils.getStorageConf(spark.sparkContext.hadoopConfiguration))
    .setBasePath(basePath)
    .build()

  metaClient.getCommitsTimeline
    .filterCompletedInstants()
    .getInstants
    .asScala
    .map(instant => CommitTime(instant.requestedTime(), instant.getCompletionTime))
    .sortBy(_.requestedTime)
    .toSeq
}

val commits = getCommitTimes(spark, basePath)
commits.foreach { c =>
  println(s"requested=${c.requestedTime}, completion=${c.completionTime}")
}
```

如果只是展示记录上的提交时间，可以继续读取 `_hoodie_commit_time`：

```scala
spark.read.format("hudi").load(basePath)
  .select("_hoodie_commit_time")
  .distinct()
  .orderBy("_hoodie_commit_time")
  .show()
```

Hudi 1.0.x 的 timeline 文件名通常形如 `requestedTime_completionTime.commit`，但生产代码建议使用 `HoodieTableMetaClient`，不要手工解析文件名。

### 2.7 适用场景

✅ **推荐使用场景：**
- **增量 ETL 管道**：仅处理新增/变更数据
- **Change Data Capture (CDC)**：捕获数据变更
- **数据同步**：同步变更到下游系统
- **事件驱动处理**：处理增量事件
- **减少数据处理量**：避免全量扫描

❌ **不推荐使用场景：**
- 需要完整数据快照
- 不关心时间范围的查询

### 2.8 代码示例

参考文件：`src/main/scala/org/example/query_types/HudiIncrementalQueryExample.scala`

**示例代码片段：**

```scala
// 第一次写入
batch1Df.write.format("hudi").save(basePath)
val commit1Time = getCommitTimes(spark, basePath).last

// 第二次写入
batch2Df.write.format("hudi").mode(SaveMode.Append).save(basePath)
val commit2Time = getCommitTimes(spark, basePath).last

// 增量查询：使用 completion time 作为边界
val changes = spark.read.format("hudi")
  .option("hoodie.datasource.query.type", "incremental")
  .option("hoodie.datasource.read.begin.instanttime", commit2Time.completionTime)
  .option("hoodie.datasource.read.end.instanttime", commit2Time.completionTime)
  .load(basePath)

changes.show()  // 显示 batch2 的数据
```

### 2.9 实际应用案例

**场景：每日增量 ETL 管道**

```scala
// 保存上次已处理的 completion time
val lastProcessedCompletionTime = getLastProcessedCompletionTime()  // 从检查点获取

// begin/end 是闭区间；下一轮应从第一个大于 checkpoint 的 completion time 开始，避免重复处理 checkpoint 所在 commit
val nextBeginCompletionTime = getCommitTimes(spark, basePath)
  .find(_.completionTime > lastProcessedCompletionTime)
  .map(_.completionTime)

nextBeginCompletionTime.foreach { beginTime =>
  val incrementalData = spark.read.format("hudi")
    .option("hoodie.datasource.query.type", "incremental")
    .option("hoodie.datasource.read.begin.instanttime", beginTime)
    .load(basePath)

  // 处理增量数据
  incrementalData
    .transform(processData)
    .write
    .format("parquet")
    .save("s3://warehouse/processed_data")
}

// 处理完成后更新最后处理的 completion time
val newLastCompletionTime = getCommitTimes(spark, basePath).last.completionTime
saveLastProcessedCompletionTime(newLastCompletionTime)
```

## 3. Read Optimized Query（读优化查询）

### 3.1 概念

Read Optimized Query **仅适用于 MOR 表**，只读取基础 Parquet 文件，跳过 Avro 增量日志，提供最快的查询性能，但数据可能不包含最新更新。

### 3.2 工作原理

**仅读取已压缩的基础文件：**

```
MOR 表结构:
  ├── Base Parquet Files (已压缩数据)
  └── Delta Logs (最近的更新，未压缩)

Snapshot Query:    [Base Files] + [Delta Logs] → Complete & Fresh
Read Optimized:    [Base Files] only → Fast but Stale
```

### 3.3 核心特点

| 特性 | 说明 |
|-----|------|
| **默认查询** | 否，需显式配置 |
| **数据新鲜度** | 可能过时（不包含未压缩的更新） |
| **支持表类型** | **仅 MOR 表**，COW 表无效 |
| **查询性能** | 最快（直接读 Parquet） |
| **返回数据** | 基础文件中的数据（压缩后） |
| **使用场景** | 长时间分析查询、可容忍数据延迟的场景 |

### 3.4 配置示例

```scala
val roDf = spark.read.format("hudi")
  .option("hoodie.datasource.query.type", "read_optimized")
  .load(basePath)
```

### 3.5 数据新鲜度

**Read Optimized Query 何时能看到更新？**

只有在**压缩（Compaction）完成后**，增量日志合并到基础文件，更新才对 Read Optimized Query 可见。

```
Timeline:
  [Commit1: Insert] → Base Files created ✓
  [Commit2: Update] → Delta Logs created (RO Query 看不到)
  [Commit3: Update] → More Delta Logs (RO Query 看不到)
  [Compaction]      → Merge Delta → Base Files (RO Query 现在可见)
```

### 3.6 适用场景

✅ **推荐使用场景：**
- **长时间运行的分析查询**（小时级/天级）
- **BI 报表**，定时刷新（如每日报表）
- **批处理作业**，对数据延迟不敏感
- **查询性能优先**，可接受轻微数据滞后
- **MOR 表的历史数据分析**

❌ **不推荐使用场景：**
- 需要实时/最新数据
- COW 表（无效，等同于 Snapshot Query）
- 对数据新鲜度要求高的场景

### 3.7 与 Snapshot Query 对比（MOR 表）

| 维度 | Snapshot Query | Read Optimized Query |
|------|----------------|----------------------|
| **读取内容** | 基础文件 + 增量日志 | 仅基础文件 |
| **数据新鲜度** | 最新（所有更新） | 可能滞后（仅压缩后） |
| **查询性能** | 中等（需合并） | 最快（直接读 Parquet） |
| **使用复杂度** | 简单 | 需了解压缩机制 |
| **适用场景** | 通用查询 | 性能敏感型查询 |

### 3.8 代码示例

参考文件：`src/main/scala/org/example/query_types/HudiReadOptimizedQueryExample.scala`

**示例代码片段：**

```scala
// 创建 MOR 表
df.write.format("hudi")
  .option("hoodie.datasource.write.table.type", "MERGE_ON_READ")
  .option("hoodie.compact.inline", "false")  // 禁用自动压缩
  .save(basePath)

// Snapshot Query（包含所有更新）
val snapshotDf = spark.read.format("hudi").load(basePath)
println(s"Snapshot count: ${snapshotDf.count()}")

// 更新数据（写入增量日志）
updateDf.write.format("hudi")
  .option("hoodie.datasource.write.operation", "upsert")
  .mode(SaveMode.Append)
  .save(basePath)

// Snapshot Query（看到更新）
val snapshotAfter = spark.read.format("hudi").load(basePath)
snapshotAfter.filter("uuid = 'uuid-001'").show()  // 显示更新后的值

// Read Optimized Query（看不到更新，因为未压缩）
val roDf = spark.read.format("hudi")
  .option("hoodie.datasource.query.type", "read_optimized")
  .load(basePath)
roDf.filter("uuid = 'uuid-001'").show()  // 显示旧值
```

## 4. 查询类型对比总结

### 4.1 完整对比表

| 特性 | Snapshot Query | Incremental Query | Read Optimized Query |
|------|---------------|-------------------|---------------------|
| **默认查询** | ✅ 是 | ❌ 否 | ❌ 否 |
| **支持 COW 表** | ✅ 是 | ✅ 是 | ⚠️ 无意义（等同 Snapshot） |
| **支持 MOR 表** | ✅ 是 | ✅ 是 | ✅ 是 |
| **数据新鲜度** | 最新 | 最新（指定范围） | 可能滞后 |
| **返回数据类型** | 完整快照 | 变更记录最新状态 / CDC 明细 | 完整快照（基础文件） |
| **查询性能** | COW: 快<br>MOR: 中 | 快 | 最快 |
| **需要时间范围** | ❌ 否 | ✅ 是 | ❌ 否 |
| **合并增量日志** | ✅ 是（MOR） | ✅ 是 | ❌ 否 |
| **典型用例** | 通用查询 | 增量 ETL | 高性能分析（MOR） |

### 4.2 决策树

```
需要完整数据快照？
├─ 是 → 对查询性能要求极高？
│        ├─ 是 → 使用 MOR 表？
│        │        ├─ 是 → 可接受数据延迟？
│        │        │        ├─ 是 → Read Optimized Query
│        │        │        └─ 否 → Snapshot Query
│        │        └─ 否 → Snapshot Query
│        └─ 否 → Snapshot Query
│
└─ 否 → 只需要变更数据？
         └─ 是 → Incremental Query
```

### 4.3 组合使用示例

在实际生产环境中，通常**组合使用**多种查询类型：

```scala
// 场景：每日数据处理管道

// 1. 使用 Incremental Query 获取增量数据
val beginCompletionTime = getCommitTimes(spark, basePath)
  .find(_.completionTime > lastCompletionTime)
  .map(_.completionTime)
  .get

val dailyChanges = spark.read.format("hudi")
  .option("hoodie.datasource.query.type", "incremental")
  .option("hoodie.datasource.read.begin.instanttime", beginCompletionTime)
  .load(basePath)

// 2. 处理增量数据
dailyChanges.write.save("warehouse/daily_changes")

// 3. 使用 Snapshot Query 验证完整性
val currentState = spark.read.format("hudi").load(basePath)
assert(currentState.count() == expectedCount)

// 4. 使用 Read Optimized Query 生成报表（MOR 表）
val report = spark.read.format("hudi")
  .option("hoodie.datasource.query.type", "read_optimized")
  .load(basePath)
report.write.save("reports/daily_summary")
```

## 6. 最佳实践

### 6.1 Snapshot Query 最佳实践

1. **默认选择**：大多数场景使用 Snapshot Query
2. **性能优化**：对 MOR 表定期执行压缩以提升查询性能
3. **分区裁剪**：利用分区字段过滤减少扫描数据量
   ```scala
   df.filter("city = 'san_francisco'")  // 只扫描相关分区
   ```

### 6.2 Incremental Query 最佳实践

1. **记录检查点**：持久化最后已处理的 completion time；因为 begin/end 是闭区间，下一次读取应从第一个大于 checkpoint 的 completion time 开始，或保证下游幂等去重。
   ```scala
   // 保存检查点
   saveCheckpoint(tableName, lastCompletionTime)
   
   // 恢复检查点
   val lastCompletionTime = loadCheckpoint(tableName)
   val startTime = getCommitTimes(spark, basePath)
     .find(_.completionTime > lastCompletionTime)
     .map(_.completionTime)
   ```

2. **批量处理**：定期运行增量查询，避免时间范围过大
   ```scala
   // 每小时处理一次增量
   val hourlyChanges = incrementalQuery(lastHour, now)
   ```

3. **监控延迟**：跟踪处理延迟，确保及时处理增量数据

4. **幂等处理**：确保增量处理逻辑幂等，支持重试

### 6.3 Read Optimized Query 最佳实践

1. **仅用于 MOR 表**：对 COW 表无效，使用 Snapshot Query

2. **配置压缩策略**：定期压缩以减少数据延迟
   ```scala
   .option("hoodie.compact.inline", "true")
   .option("hoodie.compact.inline.max.delta.commits", "5")
   ```

3. **明确数据延迟**：在 SLA 中明确定义可接受的数据延迟

4. **监控压缩状态**：跟踪压缩任务，确保及时执行

5. **混合查询策略**：
   - 实时查询：Snapshot Query
   - 批量报表：Read Optimized Query

## 7. 常见问题 (FAQ)

### Q1: Snapshot Query 在 MOR 表上查询很慢，如何优化？

**A:** 
1. **定期压缩**：减少增量日志文件数量
2. **启用元数据表**：加速文件列表
   ```scala
   .option("hoodie.metadata.enable", "true")
   ```
3. **调整压缩参数**：更频繁地压缩
   ```scala
   .option("hoodie.compact.inline.max.delta.commits", "3")
   ```

### Q2: Incremental Query 如何处理删除操作？

**A:** 默认 `latest_state` 格式更适合增量 ETL 获取最新状态，不等同于完整 CDC 明细。若需要识别 insert/update/delete 操作：

1. 写入侧需要持久化操作元数据或启用 CDC 能力，例如普通元字段场景可加：
   ```scala
   .option("hoodie.allow.operation.metadata.field", "true")
   ```
2. 读取完整变更日志时，使用 CDC 相关配置：
   ```scala
   val changes = spark.read.format("hudi")
     .option("hoodie.datasource.query.type", "incremental")
     .option("hoodie.datasource.query.incremental.format", "cdc")
     .option("hoodie.datasource.read.begin.instanttime", beginCompletionTime)
     .option("hoodie.datasource.read.end.instanttime", endCompletionTime)
     .load(basePath)
   ```
3. 如果只是普通 incremental latest_state 查询，`_hoodie_operation` 是否存在取决于写入时是否开启 `hoodie.allow.operation.metadata.field`。

### Q3: Read Optimized Query 何时能看到最新数据？

**A:** 仅在**压缩完成后**。可以：
1. 手动触发压缩
2. 配置自动压缩策略
3. 使用独立的压缩作业

### Q4: 如何选择合适的查询类型？

**A:** 参考决策矩阵：

| 需求 | 推荐查询类型 |
|------|-------------|
| 最新完整数据 | Snapshot Query |
| 仅需变更数据 | Incremental Query |
| 高性能 + 可接受延迟（MOR） | Read Optimized Query |
| CDC / 增量 ETL | Incremental Query |
| 实时仪表盘 | Snapshot Query |
| 批量报表（MOR） | Read Optimized Query |

### Q5: Incremental Query 的时间戳从哪里获取？

**A:** 推荐从 Hudi timeline 获取 completion time，而不是直接使用 `_hoodie_commit_time`。`_hoodie_commit_time` 是记录上的 requested time，适合展示和排查；增量查询 begin/end 边界应使用 `HoodieInstant.getCompletionTime`。

```scala
val commits = getCommitTimes(spark, basePath)
commits.foreach { c =>
  println(s"requested=${c.requestedTime}, completion=${c.completionTime}")
}
```
