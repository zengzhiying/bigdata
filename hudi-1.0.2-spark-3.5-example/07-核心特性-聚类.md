# Hudi 核心特性：聚类 (Clustering)

## 概述

聚类（Clustering）是 Apache Hudi 的一项强大特性，用于**重新组织数据文件的物理布局**，以优化查询性能和存储效率。通过对数据进行重新分组和排序，Clustering 通常可以改善范围查询、过滤查询等依赖数据跳过和文件裁剪的查询性能；对 Join 的收益通常来自被 Join Key 过滤或排序后的局部性改善，并不等同于 bucket join 或全局共置。

### 核心价值

- **优化文件布局**：将相关数据聚集在一起
- **提升查询性能**：减少扫描的文件数量
- **解决小文件问题**：合并小文件，提高 I/O 效率
- **改善数据局部性**：增强缓存命中率
- **降低存储成本**：更好的压缩比

## 1. 为什么需要 Clustering？

### 1.1 数据写入的问题

```
典型写入模式:
时间 T1: 写入 100 条记录 → 创建 file1.parquet
时间 T2: 写入 100 条记录 → 创建 file2.parquet
时间 T3: 小批量写入 50 条记录  → 创建 file3.parquet (小文件)
时间 T4: 写入 80 条记录      → 创建 file4.parquet (小文件)

问题:
1. 文件大小不均 (100, 100, 50, 80 条记录)
2. 相关数据分散在多个文件
3. 查询需要扫描所有文件
4. 小文件过多，元数据开销大
```

### 1.2 Clustering 的解决方案

```
Clustering 后:
1. 合并小文件: file3 + file4 → file5 (130 条记录)
2. 按 sort.columns 排序（如果配置）
3. 文件大小均衡: ~100-130 条记录/文件
4. 相关数据在同一文件: 范围查询更快

效果:
✓ 文件数量: 4 → 3
✓ 文件大小均衡
✓ 数据有序存储
✓ 查询性能可能明显提升（具体取决于查询谓词、文件统计、数据规模和执行引擎）
```

## 2. Clustering 工作原理

### 2.1 Clustering 流程

```
1. 识别阶段 (Identify)
   ├─ 扫描表文件
   ├─ 识别候选 file slices（默认关注小于 small.file.limit 的文件）
   ├─ 排除 pending compaction / pending clustering 的 file groups
   └─ 生成 Clustering Plan

2. 调度阶段 (Schedule)
   ├─ 选择要重组的文件组
   ├─ 确定 Clustering 策略
   └─ 记录到 Timeline（.replacecommit.requested）

3. 执行阶段 (Execute)
   ├─ 读取 Clustering Plan 中的 file slices
   ├─ 按执行策略重新分组/排序（如配置 sort.columns）
   ├─ 写入新的优化文件
   └─ 通过 replace commit 让旧 file groups 被新 file groups 替换

4. 完成阶段 (Commit)
   ├─ 提交 ReplaceCommit（requested → inflight → completed）
   ├─ 更新元数据和 timeline
   └─ 旧文件后续由 Cleaning 按保留策略物理清理
```

### 2.2 Clustering Key（聚类键）

**定义：** 常指 `hoodie.clustering.plan.strategy.sort.columns`，用于 Clustering 执行阶段对数据排序。注意：它不是 Hudi 的主键，也不一定决定候选文件如何被选中；默认候选选择主要由分区、文件大小和 group 配置决定。

**选择原则：**
```
优先级 1: 高频过滤字段
  SELECT * FROM table WHERE date = '2023-12-01'
  → clustering_key: date

优先级 2: 范围查询字段
  SELECT * FROM table WHERE timestamp BETWEEN t1 AND t2
  → clustering_key: timestamp

优先级 3: Join 键字段
  SELECT * FROM t1 JOIN t2 ON t1.user_id = t2.user_id
  → clustering_key: user_id

优先级 4: 选择性和排序前缀
  原则: 复合列顺序应匹配查询谓词前缀和范围条件
  注意: 高基数不是唯一标准；日期、地区等中低基数字段在高频过滤时也可能适合放前面
```

**示例：**
```scala
// 单字段 Clustering Key
.option("hoodie.clustering.plan.strategy.sort.columns", "event_time")

// 多字段 Clustering Key (复合)
.option("hoodie.clustering.plan.strategy.sort.columns", "country,city,event_time")
```

## 3. Clustering 类型

### 3.1 Inline Clustering（内联聚类）

**定义：** 在写入操作中**同步执行**的聚类

**特点：**
- ✅ 写入完成后自动调度并执行 Clustering
- ✅ 保持数据持续优化
- ❌ 增加写入延迟和资源占用
- ❌ 对高频写入容易形成阻塞或抖动

**配置：**
```scala
.option("hoodie.clustering.inline", "true")
.option("hoodie.clustering.inline.max.commits", "4")  // 每 4 次提交触发 planning
```

**适用场景：**
- 写入不频繁的批处理
- 对写入延迟不敏感
- 数据需要持续保持优化状态

### 3.2 Async Clustering（异步聚类）

**定义：** 将 Clustering 的调度和/或执行从普通写入路径中拆出来，降低写入延迟。常见有两种模式：写入作业内联调度、外部作业执行；或启用 writer 内部异步 clustering service。

**特点：**
- ✅ 不阻塞写入操作
- ✅ 写入延迟低
- ✅ 适合高频写入
- ❌ 需要额外调度
- ❌ 数据优化有延迟

**配置：**
```scala
// 模式 A：写入时仅调度 Clustering Plan，不执行
.option("hoodie.clustering.inline", "false")
.option("hoodie.clustering.schedule.inline", "true")
.option("hoodie.clustering.inline.max.commits", "4")  // 控制 inline schedule 频率

// 模式 B：writer 内部异步 clustering service
.option("hoodie.clustering.async.enabled", "true")
.option("hoodie.clustering.async.max.commits", "4")  // 控制 async clustering 频率

// 外部作业执行已调度的 Clustering Plan
spark-submit --class org.apache.hudi.utilities.HoodieClusteringJob \
  hudi-utilities-bundle.jar \
  --base-path /path/to/table \
  --mode execute \
  --parallelism 100
```

**适用场景：**
- 流式写入场景
- 高频更新工作负载
- **生产环境推荐**

> 说明：模式 A 和模式 B 不要混为一谈。`schedule.inline=true` 只是让普通 writer 负责生成 `.replacecommit.requested`，真正执行仍需要外部 Clustering Job；`async.enabled=true` 则表示 writer 进程内启动异步 clustering service。具体选择取决于资源隔离、作业调度和延迟要求。

## 4. Clustering 策略

### 4.1 默认 Plan Strategy：SparkSizeBasedClusteringPlanStrategy

**默认计划策略**，基于文件大小选择候选 file slices

**配置：**
```scala
.option("hoodie.clustering.plan.strategy.class",
  "org.apache.hudi.client.clustering.plan.strategy.SparkSizeBasedClusteringPlanStrategy")

// 目标文件大小
.option("hoodie.clustering.plan.strategy.target.file.max.bytes", "134217728")  // 128MB

// 小文件大小阈值
.option("hoodie.clustering.plan.strategy.small.file.limit", "67108864")  // 64MB
```

**特点：**
- 默认选择 base file 小于 `small.file.limit` 的 file slices
- 按 `max.bytes.per.group` 组织 clustering group
- 每个 group 按 `target.file.max.bytes` 估算输出 file groups 数量
- 适合小文件治理和常规布局优化

### 4.2 分区过滤能力

分区过滤不是单独的策略类，而是 Plan Strategy 的候选分区过滤能力。

**配置：**
```scala
// 正则过滤分区
.option("hoodie.clustering.plan.strategy.partition.regex.pattern", ".*")

// 显式指定分区列表
.option("hoodie.clustering.plan.strategy.partition.selected", "2023-12-01,2023-12-02")

// 使用分区过滤模式
.option("hoodie.clustering.plan.partition.filter.mode", "RECENT_DAYS")
.option("hoodie.clustering.plan.strategy.daybased.lookback.partitions", "7")
```

**常见 filter mode：**
- `NONE`：默认值，不按最近分区过滤
- `RECENT_DAYS`：选择最近 N 个分区，配合 `daybased.lookback.partitions`
- `SELECTED_PARTITIONS`：按 begin/end 分区范围过滤
- `DAY_ROLLING`：按小时滚动选择部分分区

**特点：**
- 可指定特定分区或最近分区进行聚类
- 适合按日期等分区的增量优化

### 4.3 自定义策略

**实现自定义聚类逻辑：**
```scala
// 实际实现需要继承 Hudi 对应引擎的 ClusteringPlanStrategy/PartitionAwareClusteringPlanStrategy
// 并实现 generateClusteringPlan(...) 或 buildClusteringGroupsForPartition(...) 等方法。
// 下面只展示配置方式：
.option("hoodie.clustering.plan.strategy.class", 
  "com.company.CustomClusteringStrategy")
```

### 4.4 Execution Strategy（执行策略）

Plan Strategy 负责选择哪些 file slices 进入 Clustering Plan；Execution Strategy 负责如何读取、排序和写出新文件。

**默认配置：**
```scala
.option("hoodie.clustering.execution.strategy.class",
  "org.apache.hudi.client.clustering.run.strategy.SparkSortAndSizeExecutionStrategy")
```

**说明：**
- 默认执行策略会根据 `hoodie.clustering.plan.strategy.sort.columns` 排序
- 如果未配置 `sort.columns`，仍可以按 size-based 方式合并小文件
- 输出文件数量主要受 `target.file.max.bytes` 和 `max.bytes.per.group` 影响

### 4.5 Layout Optimization（布局优化）

Hudi 1.0.x 还提供更高级的数据布局优化策略：

```scala
.option("hoodie.layout.optimize.strategy", "LINEAR")   // 默认
// 可选：ZORDER、HILBERT
.option("hoodie.layout.optimize.strategy", "ZORDER")
```

**适用场景：**
- 多列过滤明显，单纯线性排序无法兼顾多个维度
- 查询引擎能够利用列统计和数据跳过
- 可以接受更高的排序/采样/计算成本

## 5. 配置参数详解

### 5.1 核心配置

| 参数 | 说明 | 默认值 | 推荐值 |
|------|------|--------|--------|
| `hoodie.clustering.inline` | 启用内联聚类 | false | false（生产） |
| `hoodie.clustering.schedule.inline` | 内联调度聚类 | false | true |
| `hoodie.clustering.inline.max.commits` | 触发聚类的提交数 | 4 | 4-10 |
| `hoodie.clustering.async.enabled` | 启用 writer 内部异步 clustering service | false | 按场景启用 |
| `hoodie.clustering.async.max.commits` | 异步 clustering 触发提交数 | 4 | 4-10 |
| `hoodie.clustering.plan.strategy.target.file.max.bytes` | 目标文件大小 | 1GB | 128-512MB |
| `hoodie.clustering.plan.strategy.small.file.limit` | 小文件阈值 | 300MB | 64-128MB |

### 5.2 Clustering Key 配置

| 参数 | 说明 | 示例 |
|------|------|------|
| `hoodie.clustering.plan.strategy.sort.columns` | 排序字段 | "date,hour" |
| `hoodie.clustering.plan.partition.filter.mode` | 分区过滤模式 | "RECENT_DAYS" |
| `hoodie.clustering.plan.strategy.daybased.lookback.partitions` | 最近分区回溯数，通常配合 RECENT_DAYS | 2 |
| `hoodie.clustering.plan.strategy.daybased.skipfromlatest.partitions` | 从最新分区跳过的数量 | 0 |
| `hoodie.clustering.plan.strategy.cluster.begin.partition` | 范围过滤起始分区 | "2023-12-01" |
| `hoodie.clustering.plan.strategy.cluster.end.partition` | 范围过滤结束分区 | "2023-12-31" |

### 5.3 性能配置

| 参数 | 说明 | 默认值 |
|------|------|--------|
| `hoodie.clustering.max.parallelism` | Clustering 作业最大并行 job 数 | 15 |
| `hoodie.clustering.group.read.parallelism` | Spark 读取 clustering group 的最大并行度 | 20 |
| `hoodie.clustering.plan.strategy.max.num.groups` | 每个 Clustering Plan 最大 group 数 | 30 |
| `hoodie.clustering.plan.strategy.max.bytes.per.group` | 每个 clustering group 最大输入数据量 | 2GB |
| `hoodie.clustering.updates.strategy` | 更新策略 | SparkRejectUpdateStrategy |
| `hoodie.clustering.rollback.pending.replacecommit.on.conflict` | 冲突时是否回滚 pending replacecommit | false |

### 5.4 生产环境推荐配置

```scala
df.write.format("hudi")
  .option("hoodie.table.name", tableName)
  
  // 异步 Clustering
  .option("hoodie.clustering.inline", "false")
  .option("hoodie.clustering.schedule.inline", "true")
  .option("hoodie.clustering.inline.max.commits", "5")
  
  // Clustering 策略
  .option("hoodie.clustering.plan.strategy.target.file.max.bytes", "134217728")  // 128MB
  .option("hoodie.clustering.plan.strategy.small.file.limit", "67108864")  // 64MB
  
  // Clustering Key（根据查询模式选择）
  .option("hoodie.clustering.plan.strategy.sort.columns", "event_time,user_id")
  
  // 性能调优
  .option("hoodie.clustering.max.parallelism", "15")
  
  .save(path)
```

如果希望 writer 自身启动异步服务，而不是由外部作业执行，可替换为：

```scala
.option("hoodie.clustering.inline", "false")
.option("hoodie.clustering.schedule.inline", "false")
.option("hoodie.clustering.async.enabled", "true")
.option("hoodie.clustering.async.max.commits", "5")
```

## 6. 运行异步 Clustering

### 6.1 使用 Spark 运行

```bash
# 方式 1: 调度 + 执行 Clustering
spark-submit \
  --class org.apache.hudi.utilities.HoodieClusteringJob \
  --master yarn \
  --deploy-mode cluster \
  hudi-utilities-bundle.jar \
  --base-path s3://bucket/table_path \
  --table-name my_table \
  --mode scheduleAndExecute \
  --parallelism 200

# 方式 2: 仅调度 Clustering
spark-submit \
  --class org.apache.hudi.utilities.HoodieClusteringJob \
  hudi-utilities-bundle.jar \
  --base-path s3://bucket/table_path \
  --table-name my_table \
  --mode schedule

# 方式 3: 仅执行已调度的 Clustering
spark-submit \
  --class org.apache.hudi.utilities.HoodieClusteringJob \
  hudi-utilities-bundle.jar \
  --base-path s3://bucket/table_path \
  --table-name my_table \
  --mode execute \
  --clustering-instant-time 20231201120000
```

## 7. Clustering 监控与调优

### 7.1 监控指标

**关键指标：**
- 小文件数量和占比
- 平均文件大小
- Clustering 执行频率
- Clustering 作业执行时间
- 查询性能改善
- pending / inflight replacecommit 数量
- Clustering 失败和 rollback 次数

**查看 Clustering 状态：**
```bash
# 使用 Hudi CLI
./hudi-cli.sh
> connect --path s3://bucket/table_path
> clustering show
> clustering show --instant 20231201120000
```

**Timeline 状态：**
```
.replacecommit.requested  → 已生成 Clustering Plan，等待执行
.replacecommit.inflight   → 正在执行 Clustering
.replacecommit            → 执行完成并提交
```

### 7.2 性能调优

#### 7.2.1 文件大小调优

```scala
// 根据查询模式调整目标文件大小
// 频繁全表扫描 → 较大文件 (256-512MB)
.option("hoodie.clustering.plan.strategy.target.file.max.bytes", "268435456")  // 256MB

// 频繁点查询 → 较小文件 (64-128MB)
.option("hoodie.clustering.plan.strategy.target.file.max.bytes", "134217728")  // 128MB
```

#### 7.2.2 并行度调优

```scala
// 根据集群规模、待聚类分区数和资源余量调整
.option("hoodie.clustering.max.parallelism", "15")
.option("hoodie.clustering.group.read.parallelism", "20")

// 粗略估算输出文件数：总输入数据量 / target.file.max.bytes
// 但 max.parallelism 不是普通 Spark shuffle partition 数，不建议直接套固定公式
```

#### 7.2.3 触发频率调优

```scala
// 高频写入场景 → 较高阈值
.option("hoodie.clustering.inline.max.commits", "10")

// 低频写入场景 → 较低阈值
.option("hoodie.clustering.inline.max.commits", "3")
```

### 7.3 故障排查

#### 问题 1: Clustering 长时间未完成

**原因：**
- 数据量过大
- 并行度不足
- 资源不足
- 单个 clustering group 过大
- 与写入、compaction 等服务竞争资源

**解决：**
```bash
# 1. 检查 Clustering 状态
clustering show --instant <instant_time>

# 2. 增加并行度重试
spark-submit ... --parallelism 500
```

```scala
// 3. 分批处理大分区
.option("hoodie.clustering.plan.strategy.partition.selected", "2023-12-01")

// 4. 降低单个 group 数据量
.option("hoodie.clustering.plan.strategy.max.bytes.per.group", "1073741824")  // 1GB
```

#### 问题 2: Clustering 后查询性能无改善

**原因：**
- Clustering Key 选择不当
- 查询模式与 Clustering 策略不匹配
- 查询引擎没有利用 Parquet 统计信息或谓词下推
- Metadata Table / column stats / data skipping 未生效

**解决：**
```scala
// 重新评估 Clustering Key
// 分析查询日志，找出高频过滤字段
.option("hoodie.clustering.plan.strategy.sort.columns", "correct_column")
```

#### 问题 3: 小文件问题未解决

**原因：**
- 小文件阈值设置过小
- Clustering 频率过低

**解决：**
```scala
// 调整小文件阈值
.option("hoodie.clustering.plan.strategy.small.file.limit", "134217728")  // 提高到 128MB

// 增加触发频率
.option("hoodie.clustering.inline.max.commits", "3")
```

#### 问题 4: 写入遇到 pending clustering 冲突

**原因：**
- 默认 `SparkRejectUpdateStrategy` 会拒绝更新正在 pending clustering 的 file groups
- 高频 upsert 和频繁 clustering 同时运行，冲突概率升高

**解决：**
```scala
// 方案 1：降低 clustering 频率，减少 pending replacecommit 滞留时间
.option("hoodie.clustering.inline.max.commits", "10")

// 方案 2：允许冲突时回滚 pending replacecommit（需谨慎评估）
.option("hoodie.clustering.rollback.pending.replacecommit.on.conflict", "true")

// 方案 3：评估是否使用 AllowUpdateStrategy，需结合并发控制和一致性要求
.option("hoodie.clustering.updates.strategy",
  "org.apache.hudi.client.clustering.update.strategy.SparkAllowUpdateStrategy")
```

## 8. Clustering 最佳实践

### 8.1 Clustering Key 选择

✅ **推荐做法：**

1. **分析查询模式**
   ```sql
   -- 高频过滤查询
   SELECT * FROM orders WHERE order_date = '2023-12-01'
   → Clustering Key: order_date
   
   -- 范围查询
   SELECT * FROM events WHERE event_time BETWEEN t1 AND t2
   → Clustering Key: event_time
   
   -- Join 查询
   SELECT * FROM orders o JOIN customers c ON o.customer_id = c.id
   → Clustering Key: customer_id
   ```

2. **复合 Clustering Key 顺序**
   ```scala
   // 优先匹配查询谓词前缀和范围过滤，而不是机械按基数排序
   .option("hoodie.clustering.plan.strategy.sort.columns", 
     "event_date,event_time,user_id")
   
   // 如果主要按 user_id 点查，再考虑把 user_id 放到前面
   .option("hoodie.clustering.plan.strategy.sort.columns", 
     "user_id,event_time")
   ```

3. **避免低基数字段**
   ```scala
   // 通常不推荐：单独按性别这类低基数字段排序，裁剪效果有限
   .option("hoodie.clustering.plan.strategy.sort.columns", "gender")
   
   // 更常见：结合高频过滤字段、时间范围或高选择性字段
   .option("hoodie.clustering.plan.strategy.sort.columns", "user_id")
   ```

### 8.2 执行策略

✅ **推荐做法：**

1. **生产环境使用异步 Clustering**
   ```scala
   .option("hoodie.clustering.inline", "false")
   .option("hoodie.clustering.schedule.inline", "true")
   ```

2. **定期运行 Clustering**
   - 每天运行一次（批处理场景）
   - 每 4-10 次提交触发一次（流式场景）

3. **分区优化**
   ```scala
   // 仅对最近 N 天分区进行 Clustering
   .option("hoodie.clustering.plan.partition.filter.mode", "RECENT_DAYS")
   .option("hoodie.clustering.plan.strategy.daybased.lookback.partitions", "7")
   ```

4. **监控和告警**
   - 小文件数量 > 阈值 → 告警
   - Clustering 延迟 > 阈值 → 告警
   - pending replacecommit 长时间未完成 → 告警
   - 查询性能下降 → 触发 Clustering

5. **配合数据跳过**
   - 确认查询谓词能下推到 Parquet
   - 对常用过滤列收集和使用列统计
   - Clustering 排序列应匹配高频过滤条件

### 8.3 避免的陷阱

❌ **常见错误：**

1. **内联 Clustering 用于高频写入**
   ```scala
   // 错误：阻塞写入
   .option("hoodie.clustering.inline", "true")
   ```

2. **把 Clustering Key 当成必填项**
   ```scala
   // 未配置 sort.columns 时仍可合并小文件
   // 但无法获得按列排序带来的额外数据跳过和压缩收益
   ```

3. **文件大小设置不当**
   ```scala
   // 错误：目标文件过大
   .option("hoodie.clustering.plan.strategy.target.file.max.bytes", "2147483648")  // 2GB
   
   // 推荐：128-512MB
   .option("hoodie.clustering.plan.strategy.target.file.max.bytes", "134217728")  // 128MB
   ```

4. **忽略 Clustering 失败**
   - 未监控 Clustering 状态
   - 不处理失败的 Clustering 任务

5. **过度频繁 Clustering**
   - 频率过高会增加写放大和资源争抢
   - 高频 upsert 场景下更容易与 pending clustering 冲突

## 9. Clustering vs 其他特性

### 9.1 Clustering vs Compaction

| 维度 | Clustering | Compaction |
|------|-----------|-----------|
| **作用** | 重组 file groups 和文件布局 | 将 MOR 的 log files 合并进 base file |
| **目标** | 优化文件大小、排序和数据局部性 | 降低 MOR 读放大 |
| **适用表** | COW 和 MOR | 仅 MOR |
| **优化目标** | 查询裁剪、压缩和小文件治理 | 查询延迟和 log 文件数量 |
| **数据变更** | 通过 replace commit 重写 file groups | 生成新的 base file 版本 |

### 9.2 Clustering vs Partitioning

| 维度 | Clustering | Partitioning |
|------|-----------|--------------|
| **粒度** | file group 重写、文件大小调整、文件内/组内排序 | 目录级分隔 |
| **灵活性** | 可动态调整 | 创建后固定 |
| **查询优化** | 文件裁剪、数据跳过、范围扫描 | 分区裁剪 |
| **维护成本** | 需定期运行 | 一次配置 |

**组合使用：**
```scala
// 分区 + Clustering 组合优化
.option("hoodie.datasource.write.partitionpath.field", "date")  // 按日期分区
.option("hoodie.clustering.plan.strategy.sort.columns", "event_time,user_id")  // 分区内聚类
```

## 10. 实际应用场景

### 场景 1: 事件日志表优化

**问题：** 高频写入导致大量小文件

**解决方案：**
```scala
df.write.format("hudi")
  .option("hoodie.datasource.write.partitionpath.field", "event_date")
  .option("hoodie.clustering.plan.strategy.sort.columns", "event_time,user_id")
  .option("hoodie.clustering.inline", "false")
  .option("hoodie.clustering.schedule.inline", "true")
  .option("hoodie.clustering.inline.max.commits", "10")
  .save(path)

// 每天运行 Clustering
# crontab: 0 2 * * * /path/to/run_clustering.sh
```

**效果：**
- 小文件数量可能显著下降
- 查询时间改善幅度取决于过滤条件、文件统计和执行引擎

### 场景 2: 用户行为表优化

**问题：** 按用户 ID 查询很慢

**解决方案：**
```scala
.option("hoodie.clustering.plan.strategy.sort.columns", "user_id,timestamp")
// 在被重写的 clustering group 内按 user_id 排序，使相近 user_id 的记录更集中
```

**效果：**
- 用户维度查询在数据跳过生效时可能明显改善

### 场景 3: 时序数据优化

**问题：** 时间范围查询需要扫描大量文件

**解决方案：**
```scala
.option("hoodie.datasource.write.partitionpath.field", "date")
.option("hoodie.clustering.plan.strategy.sort.columns", "timestamp")
.option("hoodie.clustering.plan.strategy.target.file.max.bytes", "268435456")  // 256MB
```

**效果：**
- 范围查询可能减少大量文件扫描

## 11. 常见问题 (FAQ)

### Q1: Clustering 会影响写入吗？

**A:**
- **Inline Clustering：** 会阻塞写入，增加延迟
- **Schedule Inline + 外部执行：** 写入只负责调度 plan，延迟影响较小，但仍有少量 planning 开销
- **Async Clustering Service：** 在 writer 内部后台执行，不阻塞主写入流程，但会共享 writer 资源

### Q2: 多久运行一次 Clustering？

**A:**
- **实时场景：** 每 5-10 次提交或每小时
- **批处理：** 每天或每周
- **关键指标：** 小文件数量 > 总文件 20%
- **资源维度：** 避免在写入高峰、compaction 高峰和查询高峰同时运行

### Q3: Clustering Key 可以修改吗？

**A:** 可以。修改 `sort.columns` 后只影响后续 Clustering Plan；如果希望历史文件也按新列布局，需要逐步或全量重新 Clustering：
```scala
// 更改 Clustering Key
.option("hoodie.clustering.plan.strategy.sort.columns", "new_column")

// 触发全表 Clustering
spark-submit ... --mode scheduleAndExecute
```

### Q4: Clustering 和 Compaction 可以同时运行吗？

**A:** 技术上可以调度，但生产中建议错开时间或配置并发控制/锁。Hudi 会避开 pending compaction/clustering 的 file groups，但同表 table services 同时运行仍会竞争资源：
```bash
# 早上运行 Compaction
0 2 * * * /path/to/run_compaction.sh

# 晚上运行 Clustering
0 22 * * * /path/to/run_clustering.sh
```

### Q5: COW 表需要 Clustering 吗？

**A:** 视情况而定。COW 表如果存在小文件、查询依赖范围过滤/数据跳过，Clustering 很有价值；如果文件大小健康且查询收益不明显，则不必频繁运行。
