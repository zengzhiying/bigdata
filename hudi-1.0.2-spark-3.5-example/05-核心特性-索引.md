# Hudi 核心特性：索引 (Indexing)

## 概述

索引（Index）是 Apache Hudi 的核心组件之一，用于快速定位记录所在的文件位置。索引显著提升了 upsert 操作的性能，是 Hudi 实现高效更新的关键。

### 核心作用

- **快速查找**：将 Record Key 定位到 Hudi 文件组（file group/file id）
- **加速 Upsert/Delete**：减少为了定位旧记录而扫描的业务数据文件
- **控制重复**：配合写入操作类型、precombine 和索引范围，避免相同 Record Key 被写成多份
- **正确处理分区变更**：GLOBAL 或 Record Index 能发现记录从旧分区移动到新分区
- **性能优化**：降低索引查找阶段的 IO、shuffle 和 join 成本；真实复杂度取决于索引类型与数据分布

> 注意：设置 `hoodie.datasource.write.recordkey.field` 只是定义主键字段，不等于自动创建数据库式 B-Tree/Hash 主键索引。Spark 写入默认会使用 `SIMPLE` 索引做 writer-side lookup，但它不是持久化的主键位置索引。

## 1. 索引工作原理

### 1.1 无索引的问题

```
没有索引的 Upsert:
1. 收到更新: user_id = "U001"
2. 扫描所有文件: file1, file2, file3, ..., fileN
3. 逐个读取并查找 "U001"
4. 找到后更新并写回
⚠️  时间复杂度: O(n) - 非常慢!
```

### 1.2 有索引的优化

```
有索引的 Upsert:
1. 收到更新: user_id = "U001"
2. 索引查找: "U001" → file group / file id
3. 只读取命中的文件组进行合并
4. COW 重写命中文件组，MOR 追加 log 后由 compaction 合并
✓ 索引阶段避免扫描大量无关文件；最终写放大仍取决于命中文件组数量和文件大小
```

### 1.3 索引操作流程

```
Write Operation
  ↓
Record Key Extraction
  ↓
Index Lookup: Which file group contains this key?
  ├─ Found → tag record with current location
  └─ Not Found → treat as insert
  ↓
Write/Merge
  ├─ COW: merge and rewrite affected base files
  └─ MOR: write delta log, later compact if needed
  ↓
Update metadata/index state if the chosen index requires it
  ↓
Complete
```

### 1.4 主键、写入模式与索引的关系

| 概念 | 作用 | 容易混淆的点 |
|------|------|--------------|
| `recordkey.field` | 定义记录身份 | 不是持久化主键索引 |
| `precombine.field` | 同一批次或同一 key 多条记录时选择最新记录 | 不是查找索引 |
| `operation=upsert/delete` | 需要查找旧记录位置 | 通常触发 index lookup |
| `operation=insert/bulk_insert` | 主要按新增写入 | 通常不做完整旧数据查找，可能不适合有重复 key 的输入 |
| `hoodie.index.type` | 决定如何定位旧记录 | 默认不一定适合大分区或高频更新 |

对于 COW 表，索引只负责“找到哪些 file group 受影响”。真正更新时，Hudi 仍需要读取并重写命中的 base file；索引无法消除 COW 的文件重写成本。

## 2. 索引类型

### 2.1 索引类型总览

| 索引类型 | 索引状态/存储 | 查找范围 | 主要成本 | 使用场景 |
|---------|---------------|----------|----------|---------|
| **SIMPLE** | 不持久化索引；Spark 读取已有 key 后 join | 目标分区 | 读取分区内 base files 的 key + shuffle/join | 小表、小分区、开发测试 |
| **BLOOM** | 每个数据文件携带 Bloom Filter/范围信息 | 目标分区 | 读取 Bloom 元信息；候选文件再读 key 精确确认 | 中大型表，分区稳定 |
| **GLOBAL_SIMPLE** | 不持久化索引；Spark 全表 key join | 全表 | 读取全表 base files 的 key + shuffle/join | 小表且分区可能变化 |
| **GLOBAL_BLOOM** | Bloom Filter/范围信息 | 全表 | 全表文件级裁剪 + 候选文件确认 | 中大型表且分区可能变化 |
| **BUCKET** | 按 hash 映射到 bucket/file group | 通常目标分区 | bucket 规划、热点与扩容成本 | 大规模 upsert，key 分布稳定 |
| **RECORD_INDEX** | Metadata Table 中维护 key → location | 全表（Hudi 1.0.2） | 维护 metadata table 与初始化成本 | 大表、高频 upsert/delete、索引查找瓶颈 |
| **HBASE** | 外部 HBase | 全表 | 外部服务维护与 RPC | 历史超大规模方案，需维护 HBase |
| **INMEMORY** | 内存 | 全表 | 内存，不持久 | 测试用途 |

### 2.2 LOCAL vs GLOBAL 索引

#### LOCAL 索引（分区感知）

**类型：** SIMPLE, BLOOM, BUCKET（按配置和使用方式通常是分区内定位）

**特点：**
- ✅ 假设记录不会改变分区
- ✅ 仅在目标分区内查找
- ✅ 性能更快
- ❌ 无法处理分区变更（会产生重复）

**适用场景：**
```scala
// 分区字段不可变
.option("hoodie.datasource.write.partitionpath.field", "signup_date")  // 日期不会改变
.option("hoodie.datasource.write.partitionpath.field", "country_code") // 国家不变
```

#### GLOBAL 索引（分区无关）

**类型：** GLOBAL_SIMPLE, GLOBAL_BLOOM, RECORD_INDEX, HBASE

**特点：**
- ✅ 记录可以在分区间移动
- ✅ 搜索所有分区
- ✅ 正确处理分区变更
- ❌ 性能相对较慢

**适用场景：**
```scala
// 分区字段可变
.option("hoodie.datasource.write.partitionpath.field", "city")     // 用户可能搬家
.option("hoodie.datasource.write.partitionpath.field", "status")   // 状态会改变
```

### 2.3 默认行为与单分区 COW 写入

在 Spark Datasource 写入中，如果没有显式设置 `hoodie.index.type`，常见默认行为是使用 `SIMPLE`。这意味着“设置主键后默认有 writer-side lookup”，但不是数据库式持久化主键索引。

单个分区 COW `upsert` 的典型过程：

```
incoming records 只落到 partition=p1
  ↓
SIMPLE 只在 p1 内查找旧记录
  ↓
读取 p1 下相关 base files 的 record key/location
  ↓
与 incoming keys 做 join，判断哪些 key 已存在
  ↓
只重写命中的 file groups，而不是重写 p1 下所有文件
```

因此要区分两件事：

- **索引查找阶段**：默认 `SIMPLE` 可能读取该分区下所有 base files 的 key。
- **COW 写入阶段**：只重写包含被更新记录的 file groups，不会因为查找扫描了分区就重写整个分区。

如果这个分区非常大、文件很多，即使只写少量更新，`SIMPLE` 的索引查找也可能成为瓶颈。

## 3. SIMPLE 索引

### 3.1 特点

- **存储**：没有持久化的 key → location 索引，运行时读取旧文件 key 构建查找关系
- **实现**：使用 Spark Join 将 incoming keys 和已有 keys 关联
- **查找范围**：LOCAL SIMPLE 只查 incoming records 涉及的分区；GLOBAL_SIMPLE 查全表
- **无外部依赖**：配置简单，但成本随分区文件数和历史 key 数增长
- **适合场景**：小表、小分区、低频 upsert、开发测试

### 3.2 配置示例

```scala
df.write.format("hudi")
  .option("hoodie.index.type", "SIMPLE")  // 默认值
  .option("hoodie.simple.index.parallelism", "100")
  .save(basePath)
```

### 3.3 查找细节

`SIMPLE` 的核心不是“有一个内存 HashMap 一直保存主键”，而是在每次写入的索引阶段读取受影响分区的已有 record keys，然后与本次 incoming records 做 join。

```
LOCAL SIMPLE:
  incoming partitions = {p1, p2}
  -> 读取 p1/p2 下 base files 的 keys
  -> incoming keys join existing keys

GLOBAL_SIMPLE:
  不信任 incoming partition
  -> 读取全表 base files 的 keys
  -> incoming keys join existing keys
```

这也是为什么 `SIMPLE` 在“单个超大分区 + 少量 upsert”场景下表现可能很差：它写得少，但为了定位旧记录读得多。

### 3.4 优缺点

| 优点 | 缺点 |
|-----|------|
| ✅ 无外部依赖 | ❌ 内存占用大 |
| ✅ 配置简单 | ❌ 大数据集性能差 |
| ✅ 适合快速开发 | ❌ 仅分区感知 |

## 4. BLOOM 索引（推荐）

### 4.1 布隆过滤器原理

布隆过滤器是一种**概率型数据结构**：

```
特性:
• 确定性否定: "记录一定不在此文件" (100% 准确)
• 概率性肯定: "记录可能在此文件" (可能误报)
• 空间高效: 每个文件仅需几 KB
• 查找快速: O(1) 时间复杂度
```

### 4.2 工作流程

```
1. 写入时: 为每个文件生成 Bloom Filter 和 key range 等元信息
   File1.parquet + BloomFilter(keys in File1)

2. 查找时:
   需要查找 key = "U001"

   先做文件级裁剪:
   ├─ key range 不匹配 → 跳过
   ├─ Bloom Filter 表示 definitely NOT in File1 → 跳过
   └─ Bloom Filter 表示 MIGHT be in File1 → 候选文件

3. 对候选文件做精确确认:
   读取候选文件中的 record key 字段
   ├─ 找到 key → tag 到该 file group
   └─ 没找到 key → Bloom 误报，按 insert 处理或继续检查其他候选文件
```

### 4.3 配置示例

```scala
df.write.format("hudi")
  .option("hoodie.index.type", "BLOOM")
  .option("hoodie.bloom.index.filter.type", "DYNAMIC_V0")  // 推荐
  .option("hoodie.index.bloom.fpp", "0.000001")            // 误报率
  .option("hoodie.bloom.index.parallelism", "200")
  .option("hoodie.bloom.index.prune.by.ranges", "true")    // 范围裁剪
  .option("hoodie.bloom.index.use.caching", "true")        // 缓存
  .save(basePath)
```

### 4.4 关键配置参数

| 参数 | 说明 | 默认值 | 推荐值 |
|------|------|--------|--------|
| `hoodie.bloom.index.filter.type` | 过滤器类型 | DYNAMIC_V0 | DYNAMIC_V0 |
| `hoodie.index.bloom.fpp` | 误报率 | 0.000001 | 0.000001 |
| `hoodie.bloom.index.parallelism` | 并行度 | 0 (自动) | 根据集群调整 |
| `hoodie.bloom.index.prune.by.ranges` | 范围裁剪 | true | true |

### 4.5 误报率 (FPP) 调优

```scala
// 低误报率 (推荐生产环境)
.option("hoodie.index.bloom.fpp", "0.000001")  // 0.0001%
// 优点: 很少误读文件
// 缺点: Bloom Filter 稍大

// 高误报率 (不推荐)
.option("hoodie.index.bloom.fpp", "0.01")      // 1%
// 优点: Bloom Filter 更小
// 缺点: 频繁误读文件，性能下降
```

### 4.6 候选文件确认与退化场景

`BLOOM` 不是把候选文件退化成完整的 `SIMPLE` join。它先通过 Bloom Filter/range 把文件集合缩小，然后只对候选文件读取 key 做精确匹配。区别如下：

| 阶段 | SIMPLE | BLOOM |
|------|--------|-------|
| 初始文件集合 | 目标分区全部 base files | 被 Bloom/range 命中的候选 files |
| 旧数据读取 | 读取全部相关文件的 keys | 只读取候选文件的 keys 做确认 |
| 是否误报 | 无 Bloom 误报 | 有误报，需要二次确认 |
| 最坏情况 | 大分区读很多 keys | 候选文件接近全部文件，成本接近 SIMPLE |

容易退化的情况：

- record key 完全随机，range pruning 几乎不起作用。
- 一批更新 key 覆盖大量文件，候选文件集合很大。
- 小文件过多，每个文件都要读取 Bloom 元信息并可能被命中。
- Bloom FPP 设置过高，误报增多。
- 使用 `GLOBAL_BLOOM` 且分区很多，全表文件级裁剪成本明显增加。

如果确认 `BLOOM` 退化，优先考虑减少小文件、优化分区/文件布局；大规模高频 upsert 可以评估 `BUCKET` 或 `RECORD_INDEX`。

### 4.7 优缺点

| 优点 | 缺点 |
|-----|------|
| ✅ 可跳过大量无关文件 | ❌ 可能误报，需要精确确认 |
| ✅ 空间高效 | ❌ key 随机或更新分散时会退化 |
| ✅ 无外部依赖 | ❌ LOCAL BLOOM 无法自动处理分区变更 |
| ✅ 中大型表通用选择 | ❌ 小文件过多时元信息和候选检查成本高 |

## 5. GLOBAL 索引

### 5.1 GLOBAL_SIMPLE 索引

```scala
df.write.format("hudi")
  .option("hoodie.index.type", "GLOBAL_SIMPLE")
  .option("hoodie.global.simple.index.parallelism", "100")
  .save(basePath)
```

**特点：**
- 搜索所有分区
- 支持分区变更
- 性能比 LOCAL 慢

### 5.2 GLOBAL_BLOOM 索引（推荐）

```scala
df.write.format("hudi")
  .option("hoodie.index.type", "GLOBAL_BLOOM")
  .option("hoodie.bloom.index.parallelism", "200")
  .save(basePath)
```

**特点：**
- Bloom Filter + 全局搜索
- 最佳的通用选择
- 支持分区变更

### 5.3 分区变更示例

```scala
// 初始: 用户在 San Francisco
("U001", "Alice", "San Francisco", 1000L)

// 更新: 用户搬到 New York
("U001", "Alice", "New York", 2000L)

// LOCAL 索引结果:
// ❌ 两条记录: SF 和 NY 各一条 (重复!)

// GLOBAL 索引结果:
// ✅ 一条记录: 仅在 NY (正确!)
```

## 6. BUCKET 索引

### 6.1 特点

`BUCKET` 索引按 record key 或指定 hash 字段把记录映射到固定 bucket/file group。写入时可以直接根据 key 计算目标 bucket，避免像 `SIMPLE` 一样扫描分区，也避免 `BLOOM` 对大量候选文件做确认。

```
record key = U001
  ↓ hash(U001) % numBuckets
bucket id = 42
  ↓
定位到 partition 下的 bucket/file group
```

### 6.2 配置示例

```scala
df.write.format("hudi")
  .option("hoodie.index.type", "BUCKET")
  .option("hoodie.index.bucket.engine", "SIMPLE")
  .option("hoodie.bucket.index.num.buckets", "256")
  // 默认使用 record key 做 hash；也可以显式指定 hash 字段
  // .option("hoodie.bucket.index.hash.field", "user_id")
  .save(basePath)
```

### 6.3 适用与风险

✅ **适合：**
- 大分区、高频 upsert，默认 `SIMPLE`/`BLOOM` 查找成本高
- record key 分布均匀，能接受预先规划 bucket 数
- 希望写入定位稳定，减少索引查找 IO

❌ **谨慎：**
- bucket 数过少会造成大文件和热点，过多会造成小文件
- 数据增长不可预测时，固定 bucket 规划难度较高
- key 严重倾斜时，热点 bucket 仍然会拖慢写入

## 7. RECORD_INDEX（Metadata Table Record Index）

### 7.1 特点

`RECORD_INDEX` 把 `record key -> record location` 维护在 Hudi Metadata Table 中。它是持久化的记录级位置索引，目标是避免 upsert/delete 时扫描业务数据文件来找 key。

```
SIMPLE:
  incoming key -> 读取业务分区已有 keys -> join -> file group

BLOOM:
  incoming key -> Bloom/range 裁剪 -> 读取候选文件 keys 确认 -> file group

RECORD_INDEX:
  incoming key -> 查 metadata table 的 record_index -> file group
```

在大表、大分区、随机更新、高频 delete/upsert 场景下，`RECORD_INDEX` 往往比 `SIMPLE` 和退化的 `BLOOM` 更稳定。

### 7.2 Hudi 1.0.2 配置示例

```scala
df.write.format("hudi")
  .option("hoodie.metadata.enable", "true")
  .option("hoodie.metadata.record.index.enable", "true")
  .option("hoodie.index.type", "RECORD_INDEX")
  .option("hoodie.record.index.use.caching", "true")
  .save(basePath)
```

可按表规模调整 record index 文件组数量：

```scala
.option("hoodie.metadata.record.index.min.filegroup.count", "10")
.option("hoodie.metadata.record.index.max.filegroup.count", "10000")
.option("hoodie.metadata.record.index.max.filegroup.size", "1073741824") // 1GB
.option("hoodie.metadata.record.index.growth.factor", "2.0")
```

### 7.3 使用注意

- Hudi 1.0.2 中 `RECORD_INDEX` 是 global 语义，主键按全表唯一来定位。
- 已有大表首次开启需要初始化 metadata record index，一次性成本可能很高。
- 如果 record index 尚未初始化完成，Spark writer 可能 fallback 到 `GLOBAL_SIMPLE` 做 tagging，初期性能不代表最终性能。
- 每次写入都要维护 metadata table，纯 append/insert 场景可能收益不明显。
- 需要关注 metadata table compaction、cleaning、初始化进度和失败恢复。

### 7.4 适用场景

✅ **优先考虑：**
- TB/PB 级表，高频 upsert/delete
- 单个分区极大，默认 `SIMPLE` 需要读大量 key
- `BLOOM` 候选文件经常接近全量，裁剪效果差
- 需要全表唯一主键或分区字段可能变化

❌ **不一定适合：**
- 小表、小分区，`SIMPLE` 已足够快
- 主要是 `insert`/`bulk_insert` 的 append-only 表
- 不希望承担 metadata table 维护成本
- 只需要分区内唯一且不想引入 global lookup 语义

## 8. HBASE 索引

### 8.1 特点

- **外部存储**：使用 HBase 存储索引
- **全局索引**：天然支持分区变更
- **高性能**：适合超大规模数据
- **多写入者**：支持并发写入

### 8.2 配置示例

```scala
df.write.format("hudi")
  .option("hoodie.index.type", "HBASE")
  .option("hoodie.index.hbase.zkquorum", "zk1,zk2,zk3")
  .option("hoodie.index.hbase.zkport", "2181")
  .option("hoodie.index.hbase.table", "hudi_index")
  .save(basePath)
```

### 8.3 何时使用

✅ **使用场景：**
- 数据量 > 10TB
- 需要跨作业一致性
- 多个写入者并发
- 对性能要求极高

❌ **不推荐：**
- 小数据集（开销大）
- 不想维护 HBase
- 单写入者场景

## 9. 索引选择决策树

```
写入模式?
    │
    ├─ append-only / bulk_insert 为主
    │     └─ 优先优化分区、文件大小、小文件治理；索引不是主要瓶颈
    │
    └─ upsert/delete 为主
          │
          ├─ 表小或每个分区文件少?
          │     ├─ 分区不变 → SIMPLE
          │     └─ 分区可变 → GLOBAL_SIMPLE / RECORD_INDEX(如果已有 metadata 体系)
          │
          ├─ 中大型表，Bloom 能有效裁剪?
          │     ├─ 分区不变 → BLOOM
          │     └─ 分区可变 → GLOBAL_BLOOM
          │
          ├─ 大分区 + 高频 upsert + key 分布稳定?
          │     └─ BUCKET
          │
          └─ 大表/随机更新/Bloom 退化/需要全表唯一?
                └─ RECORD_INDEX
```

快速判断：

| 场景 | 优先选择 | 说明 |
|------|----------|------|
| 开发测试、小表 | SIMPLE | 默认简单，少维护 |
| 分区稳定，中等规模 upsert | BLOOM | 通用性好，能跳过无关文件 |
| 分区字段会变化 | GLOBAL_BLOOM 或 RECORD_INDEX | 避免旧分区残留重复记录 |
| 单个大分区，文件很多 | BUCKET 或 RECORD_INDEX | 避免每次扫分区 keys |
| 随机更新覆盖大量文件 | RECORD_INDEX | Bloom 候选文件可能很多 |
| key 分布均匀且可规划 bucket | BUCKET | 定位稳定，但 bucket 数要规划 |
| 纯新增写入 | 不必优先强化索引 | 关注 bulk_insert、文件大小、clustering |

## 10. 性能对比

### 10.1 写入性能

下面是相对趋势，不是固定 benchmark。实际耗时取决于文件数、每批更新 key 分布、分区数量、文件大小、集群资源和是否命中 COW 大文件重写。

| 索引 | 索引查找趋势 | 最容易慢在哪里 |
|------|--------------|----------------|
| SIMPLE | 小分区快，大分区线性变慢 | 读取分区内已有 keys + join |
| BLOOM | 裁剪有效时快 | 候选文件过多、误报、小文件多 |
| GLOBAL_SIMPLE | 通常最慢之一 | 全表 keys join |
| GLOBAL_BLOOM | 比 GLOBAL_SIMPLE 好 | 全表文件级裁剪成本 |
| BUCKET | 定位稳定 | bucket 热点、bucket 数规划不当 |
| RECORD_INDEX | 大规模 lookup 通常最稳 | metadata table 维护和初始化 |
| HBASE | lookup 性能好 | 外部 HBase 运维和 RPC |

### 10.2 资源使用

| 索引 | 主要资源消耗 | 备注 |
|------|--------------|------|
| SIMPLE | Spark executor 内存、shuffle、读取 base file keys | 不维护持久索引 |
| BLOOM | 文件 footer/metadata 读取、候选文件 key 确认 | Bloom Filter 存在数据文件中 |
| BUCKET | bucket 文件布局、写入倾斜处理 | 以规划换 lookup 稳定性 |
| RECORD_INDEX | Metadata Table 存储、compaction、初始化 | 持久化 record-level location |
| HBASE | HBase 存储、RegionServer、网络 RPC | 外部系统成本最高 |

## 11. 最佳实践

### 11.1 生产环境推荐配置

```scala
// 中等规模、分区不变、Bloom 裁剪有效
df.write.format("hudi")
  .option("hoodie.index.type", "BLOOM")
  .option("hoodie.bloom.index.filter.type", "DYNAMIC_V0")
  .option("hoodie.index.bloom.fpp", "0.000001")
  .option("hoodie.bloom.index.parallelism", "200")
  .option("hoodie.bloom.index.prune.by.ranges", "true")
  .option("hoodie.bloom.index.use.caching", "true")
  .save(basePath)

// 分区可变，需要跨分区找到旧记录
df.write.format("hudi")
  .option("hoodie.index.type", "GLOBAL_BLOOM")
  .option("hoodie.bloom.index.filter.type", "DYNAMIC_V0")
  .option("hoodie.index.bloom.fpp", "0.000001")
  .option("hoodie.bloom.index.parallelism", "200")
  .option("hoodie.bloom.index.update.partition.path", "true")
  .save(basePath)

// 大分区、高频 upsert，key 分布稳定
df.write.format("hudi")
  .option("hoodie.index.type", "BUCKET")
  .option("hoodie.index.bucket.engine", "SIMPLE")
  .option("hoodie.bucket.index.num.buckets", "256")
  .save(basePath)

// 大表、随机更新、Bloom 退化或需要全表唯一
df.write.format("hudi")
  .option("hoodie.metadata.enable", "true")
  .option("hoodie.metadata.record.index.enable", "true")
  .option("hoodie.index.type", "RECORD_INDEX")
  .save(basePath)
```

### 11.2 不同规模下的最佳实践

| 规模/形态 | 推荐方案 | 优化重点 |
|-----------|----------|----------|
| 小表 `< 100GB` 或分区文件少 | SIMPLE | 保持简单，先验证业务语义 |
| 中等表 `100GB - 数 TB` | BLOOM / GLOBAL_BLOOM | 文件大小、Bloom 裁剪、并行度 |
| 大表、分区稳定、upsert 频繁 | BUCKET 或 RECORD_INDEX | 避免分区级扫描，控制写放大 |
| 大表、随机更新、跨分区变更 | RECORD_INDEX | metadata table 初始化与维护 |
| 超大表、多租户或历史 HBase 体系 | RECORD_INDEX 或 HBASE | 优先内置 metadata，HBase 需考虑运维成本 |
| append-only | bulk_insert + 文件治理 | 索引不是首要瓶颈 |

### 11.3 索引最佳实践

✅ **推荐做法：**
1. 先明确主键唯一范围：分区内唯一还是全表唯一。
2. 根据分区字段是否会变化选择 LOCAL、GLOBAL 或 RECORD_INDEX。
3. 对 `upsert` 表监控 index lookup/tagLocation 耗时，不只看总写入耗时。
4. 控制文件大小和小文件数量，避免 Bloom/Simple 都被小文件拖慢。
5. COW 表关注命中文件组数量；索引快不代表重写成本低。
6. 对大表开启 `RECORD_INDEX` 前先在影子表或测试环境完成初始化和回放验证。

❌ **应避免：**
1. 大分区高频 upsert 仍长期使用默认 SIMPLE。
2. 分区可变时使用 LOCAL 索引导致旧分区残留重复记录。
3. 认为 Bloom 命中后不需要读取候选文件确认。
4. 盲目降低 Bloom Filter 大小或调高 FPP。
5. bucket 数随意设置，导致热点 bucket 或大量小文件。
6. 开启 Record Index 后忽略 metadata table compaction 和初始化状态。

## 12. 常见问题 (FAQ)

### Q1: LOCAL 索引产生了重复记录怎么办？

**A:** 原因是使用了 LOCAL 索引但分区字段发生了变化。

**解决方案：**
```scala
// 方案 1: 切换到 GLOBAL 索引
.option("hoodie.index.type", "GLOBAL_BLOOM")

// 方案 2: 手动清理重复
spark.read.format("hudi").load(path)
  .groupBy("_hoodie_record_key")
  .agg(max("updated_ts").as("max_ts"))
  // 保留最新记录
```

### Q2: BLOOM 索引 upsert 还是很慢？

**A:** 重点判断 Bloom 是否有效裁剪了文件：
1. 候选文件数量是否接近目标分区全部文件。
2. record key 是否随机，导致 range pruning 无效。
3. 小文件是否过多，导致 Bloom 元信息和候选检查成本高。
4. FPP 是否被调得过高，误报是否明显增加。
5. COW 是否命中了大量大文件重写，瓶颈可能不在索引。

可选方案：
```scala
// 继续优化 Bloom
.option("hoodie.bloom.index.parallelism", "更高并行度")
.option("hoodie.bloom.index.prune.by.ranges", "true")
.option("hoodie.index.bloom.fpp", "0.000001")

// 如果 Bloom 长期退化，评估
.option("hoodie.index.type", "BUCKET")
// 或
.option("hoodie.index.type", "RECORD_INDEX")
```

### Q3: 设置主键后默认就有高性能索引吗？

**A:** 不是。`recordkey.field` 定义主键，默认 Spark 写入通常使用 `SIMPLE` 做 writer-side lookup。它能保证 upsert 语义，但不维护持久化主键位置索引。大分区下，`SIMPLE` 仍可能读取分区内很多 base files 的 keys。

### Q4: Bloom 对未跳过文件是不是退化成 SIMPLE？

**A:** 机制上不是。Bloom 先裁剪文件，只对候选文件读取 key 精确确认；`SIMPLE` 是读取目标分区全部相关文件 keys 做 join。但如果 Bloom 裁剪很差，候选文件接近全部文件，实际 IO 成本会接近 SIMPLE。

### Q5: Record Index 一定比 Bloom 更好吗？

**A:** 不一定。它通常在大表、随机更新、Bloom 候选文件过多时更稳，但需要维护 metadata table，并有初始化成本。小表或 append-only 表开启后可能收益很小。

### Q6: 如何选择 BLOOM 还是 HBASE 索引？

**A:** 决策因素：
```
选择 BLOOM 当:
• 数据量 < 10TB
• 单个写入者
• 不想维护 HBase

选择 HBASE 当:
• 数据量 > 10TB
• 多个并发写入者
• 需要极致性能
• 可以维护 HBase 集群
```

### Q7: GLOBAL 索引比 LOCAL 慢多少？

**A:** 通常 **2-5 倍**慢，取决于：
- 分区数量
- 数据分布
- 集群资源

**权衡**：牺牲部分性能换取正确性。

### Q8: 可以动态切换索引类型吗？

**A:** 可以，但需要小心：
```scala
// 在新的写入中指定新索引类型
df.write.format("hudi")
  .option("hoodie.index.type", "BLOOM")  // 从 SIMPLE 切换到 BLOOM
  .mode(SaveMode.Append)
  .save(basePath)
```

建议：在测试环境先验证新索引类型的效果。

## 14. 配置参数完整列表

| 参数 | 说明 | 默认值/备注 |
|------|------|-------------|
| `hoodie.index.type` | 索引类型 | 常见 Spark 默认为 SIMPLE；可选 SIMPLE/BLOOM/GLOBAL_BLOOM/BUCKET/RECORD_INDEX 等 |
| `hoodie.simple.index.parallelism` | SIMPLE 索引并行度 | 0 (auto) |
| `hoodie.global.simple.index.parallelism` | GLOBAL_SIMPLE 索引并行度 | 0 (auto) |
| `hoodie.simple.index.use.caching` | SIMPLE 是否缓存输入 RDD | true |

| `hoodie.index.bloom.fpp` | Bloom Filter 误报率 | 0.000001 |
| `hoodie.bloom.index.prune.by.ranges` | 基于 key range 裁剪文件 | true；随机 key 可评估是否关闭 |
| `hoodie.bloom.index.use.caching` | Bloom 是否缓存输入 RDD | true |
| `hoodie.bloom.index.use.treebased.filter` | Bloom range 裁剪使用 interval tree | true |
| `hoodie.bloom.index.bucketized.checking` | Bloom 候选检查 bucket 化，缓解 skew | true |

| `hoodie.index.bucket.engine` | Bucket index 引擎 | SIMPLE |
| `hoodie.bucket.index.num.buckets` | 每个分区 bucket 数 | 256；需按数据规模规划 |
| `hoodie.bucket.index.hash.field` | Bucket hash 字段 | 默认可使用 record key，按业务显式指定更清晰 |

| `hoodie.metadata.record.index.enable` | 创建 Metadata Table Record Index | false |
| `hoodie.record.index.use.caching` | Record Index 是否缓存输入 | true |
| `hoodie.record.index.update.partition.path` | Record Index 下是否按新分区路径移动记录 | false |
| `hoodie.metadata.record.index.min.filegroup.count` | Record Index 最小 file group 数 | 10 |
| `hoodie.metadata.record.index.max.filegroup.count` | Record Index 最大 file group 数 | 10000 |
| `hoodie.metadata.record.index.max.filegroup.size` | Record Index 单 file group 最大大小 | 1073741824 |
| `hoodie.metadata.record.index.growth.factor` | Record Index 初始化估算增长因子 | 2.0 |
