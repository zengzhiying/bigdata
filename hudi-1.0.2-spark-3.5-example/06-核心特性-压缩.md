# Hudi 核心特性：压缩 (Compaction)

## 概述

压缩（Compaction）是 Apache Hudi 中**专门用于 MOR 表**的关键操作，用于将增量日志文件（Avro）合并到基础文件（Parquet）中，以优化存储和查询性能。

### 核心价值

- **优化查询性能**：减少读取时需要合并的文件数量
- **减少存储开销**：清理冗余数据，压缩小文件
- **提升 Read Optimized 查询**：更新后的数据对 RO 查询可见
- **平衡写入与读取**：通过后台压缩维持系统性能

---

## 1. 为什么需要 Compaction？

### 1.1 MOR 表的写入机制

```
MOR 表更新流程:
1. 初始写入 → 创建 Base File (Parquet)
   [file_v1.parquet]: Record1, Record2, Record3

2. 后续更新 → 追加 Delta Log (Avro)
   [file_v1.parquet]: Record1, Record2, Record3
   [file_v1.log]: Update Record2 → Record2'

3. 再次更新 → 继续追加 Delta Log
   [file_v1.parquet]: Record1, Record2, Record3
   [file_v1.log]: Update Record2 → Record2', Insert Record4

问题:
• Delta Log 越来越多
• Snapshot Query 需要合并多个文件 → 性能下降
• Read Optimized Query 读不到最新数据
```

### 1.2 Compaction 的作用

```
Compaction 操作:
合并前:
  Base: [Record1, Record2, Record3]
  Log:  [Record2', Record4]

合并后:
  Base: [Record1, Record2', Record3, Record4]
  Log:  (清空)

效果:
✓ 减少文件数量
✓ 加快 Snapshot Query
✓ Read Optimized Query 可见最新数据
✓ 释放存储空间
```

## 2. Compaction 类型

### 2.1 Inline Compaction（内联压缩）

**定义：** 在写入操作**同步执行**的压缩

**特点：**
- ✅ 自动触发，无需额外调度
- ✅ 保证数据新鲜度
- ❌ 增加写入延迟
- ❌ 阻塞写入操作

**配置：**
```scala
.option("hoodie.compact.inline", "true")  // 启用内联压缩
.option("hoodie.compact.inline.max.delta.commits", "5")  // 每5次提交触发
```

**适用场景：**
- 写入不频繁的批处理作业
- 对写入延迟不敏感
- 需要保证数据实时可见

### 2.2 Async Compaction（异步压缩）

**定义：** 在后台**异步执行**的压缩，不阻塞写入

**特点：**
- ✅ 不阻塞写入操作
- ✅ 写入延迟低
- ✅ 适合高频写入
- ❌ 需要额外调度
- ❌ 数据可见性有延迟

**配置：**
```scala
// 写入时调度压缩任务（不执行）
.option("hoodie.compact.inline", "false")
.option("hoodie.compact.schedule.inline", "true")
.option("hoodie.compact.inline.max.delta.commits", "5")

// 单独运行压缩作业
spark-submit --class org.apache.hudi.utilities.HoodieCompactor \
  --target-base-path /path/to/table \
  --parallelism 100
```

**关键理解：** Async Compaction 不是“Spark 写入任务结束后，Hudi 仍然在后台自动压缩”。普通批量 Spark 作业退出后，Driver 和内部线程都会结束，不会留下常驻后台进程。

Async Compaction 实际上拆成两个动作：

```
Schedule Compaction：生成压缩计划，写入 Timeline，例如 .compaction.requested
Execute Compaction：执行压缩计划，合并 Base File + Delta Logs，生成新的 Base File
```

因此，当配置为：

```scala
.option("hoodie.compact.inline", "false")
.option("hoodie.compact.schedule.inline", "true")
```

含义是：**写入任务只负责调度压缩计划，不负责执行压缩**。真正执行压缩需要以下任一方式：

1. 启动独立的 compaction Spark 作业（Cron、Airflow、DolphinScheduler、K8s CronJob 等调度）
2. 使用长期运行的流式写入服务承载异步 compaction
3. 改用 Inline Compaction，让写入任务同步执行压缩

**适用场景：**
- 流式写入场景
- 高频更新工作负载
- 对写入延迟敏感
- **生产环境推荐**

### 2.3 对比总结

| 维度 | Inline Compaction | Async Compaction |
|------|------------------|------------------|
| **执行时机** | 写入时同步执行 | 后台异步执行 |
| **写入延迟** | 高（阻塞） | 低（不阻塞） |
| **数据新鲜度** | 即时可见 | 延迟可见 |
| **资源占用** | 占用写入资源 | 独立资源 |
| **调度复杂度** | 简单（自动） | 复杂（需独立作业或常驻进程） |
| **生产推荐** | 批处理 | 流式处理（推荐） |

## 3. Compaction 策略

### 3.1 触发条件

**基于提交次数：**
```scala
.option("hoodie.compact.inline.max.delta.commits", "5")
// 每累积 5 次提交，触发一次压缩
```

**基于时间：**
```scala
.option("hoodie.compact.inline.trigger.strategy", "TIME_ELAPSED")
.option("hoodie.compact.inline.max.delta.seconds", "3600")
// 每小时触发一次压缩
```

**基于文件数量：**
```scala
.option("hoodie.compact.inline.trigger.strategy", "NUM_COMMITS")
.option("hoodie.compact.inline.max.delta.commits", "10")
// Delta 文件超过 10 个时触发
```

### 3.2 压缩策略类型

#### 3.2.1 UnBoundedCompactionStrategy（默认）

**特点：** 压缩所有待压缩的文件组

**配置：**
```scala
.option("hoodie.compaction.strategy", 
  "org.apache.hudi.table.action.compact.strategy.UnBoundedCompactionStrategy")
```

**适用：** 大多数场景

#### 3.2.2 BoundedIOCompactionStrategy

**特点：** 限制单次压缩的 IO 量

**配置：**
```scala
.option("hoodie.compaction.strategy",
  "org.apache.hudi.table.action.compact.strategy.BoundedIOCompactionStrategy")
.option("hoodie.compaction.target.io", "512000")  // 限制 512GB
```

**适用：** 控制压缩对系统的影响

#### 3.2.3 LogFileSizeBasedCompactionStrategy

**特点：** 基于 Delta Log 大小决定是否压缩

**配置：**
```scala
.option("hoodie.compaction.strategy",
  "org.apache.hudi.table.action.compact.strategy.LogFileSizeBasedCompactionStrategy")
.option("hoodie.compaction.logfile.size.threshold", "1073741824")  // 1GB
```

**适用：** 优化存储空间

## 4. Compaction 生命周期

### 4.1 完整流程

```
1. 写入阶段
   ├─ 数据写入到 Delta Logs
   └─ 检查是否达到压缩触发条件

2. 调度阶段 (Schedule)
   ├─ 选择需要压缩的文件组
   ├─ 生成 Compaction Plan
   └─ 记录到 Timeline (.compaction.requested)

3. 执行阶段 (Execute)
   ├─ 读取 Base Files 和 Delta Logs
   ├─ 合并数据
   ├─ 写入新的 Base Files
   └─ 完成压缩 (.commit)

4. 清理阶段 (Clean)
   ├─ 删除旧的 Base Files
   ├─ 删除已压缩的 Delta Logs
   └─ 释放存储空间
```

### 4.2 Timeline 状态

```
正常流程:
.compaction.requested  → 压缩已调度
.compaction.inflight   → 压缩正在执行
.commit                → 压缩完成

异常处理:
.compaction.inflight → 长时间未完成
  ↓
通过 Rollback 回滚
  ↓
重新调度压缩
```

## 5. 配置参数详解

### 5.1 核心配置

| 参数 | 说明 | 默认值 | 推荐值 |
|------|------|--------|--------|
| `hoodie.compact.inline` | 启用内联压缩 | false | false（生产） |
| `hoodie.compact.schedule.inline` | 内联调度压缩 | false | true |
| `hoodie.compact.inline.max.delta.commits` | 触发压缩的提交数 | 5 | 5-10 |
| `hoodie.compaction.strategy` | 压缩策略类 | UnBounded... | 默认 |
| `hoodie.compaction.target.io` | 目标 IO 量（字节） | 512000 MB | 根据集群 |

#### 核心参数生效方式

| 参数组合 | Schedule | Execute | 适用场景 |
|---------|----------|---------|----------|
| `hoodie.compact.inline=true` | 写入任务负责 | 写入任务负责 | 批处理、Demo、低频写入 |
| `hoodie.compact.inline=false` + `hoodie.compact.schedule.inline=true` | 写入任务负责 | 独立 compaction 作业负责 | 生产异步压缩 |
| 两者都为 `false` | 独立服务负责 | 独立服务负责 | 完全外部化 table service |

`hoodie.compact.inline.max.delta.commits` 控制“什么时候尝试调度压缩”，默认触发策略是 `NUM_COMMITS`。例如配置为 `5` 时，表示距离上次 compaction 或 compaction request 之后累计 5 次 delta commit，就尝试生成新的 compaction plan。

如果同时配置了 `LogFileSizeBasedCompactionStrategy` 和 `hoodie.compaction.logfile.size.threshold`，那么达到 delta commit 数量只代表“开始尝试调度”；最终哪些 file group 进入 compaction plan，还要看 log 文件大小是否超过阈值。

### 5.2 高级配置

| 参数 | 说明 | 默认值 |
|------|------|--------|
| `hoodie.compaction.logfile.num.threshold` | 触发的 Log 文件数 | 10 |
| `hoodie.compaction.logfile.size.threshold` | 触发的 Log 文件大小 | 1GB |
| `hoodie.parquet.small.file.limit` | 小文件大小限制，用于写入时的小文件填充优化 | 100MB |
| `hoodie.compaction.reverse.log.read.enabled` | 反向读取 Log | false |

### 5.3 生产环境推荐配置

```scala
// 异步压缩配置（推荐）
df.write.format("hudi")
  .option("hoodie.datasource.write.table.type", "MERGE_ON_READ")
  
  // 压缩调度
  .option("hoodie.compact.inline", "false")
  .option("hoodie.compact.schedule.inline", "true")
  .option("hoodie.compact.inline.max.delta.commits", "5")
  
  // 压缩策略
  .option("hoodie.compaction.strategy", 
    "org.apache.hudi.table.action.compact.strategy.LogFileSizeBasedCompactionStrategy")
  .option("hoodie.compaction.logfile.size.threshold", "1073741824")  // 1GB
  
  // 小文件调优：影响写入时的小文件填充，不是 compaction 执行开关
  .option("hoodie.parquet.small.file.limit", "104857600")  // 100MB
  
  .save(path)
```

这段配置只会让写入任务在满足条件时生成 compaction plan。一次性批任务写完就退出时，不会有后台线程继续执行压缩；需要再提交独立 compaction 作业，或把 `hoodie.compact.inline` 改为 `true`。

## 6. 运行异步 Compaction

异步 compaction 的执行方式取决于写入任务是否常驻：

```
一次性批量写入任务:
  写入完成后 Spark Application 退出
  如果只配置 schedule.inline=true，只会留下 .compaction.requested
  需要后续独立 spark-submit 执行 compaction

长期运行的流式写入任务:
  Spark Application 一直运行
  可以在同一个常驻进程里调度/执行异步 table service
```

### 6.1 使用 Spark 运行

```bash
# 方式 1: 使用 HoodieCompactor
spark-submit \
  --class org.apache.hudi.utilities.HoodieCompactor \
  --master yarn \
  --deploy-mode cluster \
  --conf spark.serializer=org.apache.spark.serializer.KryoSerializer \
  hudi-utilities-bundle.jar \
  --base-path s3://bucket/table_path \
  --table-name my_table \
  --parallelism 200 \
  --strategy org.apache.hudi.table.action.compact.strategy.UnBoundedCompactionStrategy

# 方式 2: 使用 DeltaStreamer（包含压缩）
spark-submit \
  --class org.apache.hudi.utilities.deltastreamer.HoodieDeltaStreamer \
  hudi-utilities-bundle.jar \
  --table-type MERGE_ON_READ \
  --target-base-path s3://bucket/table_path \
  --target-table my_table \
  --continuous \
  --compact-scheduling-minshare 1 \
  --compact-scheduling-weight 1
```

### 6.2 调度方式

#### 6.2.1 Cron 定时任务

```bash
# 每小时运行一次压缩
0 * * * * /path/to/run_compaction.sh

# run_compaction.sh
#!/bin/bash
spark-submit \
  --class org.apache.hudi.utilities.HoodieCompactor \
  --master yarn \
  hudi-utilities-bundle.jar \
  --base-path s3://bucket/table_path \
  --table-name my_table \
  --parallelism 200
```

#### 6.2.2 Airflow DAG

```python
from airflow import DAG
from airflow.providers.apache.spark.operators.spark_submit import SparkSubmitOperator

compaction_task = SparkSubmitOperator(
    task_id='hudi_compaction',
    application='/path/to/hudi-utilities-bundle.jar',
    java_class='org.apache.hudi.utilities.HoodieCompactor',
    application_args=[
        '--base-path', 's3://bucket/table_path',
        '--table-name', 'my_table',
        '--parallelism', '200'
    ],
    dag=dag
)
```

#### 6.2.3 持续运行（Continuous Mode）

```scala
// 在长期运行的 Spark Streaming 作业中持续调度压缩
// 注意：只有作业持续运行时，异步服务才可能继续工作
df.writeStream
  .format("hudi")
  .option("hoodie.compact.schedule.inline", "true")
  .option("hoodie.compact.inline.max.delta.commits", "5")
  .start()

// 单独的持续压缩进程
spark-submit \
  --class org.apache.hudi.utilities.HoodieCompactor \
  --conf spark.hudi.compaction.continuous=true \
  hudi-utilities-bundle.jar
```

```scala
// 增加压缩并行度
.option("hoodie.compaction.parallelism", "200")

// 根据数据量调整
```

```bash
spark-submit \
```

```scala
.option("hoodie.parquet.small.file.limit", "104857600")  // 100MB

```

`hoodie.parquet.small.file.limit` 主要用于写入时的小文件填充和 bin-packing，不负责触发或执行 compaction。MOR compaction 的核心目标是合并 Base File 与 Delta Logs；如果要专门优化文件布局和小文件数量，还需要结合 Clustering。

### 7.3 故障排查

#### 问题 1: 压缩长时间未完成

**原因：**
- 数据量过大
- 并行度不足
- 资源不足

**解决：**
```bash
# 1. 检查压缩状态
compaction show --instant <instant_time>

# 2. 增加并行度重试
spark-submit ... --parallelism 500

# 3. 如果卡住，回滚后重试
rollback --instant <instant_time>
```

#### 问题 2: 压缩后查询仍然慢

**原因：**
- 文件碎片化
- 需要 Clustering
- 索引问题

**解决：**
```scala
// 运行 Clustering 优化文件布局
spark-submit --class org.apache.hudi.utilities.HoodieClusteringJob
```

#### 问题 3: 压缩消耗过多资源

**原因：**
- 压缩频率过高
- 单次压缩数据量过大

**解决：**
```scala
// 调整触发频率
.option("hoodie.compact.inline.max.delta.commits", "10")  // 增加到10

// 使用 BoundedIO 策略限制单次 IO
.option("hoodie.compaction.strategy", "BoundedIOCompactionStrategy")
.option("hoodie.compaction.target.io", "512000")
```

## 8. 最佳实践

### 8.1 压缩策略选择

✅ **推荐做法：**

1. **生产环境使用异步压缩**
   ```scala
   .option("hoodie.compact.inline", "false")
   .option("hoodie.compact.schedule.inline", "true")
   ```

2. **根据写入频率调整触发条件**
   - 高频写入（分钟级）：`max.delta.commits = 10-20`
   - 中频写入（小时级）：`max.delta.commits = 5-10`
   - 低频写入（天级）：`max.delta.commits = 2-5`

3. **监控和告警**
   - 待压缩文件数 > 阈值 → 告警
   - 压缩延迟 > 阈值 → 告警
   - Read Optimized 查询延迟增加 → 告警

4. **定期检查和维护**
   ```bash
   # 每天检查压缩状态
   compactions show all
   
   # 清理失败的压缩
   compactions repair
   ```

### 8.2 避免的陷阱

❌ **常见错误：**

1. **内联压缩用于高频写入**
   ```scala
   // 错误：阻塞写入
   .option("hoodie.compact.inline", "true")
   ```

2. **压缩频率过低**
   ```scala
   // 错误：Delta Log 堆积
   .option("hoodie.compact.inline.max.delta.commits", "100")
   ```

3. **忽略压缩失败**
   - 未监控压缩状态
   - 不处理失败的压缩任务

4. **资源分配不足**
   ```bash
   # 错误：压缩作业资源太少
   --executor-memory 2G  # 太小
   --parallelism 10      # 太低
   ```

## 9. 与其他特性的关系

### 9.1 Compaction vs Cleaning

| 维度 | Compaction | Cleaning |
|------|-----------|----------|
| **作用** | 合并 Delta Logs | 清理旧版本文件 |
| **目标** | 优化查询性能 | 释放存储空间 |
| **适用表** | 仅 MOR | COW 和 MOR |
| **执行频率** | 频繁 | 定期 |

### 9.2 Compaction vs Clustering

| 维度 | Compaction | Clustering |
|------|-----------|-----------|
| **作用** | 合并 Delta Logs | 重组文件布局 |
| **优化目标** | 减少文件数 | 优化数据局部性 |
| **适用表** | 仅 MOR | COW 和 MOR |
| **性能提升** | Read 查询 | 范围查询 |

### 9.3 压缩与查询的关系

```
压缩前:
  Base: [Record1, Record2]
  Log:  [Record2', Record3]
  
  Snapshot Query:  合并 Base + Log → 慢
  Read Optimized:  仅读 Base → 快，但数据旧

压缩后:
  Base: [Record1, Record2', Record3]
  Log:  (空)
  
  Snapshot Query:  仅读 Base → 快
  Read Optimized:  读 Base → 快，且数据新
```

## 10. 常见问题 (FAQ)

### Q1: 什么时候应该运行 Compaction？

**A:** 
- **实时场景：** 每 5-10 次提交或每小时
- **批处理：** 每天或每次作业结束后
- **关键指标：** 当 Delta Log 数量 > 10 或大小 > 1GB

### Q2: Compaction 会影响写入吗？

**A:**
- **Inline Compaction：** 会阻塞写入，增加延迟
- **Async Compaction：** 不阻塞写入，推荐使用

### Q3: 配置了异步压缩后，批任务结束了还会继续压缩吗？

**A:** 不会。普通 Spark 批任务结束后不会留下 Hudi 后台进程。

```scala
.option("hoodie.compact.inline", "false")
.option("hoodie.compact.schedule.inline", "true")
```

这组配置表示“写入时调度压缩计划，但不执行压缩”。它可能只是在 timeline 中留下 `.compaction.requested`。要真正完成压缩，需要：

1. 额外提交 `HoodieCompactor` 作业执行这些 requested instants
2. 使用常驻流式写入服务承载异步 compaction
3. 或改成 `hoodie.compact.inline=true`，让写入任务同步执行压缩

### Q4: `hoodie.compact.inline.max.delta.commits=5` 是每 5 次提交自动压缩吗？

**A:** 要看 `hoodie.compact.inline` 和 `hoodie.compact.schedule.inline` 的组合：

- `hoodie.compact.inline=true`：达到 5 次 delta commit 后，写入任务会尝试调度并执行压缩
- `hoodie.compact.inline=false` 且 `hoodie.compact.schedule.inline=true`：达到 5 次 delta commit 后，只尝试调度压缩计划
- 如果使用 log 文件大小策略，还要满足 `hoodie.compaction.logfile.size.threshold` 等策略条件，file group 才会进入压缩计划

### Q5: Compaction 失败怎么办？

**A:**
```bash
# 1. 查看失败原因
compaction show --instant <instant_time>

# 2. 回滚失败的压缩
rollback --instant <instant_time>

# 3. 检查资源和配置后重试
spark-submit ... --parallelism 200
```

### Q6: 如何判断是否需要 Compaction？

**A:** 检查以下指标：
```sql
-- 查看 Delta Log 数量
SELECT _hoodie_file_name, COUNT(*) as log_count
FROM hudi_table_ro
WHERE _hoodie_file_name LIKE '%.log%'
GROUP BY _hoodie_file_name

-- 如果 log_count > 10，需要压缩
```

### Q7: COW 表需要 Compaction 吗？

**A:** 不需要。Compaction 是 MOR 表特有的操作。COW 表直接重写文件，无需压缩。
